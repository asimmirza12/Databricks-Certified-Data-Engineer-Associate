The idea

A standard plug for talking to databases

Databases come from many makers, but programs need one common way to talk to them. Two long-established standards provide it.

  • JDBC is the standard used by programs that run on Java technology. Spark is one of them, so JDBC is Spark's natural way to reach a database.
  • ODBC is an older, language-neutral standard that does the same job. Reporting tools and Python libraries often use it.

Both work the same way: a small piece of software called a driver translates between the standard and one specific database. You give an address, a user name and a password, send a SQL query, and get rows back.

In a Databricks notebook, the usual route is Spark's built-in JDBC reader. You tell it where the database is and which table or query you want. It returns a DataFrame, which you save to a bronze table or to files in a volume. Then you schedule the notebook with Lakeflow Jobs.

This is the do-it-yourself path. It gives total control and it works with nearly any database. In exchange, you are responsible for what a managed connector would have done: finding what changed, running in parallel, and keeping the password safe.

Everyday analogy

Travel plug adaptors. Every country has its own wall socket, but your charger has one plug. An adaptor for each country lets the same charger work anywhere. The charger is Spark, the socket is a database, and the adaptor is the JDBC driver for that database.

How it works

One connection, or several at once

By default Spark reads a database table through a single connection. One executor asks for all the rows and the others stand idle. For a large table that is slow.

Four options, always used together, turn on parallel reading:

  • partitionColumn: a numeric column to split on, ideally evenly spread and indexed, such as an ID.
  • lowerBound and upperBound: the range of that column you expect.
  • numPartitions: how many pieces, and therefore how many simultaneous connections.

The bounds only decide where to cut. They do not filter. Rows below the lower bound all go into the first piece, and rows above the upper bound all go into the last piece. Every row is still read.

Code

A JDBC ingestion notebook

# Never type a password into a notebook. Fetch it from a secret store at run time.
user     = dbutils.secrets.get(scope="bakery-secrets", key="orders-db-user")
password = dbutils.secrets.get(scope="bakery-secrets", key="orders-db-password")

jdbc_url = "jdbc:postgresql://orders-db.bakery.example:5432/sales"

orders = (spark.read
    .format("jdbc")
    .option("url", jdbc_url)
    .option("dbtable", "public.orders")         # the table to read
    .option("user", user)
    .option("password", password)
    .option("partitionColumn", "order_id")      # split on this numeric column
    .option("lowerBound", 1)
    .option("upperBound", 1000000)
    .option("numPartitions", 4)                # 4 queries at the same time
    .option("fetchsize", 100000)               # rows fetched per round trip
    .load())

# Land it in bronze as a Unity Catalog table.
orders.write.mode("overwrite").saveAsTable("bakery.bronze.orders_db_raw")

That is a full load. For an incremental load, send a query with a high-water mark instead of a table name:

# Find the newest change we already hold.
last = spark.sql("SELECT coalesce(max(updated_at), '1900-01-01') FROM bakery.bronze.orders_db_raw").first()[0]

changed = (spark.read.format("jdbc")
    .option("url", jdbc_url)
    # "query" is run by the database itself, so only changed rows travel over the network.
    .option("query", f"SELECT * FROM public.orders WHERE updated_at > '{last}'")
    .option("user", user).option("password", password)
    .load())

changed.write.mode("append").saveAsTable("bakery.bronze.orders_db_raw")

Unity Catalog can hold the login for you. A JDBC connection stores the address and credentials once, and people with the USE CONNECTION privilege read through it without ever seeing the password:

orders = (spark.read.format("jdbc")
    .option("databricks.connection", "bakery_orders_db")   # a Unity Catalog connection
    .option("dbtable", "public.orders")
    .load())

ODBC from a notebook follows the same pattern with a Python ODBC library and the database's ODBC driver installed on the compute. Because Spark speaks JDBC natively, JDBC is the usual choice inside notebooks. Verify driver set-up in the docs for your compute type.

What if I change this?

The options that matter

ChangeEffect
Leave out the four partitioning optionsOne connection, one task. Fine for small tables, slow for big ones.
Raise numPartitionsMore queries run at once and the read gets faster, until the source database cannot cope with the extra load.
Set upperBound far below the real maximumNo rows are lost. But everything above the bound lands in the last piece, so one task does almost all the work.
Choose a partitionColumn with uneven valuesSome pieces are huge and others nearly empty. The read is only as fast as the largest piece.
Use query instead of dbtableThe SQL you write is run by the source database, and only its result is sent. Use it to filter at the source.
Raise fetchsizeFewer round trips, faster reads. Too high and the reading machine may run short of memory.
Write with mode("overwrite") on an incremental readThe table is replaced by just the changed rows. Use append or a MERGE.
Put the password in the notebook as textEveryone who can open the notebook, or its history, can read it. Use secrets or a connection.

Don't confuse these

JDBC traps

Bounds are not filters

lowerBound and upperBound set the cut points for parallel reading. They never exclude rows. To exclude rows, use query with a WHERE.

dbtable vs query

dbtable names a table. query is a SQL statement the source runs. Use one of them, not both.

JDBC out vs JDBC in

Here JDBC lets Databricks read from another database. Separately, reporting tools use JDBC or ODBC drivers to connect to Databricks. Same standard, opposite direction.

Ingesting vs federating

JDBC ingestion copies data into Delta tables. Lakehouse Federation leaves it where it is and queries it live.

Check yourself

Quiz

1. A JDBC read sets lowerBound 1 and upperBound 100,000, but IDs go up to 1,000,000. What happens to rows above 100,000?

Bounds only place the cut points. Rows outside them fall into the first or last piece, which then becomes much larger than the rest.

2. Which set of options makes Spark read a database table in parallel?

All four go together. Without them there is a single connection.

3. What is the safe way to supply a database password in a notebook?

Secrets and connections keep credentials out of code and out of the notebook's history.

4. In the demo with the bound that matched the data, what happened to the read time when you went from 1 partition to 4?

Four equal pieces read at once finish in roughly a quarter of the time of one piece holding everything.

5. An analyst needs to look up a few rows in an outside database once a week. Nothing needs to be stored. What fits?

Federation queries the source in place. Copying the whole table for an occasional look-up would be wasted effort.

Wrap up

Key takeaways

  • JDBC and ODBC are standard ways to talk to databases. Spark uses JDBC.
  • A JDBC read is single-connection unless you set the four partitioning options.
  • Bounds decide the split. They do not filter rows.
  • query pushes your SQL to the source, which is how incremental reads stay small.
  • Keep credentials in secrets or a Unity Catalog connection, and schedule the notebook with Lakeflow Jobs.
