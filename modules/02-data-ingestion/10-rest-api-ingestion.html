The idea

Ask a web address, get data back

An API is a way for one program to ask another for something. A REST API is the most common kind on the internet. Your program sends a request to a web address, and the answer comes back as text, almost always JSON.

A weather service, a payments provider, a delivery company: each offers a REST API. When there is no connector for a system, its REST API is usually the way in.

A notebook that ingests from one does four things:

  1. Authenticate. Prove who you are, usually with a secret key called a token.
  2. Request, page by page. APIs rarely send everything at once. They send a page of results and a pointer to the next page. Fetching page after page is called pagination.
  3. Land the raw response. Save the JSON exactly as received, as a file in a volume.
  4. Load it into a table. Read those files into bronze with Auto Loader or read_files.

Then a Lakeflow Jobs schedule runs the notebook, so it happens every hour or every night without anyone pressing a button.

Everyday analogy

Collecting a long report from a counter. You show your pass (authentication). The clerk hands over ten sheets and says "come back for sheets 11 to 20" (pagination). If you ask too fast, the clerk tells you to slow down (rate limiting). You photocopy every sheet before you start writing on any of them (landing the raw copy). And you send a courier at 6 am every day instead of going yourself (scheduling).

How it works

From web address to bronze table

Why land the raw response first?

You could turn the JSON straight into a table and skip the files. For small reference data that is fine. But most APIs only let you ask for recent data. If your parsing had a bug, the original responses are gone and cannot be requested again. Raw files in a volume are your bronze-before-bronze: you can always reload from them.

Code

Task 1: fetch and land

import json, time, requests
from datetime import date

# The token comes from a secret store, never from text in the notebook.
token   = dbutils.secrets.get(scope="bakery-secrets", key="delivery-api-token")
headers = {"Authorization": f"Bearer {token}"}
url     = "https://api.delivery.example/v1/deliveries"

records, page = [], 1
while True:
    response = requests.get(url, headers=headers, params={"page": page, "per_page": 100}, timeout=30)

    if response.status_code == 429:      # 429 means "too many requests": wait, then try again
        time.sleep(int(response.headers.get("Retry-After", 30)))
        continue
    response.raise_for_status()           # stop with an error on any other failure

    batch = response.json()["data"]
    if not batch:                         # an empty page means we have everything
        break
    records.extend(batch)
    page += 1

# Land the raw response. Volume paths work like ordinary file paths.
# A dated name gives one file per day, and a rerun on the same day replaces it.
path = f"/Volumes/bakery/landing/delivery_api/deliveries_{date.today()}.json"
with open(path, "w") as f:
    for r in records:
        f.write(json.dumps(r) + "\n")      # one JSON record per line

Task 2: load into bronze

checkpoint = "/Volumes/bakery/ops/checkpoints/deliveries_raw"

(spark.readStream.format("cloudFiles")
    .option("cloudFiles.format", "json")
    .option("cloudFiles.schemaLocation", checkpoint)
    .load("/Volumes/bakery/landing/delivery_api/")
    .writeStream
    .option("checkpointLocation", checkpoint)
    .trigger(availableNow=True)
    .toTable("bakery.bronze.deliveries_raw"))

The schedule

The two notebooks become two tasks of one Lakeflow job. Module 04 covers jobs in depth. This is what the definition looks like:

name: ingest_deliveries
schedule:
  quartz_cron_expression: "0 0 2 * * ?"      # every day at 02:00
  timezone_id: "Europe/London"
tasks:
  - task_key: fetch
    max_retries: 2                           # try again if the API is briefly down
    notebook_task:
      notebook_path: /Workspace/bakery/ingest/fetch_deliveries
  - task_key: load
    depends_on:
      - task_key: fetch                      # only after fetch has succeeded
    notebook_task:
      notebook_path: /Workspace/bakery/ingest/load_deliveries
What if I change this?

Choices in an API notebook

ChangeEffect
Fetch only the first pageYou get a small part of the data and no error. The table looks plausible and is badly incomplete.
Ignore the "too many requests" responseThe notebook fails partway, or the API blocks you for a while. Waiting and retrying is the correct reaction.
Write straight to a table and keep no raw fileLess to manage. If the parsing was wrong, there is nothing to reload from.
Use the same file name on every runEach run replaces the last file. A loader that tracks files by name sees nothing new and loads nothing.
Use a new file name on every run, including rerunsA rerun on the same day creates a second file with the same records, and bronze gets duplicates. Remove them in silver, or name files by the day they cover.
Add retries to the fetch taskA brief outage at the API no longer fails the whole night's run.
Run both steps in one notebook instead of two tasksSimpler. But when it fails you cannot tell at a glance which half broke, or rerun only that half.

Three things every API makes you handle

Authentication

A token or key that proves who you are. Keep it in a secret.

Pagination

Results come in pages. Keep asking until a page comes back empty or there is no "next" pointer.

Rate limits

A cap on how many requests you may make in a period. Go over it and you get a "slow down" response.

Don't confuse these

API ingestion traps

Fetching vs loading

Fetching brings data from the API into your storage. Loading turns stored files into table rows. Different steps, different failures.

Volume vs table as landing place

The exam phrase is "land data into cloud storage or directly into Unity Catalog-governed tables". Both are valid. Know why you would pick the volume.

Retry vs rerun

A retry is a job automatically trying a failed task again. A rerun is you starting the job again. Both are safe only if the task is idempotent.

Notebook vs job

The notebook holds the code. The job is what runs it on a schedule with retries and alerts. A notebook alone is not a pipeline.

Check yourself

Quiz

1. What is pagination?

APIs split large results into pages. A limit on call frequency is rate limiting, a different thing.

2. Why save the raw API response to a volume before loading a table?

The raw files are a safety copy of something you may not be able to fetch a second time.

3. Where should the API token be kept?

Secrets keep credentials out of code, output and revision history.

4. In the demo, with the fixed file name deliveries.json, what did the second day's job load?

The loader tracks files by name. Overwriting an already-loaded name gives it nothing new to pick up.

5. What makes the fetch notebook run every night without a person?

Lakeflow Jobs runs notebooks on a schedule, in order, with retries. Auto Loader loads files but does not call APIs.

Wrap up

Key takeaways

  • A REST API returns JSON from a web address. A notebook can call it with ordinary Python.
  • Handle authentication, pagination and rate limits, or the data will be incomplete.
  • Land the raw response in a volume first, then load it into bronze.
  • Name raw files so that a rerun does not create duplicates and a new day is seen as new.
  • Lakeflow Jobs provides the schedule, the task order and the retries.
