The idea

How much to copy, and how to know what changed

Lesson 00-04 introduced batch, streaming and incremental processing. For ingestion, the same ideas turn into three practical patterns.

  • Full load. Copy everything from the source every time and replace what you had. Also called a snapshot load.
  • Incremental load. Copy only what is new or changed since the last run.
  • Streaming load. Stay connected and copy each change shortly after it happens.

Full load is easy and always correct, but it re-reads everything. Incremental and streaming are efficient, but they only work if you can answer one question: what changed since last time? There are three common ways to find out.

  • New files. When data arrives as files, "what is new" means "which files have I not loaded yet". The tool keeps a list of files it has seen.
  • A high-water mark. When the source is a table with a column that only grows, such as an ID or a "last updated" time, you remember the largest value you have loaded and ask for rows above it.
  • Change data capture (CDC). The source database keeps its own log of every insert, update and delete. You read that log and replay it.
Everyday analogy

Keeping a copy of a friend's address book. Full load: photocopy the whole book every week. Simple, slow, never wrong. High-water mark: each week copy only entries added after the last one you have. Fast, but you miss it when a friend changes an old entry or crosses one out. CDC: your friend keeps a notepad of every change ("added Sam", "changed Ana's number", "removed Raj") and you copy from the notepad. Fast and complete.

How it works

Three ways to find the changes

Once you have the changes, you apply them to the target table. New rows are simply appended. Changed rows need an upsert: update the row if it exists, insert it if it does not. Deleted rows must be deleted from the target too, which only CDC or a full load can tell you about.

Where the data comes from

Local files

A file on your own computer, uploaded through the Databricks UI. Good for one-off and small data. Lesson 02-02.

Standard connectors

Building blocks you configure yourself to read files in cloud storage, message streams and more. Auto Loader and COPY INTO belong here. Lessons 02-04 to 02-07.

Managed connectors

Ready-made, fully managed pipelines for business applications and databases, such as Salesforce or SQL Server. Lessons 02-03 and 02-08.

The second and third are the two halves of Lakeflow Connect, the Databricks name for its ingestion tools.

Code

The same table, loaded three ways

-- 1. FULL LOAD: replace the target with everything in the source.
CREATE OR REPLACE TABLE bakery.bronze.customers AS
SELECT * FROM bakery.landing.customers_export;
-- 2. INCREMENTAL with a high-water mark: only rows changed since the newest one we hold.
MERGE INTO bakery.bronze.customers AS t
USING (
  SELECT * FROM bakery.landing.customers_export
  WHERE updated_at > (SELECT coalesce(max(updated_at), '1900-01-01') FROM bakery.bronze.customers)
) AS s
ON t.customer_id = s.customer_id
WHEN MATCHED THEN UPDATE SET *      -- the row exists: overwrite it
WHEN NOT MATCHED THEN INSERT *;     -- the row is new: add it
# 3. INCREMENTAL on files, as a stream that can also run continuously.
# "cloudFiles" is Auto Loader. It remembers which files it has already loaded (lesson 02-05).
(spark.readStream.format("cloudFiles")
    .option("cloudFiles.format", "json")
    .option("cloudFiles.schemaLocation", "/Volumes/bakery/ops/checkpoints/customers")
    .load("/Volumes/bakery/landing/crm_files/customers/")
    .writeStream
    .option("checkpointLocation", "/Volumes/bakery/ops/checkpoints/customers")
    .trigger(availableNow=True)      # load what is new, then stop
    .toTable("bakery.bronze.customers_raw"))

You rarely write CDC by hand. A managed connector reads the source's change log and applies the inserts, updates and deletes for you (lesson 02-08).

What if I change this?

Choosing a pattern, and its price

ChangeEffect
Full load on a table that has grown to a billion rowsStill correct, but every run reads a billion rows to pick up a few thousand changes.
High-water mark on an ID columnNew rows are caught. Changes to existing rows are missed, because their ID did not grow.
High-water mark on a "last updated" columnNew and changed rows are caught. Rows deleted at the source are still missed: a deleted row has no "last updated" value to find.
Append instead of upsert when using "last updated"Every changed row is added again, so the target holds the old and the new version side by side.
Switch to CDCInserts, updates and deletes are all captured. It needs the source database to have change logging turned on.
The source application does not maintain "last updated" reliablyThe high-water mark silently skips changes. Fall back to full load or CDC.

Don't confuse these

Pattern words

Incremental vs streaming

Incremental says how much is read: only the new part. Streaming says when: continuously. A stream that runs once and stops is incremental without being continuous.

High-water mark vs watermark

A high-water mark is the last value you loaded. A "watermark" in Spark streaming is a setting for how late data may arrive. Different things.

CDC vs Change Data Feed

CDC reads changes out of a source database. Change Data Feed is a Delta table feature that lets you read changes made to a Delta table.

Append vs upsert

Append always adds rows. Upsert updates a matching row or inserts a new one. Changed data needs upsert, or you get duplicates.

Check yourself

Quiz

1. Which pattern can detect a row that was deleted at the source, without re-reading the whole table?

Only the source's change log records a delete. A high-water mark looks for rows above a value, and a deleted row is simply not there.

2. In the demo, you changed a city and ran the "high-water mark on id" load. What happened?

The row's ID did not increase, so it was below the mark and never read.

3. A small reference table of 150 rows changes rarely. What is the sensible pattern?

Re-reading 150 rows costs almost nothing and is always correct. Save the machinery for large or fast-changing data.

4. What must a new-file ingestion tool remember between runs?

For files, "what is new" means "what have I not seen". Auto Loader and COPY INTO both keep that record for you.

Wrap up

Key takeaways

  • Full load is simple and complete, but re-reads everything.
  • Incremental load needs a way to know what changed: new files, a high-water mark, or CDC.
  • High-water marks miss deletes. Marks on an ID also miss updates.
  • CDC captures inserts, updates and deletes from the source's own change log.
  • Changed rows need an upsert, not an append.
