02-03 Lakeflow Connect: standard vs managed connectors
The idea

A few parts, each with one job

Every managed connector is assembled from the same small set of parts.

  • A connection is a Unity Catalog object that stores where the source is and how to log in. It is created once and can be reused. Because it is a Unity Catalog object, who may use it is controlled by grants.
  • An ingestion pipeline copies data from the source into destination tables. It runs on serverless compute, on a schedule you choose.
  • Destination tables are streaming tables in the catalog and schema you pick.

Connectors for databases that use CDC need two more parts, because a database's change log cannot wait.

  • An ingestion gateway stays connected to the database and continuously pulls out its changes. It runs on classic compute and must keep running, because databases clear old entries from their change logs. A gateway that is off for too long misses changes for good.
  • A staging volume is a Unity Catalog volume where the gateway parks what it has extracted until the ingestion pipeline picks it up.
Everyday analogy

A newspaper delivery round. The connection is the list of addresses and the gate codes. The printing press runs all night and cannot be paused: papers come off it whether or not a van is waiting. That is the database's change log. The gateway is the worker who stands at the press and stacks every paper as it comes. The loading bay where the stacks wait is the staging volume. The van that does the round at 6 am is the ingestion pipeline. If nobody stands at the press, papers fall on the floor and are swept away.

Keeping history: two ways to store a change

When a source row changes, the destination can react in two ways. The names come from an old data warehousing term, slowly changing dimension (SCD).

SCD type 1: keep the latest

The destination row is overwritten with the new values. The table always matches the source as it is now. Old values are gone. This is the default.

SCD type 2: keep the history

The old version is kept and marked as ended. A new row is added for the new version. Two extra columns, __START_AT and __END_AT, say when each version was current.

There is also a simpler family called query-based connectors. They have no gateway and no staging volume. The pipeline just queries the source database on a schedule for rows that changed. Less to run, but it relies on a column that reveals changes, as in lesson 02-01.

Code

Setting one up

Most people configure a managed connector in the UI, which walks through the same steps. Here they are as code. First the connection:

-- A connection is a Unity Catalog object. Creating one needs the CREATE CONNECTION privilege.
-- secret() reads the password from a secret store, so it never appears in the code.
CREATE CONNECTION bakery_orders_db TYPE sqlserver
OPTIONS (
  host 'orders-db.bakery.example',
  port '1433',
  user 'ingest_reader',
  password secret('bakery-secrets', 'orders-db-password')
);

-- Let the data engineering group build pipelines with it.
GRANT USE CONNECTION ON CONNECTION bakery_orders_db TO `data_engineers`;

Then the pipeline, as a description of what to ingest and how:

# Illustrative shape. Field names vary by connector: check its documentation.
ingestion_definition:
  ingestion_gateway_id: ${gateway_id}       # database connectors only
  objects:
    - table:
        source_schema: sales
        source_table: customers
        destination_catalog: bakery
        destination_schema: bronze
        table_configuration:
          scd_type: SCD_TYPE_2            # keep history. Default is SCD_TYPE_1.

Reading the result is ordinary SQL. With history kept, "current" rows are those whose end is empty:

-- The current version of every customer, from a table that keeps history.
SELECT customer_id, name, city
FROM bakery.bronze.customers
WHERE __END_AT IS NULL;
What if I change this?

Settings that affect reliability

ChangeEffect
SCD type 1 to SCD type 2The destination keeps every past version of a row, with __START_AT and __END_AT. The table grows faster, and queries must filter for current rows.
Stop the gateway of a database connectorChanges stop being captured. If the database clears its change log before the gateway returns, those changes are lost and a full refresh is needed.
Run the ingestion pipeline hourly instead of dailyDestination tables are fresher. The gateway is unaffected: it captures continuously either way.
Run a full refreshThe destination is rebuilt from a new complete copy of the source. With history tracking on, the accumulated history is erased.
Use a query-based connector instead of a CDC oneNo gateway and no staging volume to run. In exchange it depends on a column that shows which rows changed.
Revoke USE CONNECTION from a groupThey can no longer create or run pipelines that log in through that connection.
The source adds a columnThe connector adapts and the destination gains the column. No code change.

What makes it "reliable"

Automatic retries

Temporary failures, such as a brief network fault, are retried without your involvement.

Incremental by design

Each run continues from where the last stopped. A failed run does not cause gaps or duplicates.

Governed end to end

The connection, the staging volume and the destination tables are all Unity Catalog objects with grants and lineage.

Don't confuse these

Managed connector traps

Gateway vs pipeline

The gateway extracts from the database, continuously, on classic compute. The pipeline loads into tables, on a schedule, on serverless. Only database CDC connectors have a gateway.

SCD type 1 vs type 2

Type 1 overwrites and keeps no history. Type 2 adds a row per version and keeps it all. Type 1 is the default.

Refresh vs full refresh

A normal run brings in what changed. A full refresh throws away the destination and reloads everything.

Staging volume vs destination

The staging volume is a temporary holding area for extracted changes. Your queries read the destination tables, never the staging volume.

Check yourself

Quiz

1. Which part of a database CDC connector must run continuously?

The gateway has to capture changes before the database clears them from its log. The pipeline can run on any schedule.

2. What does a connection store?

A connection is a governed Unity Catalog object holding how to reach and authenticate to one source.

3. A customer's city changes. With SCD type 2, what is in the destination afterwards?

Type 2 keeps each version. __END_AT is filled in on the old one and empty on the current one.

4. In the demo, what happened to changes made while the gateway was off?

With nobody reading the change log, those changes were missed. Only a full refresh brought the destination back in line.

5. Which compute runs the ingestion pipeline of a managed connector?

Ingestion pipelines run on serverless. The gateway, where there is one, is the part on classic compute.

Wrap up

Key takeaways

  • Every managed connector has a connection, an ingestion pipeline and destination streaming tables.
  • Database CDC connectors add an always-on gateway on classic compute and a staging volume.
  • The ingestion pipeline runs on serverless, on your schedule.
  • SCD type 1 keeps the latest values. SCD type 2 keeps history with start and end columns.
  • A full refresh reloads everything and erases kept history.
