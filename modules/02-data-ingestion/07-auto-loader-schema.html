Auto Loader schema inference, enforcement and evolution

Files change shape. A source adds a column, or sends words where a number should be. This lesson is about what Auto Loader does at that moment, and how you choose its reaction.

The idea

Three questions about the shape of the data

1. What is the schema to begin with? You can state it yourself. Or you can let Auto Loader work it out by sampling the first files. That is schema inference. What it finds is saved in the schema location, so later runs reuse it.

2. What happens when a file has a column that is not in the schema? This is the choice between enforcement and evolution. Enforcement means the schema stays as it is. Evolution means the schema is allowed to grow. Auto Loader has four settings for this, called schema evolution modes.

3. What happens to data that does not fit? It need not be lost. Auto Loader can put anything that does not match the schema into a spare column called the rescued data column, named _rescued_data. The row still loads, and the awkward part is kept beside it for you to deal with later.

Everyday analogy

A form with fixed boxes. People are sent a form with boxes for name, date and amount. One day a form comes back with an extra note scribbled in the margin. You have four choices. Redesign the form to add a box for it (evolve). Leave the form alone and copy the note into a "remarks" box (rescue). Reject the form until someone decides what to do (fail). Or ignore the note (none). The "remarks" box is the rescued data column.

How it works

A new column arrives: four possible reactions

The default depends on one thing. If you let Auto Loader infer the schema, the default mode is addNewColumns. If you supply the schema yourself, the default is none.

How inference treats types

When Auto Loader infers a schema from JSON or CSV files, it reads every column as text (a string) by default. It does not guess that price is a number. This is deliberately cautious: text can hold anything, so nothing fails. You have two ways to get real types:

  • cloudFiles.inferColumnTypes set to true makes it guess types from the data.
  • cloudFiles.schemaHints lets you state the types of just the columns you care about, and leave the rest inferred. These are schema hints.

Formats that carry their own schema, such as Parquet and Avro, do not have this problem. Their types are read from the files.

Code

Setting the schema behaviour

checkpoint = "/Volumes/bakery/ops/checkpoints/web_orders_raw"

orders = (spark.readStream.format("cloudFiles")
    .option("cloudFiles.format", "json")
    .option("cloudFiles.schemaLocation", checkpoint)          # inferred schema is stored here
    .option("cloudFiles.schemaHints",                         # types for the columns that matter
            "price DECIMAL(10,2), order_ts TIMESTAMP")
    .option("cloudFiles.schemaEvolutionMode", "rescue")       # never change the schema, never stop
    .load("/Volumes/bakery/landing/web_orders/"))

(orders.writeStream
    .option("checkpointLocation", checkpoint)
    .trigger(availableNow=True)
    .toTable("bakery.bronze.web_orders_raw"))

With addNewColumns, the target table must also be allowed to grow. That is the mergeSchema write option from lesson 01-02:

(orders.writeStream
    .option("checkpointLocation", checkpoint)
    .option("mergeSchema", "true")        # let the Delta table accept the new column
    .trigger(availableNow=True)
    .toTable("bakery.bronze.web_orders_raw"))

Later, in silver, you pick useful values back out of the rescued data column:

-- _rescued_data holds the unmatched fields as JSON text. Pull one out with the : operator.
SELECT order_id,
       price,
       _rescued_data:loyalty::string AS loyalty
FROM bakery.bronze.web_orders_raw
WHERE _rescued_data IS NOT NULL;
What if I change this?

Each mode and option

ChangeEffect
schemaEvolutionMode = addNewColumns (default when the schema is inferred)On a new column the stream fails once with an "unknown field" error, after saving the wider schema. When restarted it carries on, and the column is there. Old rows show NULL in it. A job with automatic retries restarts it for you.
schemaEvolutionMode = rescueThe schema never changes and the stream never stops for this reason. New columns land in _rescued_data.
schemaEvolutionMode = failOnNewColumnsThe stream fails and keeps failing until you update the schema yourself or remove the offending file. The strictest setting.
schemaEvolutionMode = none (default when you supply the schema)New columns are ignored and the stream carries on. Their data is lost unless you set rescuedDataColumn.
No schemaHints and no inferColumnTypes, with JSON or CSVEvery inferred column is a string. Nothing fails, and nothing is a number until you convert it in silver.
cloudFiles.inferColumnTypes = trueTypes are guessed from the sampled files. Convenient, but a guess made from early files may not suit later ones.
A value does not match its column's typeThe column gets NULL for that row, and the original value is kept in _rescued_data if that column exists.
A field arrives as Price when the schema has priceTreated as a mismatch of letter case and sent to _rescued_data.

Enforcement or evolution?

Enforcement

The schema is a contract. failOnNewColumns and none enforce it strictly. rescue enforces it too, while keeping what does not fit.

Evolution

The schema follows the data. addNewColumns is the evolving mode.

Don't confuse these

Schema traps

addNewColumns fails first

It does not glide over a new column. The stream stops once so that the new schema takes effect on restart. Many people expect no failure at all.

rescue vs none

Both keep the schema fixed and the stream running. rescue keeps the unexpected data. none throws it away.

Two defaults

Inferred schema: default addNewColumns. Supplied schema: default none.

Auto Loader vs read_files types

Auto Loader infers JSON and CSV columns as strings by default. read_files infers real types by default.

Check yourself

Quiz

1. Auto Loader infers the schema and you set no evolution mode. A file arrives with a new column. What happens?

The default with an inferred schema is addNewColumns: record the wider schema, stop, and continue with it after a restart.

2. Which mode keeps the schema fixed, keeps the stream running, and loses no data?

rescue puts unexpected columns into _rescued_data. none also keeps running but drops them.

3. By default, what type does Auto Loader give a JSON field containing 4.50?

JSON and CSV columns are inferred as strings unless you turn on inferColumnTypes or give schema hints.

4. In the demo with the price hint on, where did the value "three" end up?

A value that does not fit its column's type is rescued. The row still loads, with NULL in the typed column.

5. What does cloudFiles.schemaHints do?

Hints are a middle path: you fix the important types without writing out every column.

Wrap up

Key takeaways

  • Auto Loader can infer the schema and stores it in the schema location.
  • JSON and CSV columns are inferred as strings unless you ask for types or give hints.
  • Four evolution modes: addNewColumns, rescue, failOnNewColumns, none.
  • addNewColumns fails once and continues after a restart. It is the default when the schema is inferred.
  • _rescued_data keeps new columns, type mismatches and case mismatches that do not fit.
