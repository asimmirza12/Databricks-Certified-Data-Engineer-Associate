COPY INTO: simple incremental file loading

One SQL statement that loads files from a folder into a table and remembers which files it has already loaded. Run it as often as you like: each file goes in once.

The idea

A load you can safely run twice

COPY INTO is a SQL command. You give it a target table, a folder of files and the file format. It reads the files and appends their rows to the table.

Its special quality is memory. The table keeps a record of every file that COPY INTO has loaded into it. On the next run, files already on that record are skipped and only new files are loaded.

A task that gives the same end result however many times you run it is called idempotent. COPY INTO is idempotent. That matters in practice: if a scheduled run fails halfway or is started twice by mistake, you simply run it again and nothing is duplicated.

Everyday analogy

Ticking off deliveries on a clipboard. A shop assistant unpacks boxes from the stock room and ticks each box number on a clipboard. Sent back to "unpack the stock room" a second time, they check the clipboard, see every box is ticked and unpack nothing. When three new boxes arrive, only those three are unpacked. The clipboard is the table's record of loaded files.

How it works

Check the record, load what is missing

Only the new file travels to the table. Because the record lives with the table, there is no separate checkpoint folder to manage.

The statement has four working parts:

  • The target: the table to load into. It must exist already.
  • The source: a folder, usually a volume path.
  • FILEFORMAT: CSV, JSON, Parquet, Avro and others.
  • Two option lists. FORMAT_OPTIONS tell the reader how to understand the files, such as "the first line is a header". COPY_OPTIONS change how the command itself behaves, such as "reload everything".
Try it

Run COPY INTO again and again

Run the command twice and watch the second run do nothing. Let a new file arrive and run again. Then tick force and see why it is dangerous. Try a file pattern and a dry run.

Code

The statement, piece by piece

-- The target must exist. An empty table with no columns is allowed:
-- COPY INTO can work the columns out from the files (see mergeSchema below).
CREATE TABLE IF NOT EXISTS bakery.bronze.prices_raw;

COPY INTO bakery.bronze.prices_raw
FROM '/Volumes/bakery/landing/supplier_drop/prices/'     -- the folder to load from
FILEFORMAT = CSV
FORMAT_OPTIONS (
  'header' = 'true',          -- first line holds column names
  'inferSchema' = 'true'      -- work out column types from the data
)
COPY_OPTIONS (
  'mergeSchema' = 'true'      -- let the table take on the columns found in the files
);

You can narrow which files are considered, and transform columns on the way in:

-- Only files whose names match a pattern, with a little shaping during the load.
COPY INTO bakery.bronze.prices_raw
FROM (
  SELECT item, CAST(price AS DECIMAL(10,2)) AS price, _metadata.file_path AS source_file
  FROM '/Volumes/bakery/landing/supplier_drop/prices/'
)
FILEFORMAT = CSV
PATTERN = 'prices_2026-11-*.csv'
FORMAT_OPTIONS ('header' = 'true');
-- A dry run: check that the first 20 rows parse and fit the table. Nothing is written.
COPY INTO bakery.bronze.prices_raw
FROM '/Volumes/bakery/landing/supplier_drop/prices/'
FILEFORMAT = CSV
VALIDATE 20 ROWS
FORMAT_OPTIONS ('header' = 'true');

To load from a volume you need READ VOLUME on it, plus the usual USE CATALOG and USE SCHEMA, and permission to write to the target table.

What if I change this?

Every important option

ChangeEffect
Run the same statement a second timeNothing is loaded. All files are on the record already.
COPY_OPTIONS ('force' = 'true')The record is ignored and every matching file is loaded again. Rows that were already in the table are now there twice. The default is false.
COPY_OPTIONS ('mergeSchema' = 'true')The table's schema may grow to include columns found in the files. Needed when the target was created with no columns.
PATTERN = '...'Only files whose names match are considered. Others are left alone and stay unloaded.
FILES = ('a.csv', 'b.csv')Only the named files are considered. Use FILES or PATTERN, not both.
VALIDATE, optionally with a number of rowsThe data is checked against the table but not written. Good before a first load.
Leave out 'header' = 'true' for CSV files that have a header lineThe header line is loaded as a row of data, and columns get placeholder names.
Add a SELECT in the FROMYou can pick, rename and cast columns during the load.
Compare

COPY INTO or Auto Loader?

Both load new files only. Auto Loader is the subject of the next three lessons. Here is the short version.

COPY INTOAuto Loader
Written inSQLPython or SQL (as a streaming table)
Where "files already loaded" is rememberedWith the target tableIn a checkpoint location you provide
Comfortable number of filesThousandsMillions and more
Schema changes over timeBasic, with mergeSchemaRich: inference, evolution modes, rescued data
Reload a few chosen filesEasy: name them and use forceHarder
Can run continuouslyNo. Each run is a batch.Yes

Databricks recommends Auto Loader over COPY INTO where it is available, and streaming tables as the scalable choice for SQL users. COPY INTO remains a good fit for simple, modest loads, and it is named in the exam guide.

Don't confuse these

COPY INTO traps

FORMAT_OPTIONS vs COPY_OPTIONS

FORMAT_OPTIONS describe the files: header, delimiter, type inference. COPY_OPTIONS steer the command: force, mergeSchema.

force vs overwrite

force does not replace the table's contents. It adds the files' rows again on top of what is there.

COPY INTO vs INSERT INTO

INSERT INTO ... SELECT from files loads them every time it runs. COPY INTO skips files it has loaded before.

Two places for mergeSchema

In COPY_OPTIONS it lets the table gain columns. In FORMAT_OPTIONS it combines differing schemas across the files being read.

Check yourself

Quiz

1. You run the same COPY INTO twice with no new files in between. What does the second run do?

Files that were already loaded are skipped. This is what makes the command safe to retry.

2. Which option makes COPY INTO load files it has already loaded?

force switches off the "already loaded" check. mergeSchema is about columns, and VALIDATE writes nothing at all.

3. Where does 'header' = 'true' belong?

It describes how to read the files, so it is a format option.

4. A folder will receive millions of files and their columns change often. Which tool is the better fit?

COPY INTO suits thousands of files with a stable shape. Auto Loader is built for very large numbers of files and changing schemas.

5. In the demo, what did the VALIDATE run change in the table?

VALIDATE checks that the data would load. It writes no rows and does not mark files as loaded.

Wrap up

Key takeaways

  • COPY INTO loads files from a folder into an existing table with one SQL statement.
  • It skips files it has already loaded, so it is idempotent and safe to rerun.
  • FORMAT_OPTIONS describe the files. COPY_OPTIONS steer the command.
  • force reloads everything and creates duplicates. VALIDATE checks without writing.
  • Good for thousands of files. For millions, or changing schemas, use Auto Loader.
