The idea

Start from the source, then apply four tests

The first question is always the same: where does the data live? The kind of source narrows the choice to one or two tools straight away.

  • Files in cloud storage or a volume: Auto Loader, or COPY INTO for small simple loads.
  • A business application (SaaS): a managed connector if one exists.
  • A database: a managed database connector, or a JDBC notebook.
  • A message stream: a streaming reader.
  • A REST API with no connector: a notebook, scheduled with Lakeflow Jobs.
  • A file on a laptop: upload it.

Then the four things the exam objective names decide between the remaining candidates.

  • Volume: how much data, and for files, how many of them.
  • Frequency: once, nightly, hourly, or continuously.
  • Data type: structured, semi-structured or unstructured, and whether its shape changes.
  • Governance: must access and lineage be controlled by Unity Catalog from the first moment?

One rule sits above the rest: prefer the most managed option that meets the need. Less code that you own means fewer things that break at night.

Everyday analogy

Sending something across town. First, what is it? A letter, a sofa, a live fish. That alone rules out most options. Then: how big, how often, how fragile, and does it need a signature on delivery? You would not hire a removal lorry for a letter, or post a sofa. And if a courier already runs that route every day, you use the courier instead of buying a van.

One more option: partner tools

Other companies sell ingestion products with hundreds of ready-made connectors. Databricks calls them technology partners. Partner Connect is a page in the workspace that sets up a connection to one of them with a few clicks: it creates the Databricks resources the partner needs and hands over the details. A partner tool is the usual answer when a source has no Databricks connector and you would rather not write and maintain the code yourself.

The tools, one glance each

A reminder of what each choice looks like in practice. Recognising these shapes is half of answering exam questions.

-- COPY INTO: SQL, files, idempotent, modest scale.
COPY INTO bakery.bronze.prices_raw
FROM '/Volumes/bakery/landing/supplier_drop/prices/'
FILEFORMAT = CSV FORMAT_OPTIONS ('header' = 'true');
# Auto Loader: files at any scale, schema evolution, batch or continuous.
(spark.readStream.format("cloudFiles")
    .option("cloudFiles.format", "json")
    .option("cloudFiles.schemaLocation", checkpoint)
    .load("/Volumes/bakery/landing/web_orders/")
    .writeStream.option("checkpointLocation", checkpoint)
    .trigger(availableNow=True)
    .toTable("bakery.bronze.web_orders_raw"))
-- Streaming table: Auto Loader for SQL users.
CREATE OR REFRESH STREAMING TABLE bakery.bronze.web_orders_raw
AS SELECT * FROM STREAM read_files('/Volumes/bakery/landing/web_orders/', format => 'json');
# JDBC notebook: any database, your own logic, your own change tracking.
orders = (spark.read.format("jdbc")
    .option("databricks.connection", "bakery_orders_db")
    .option("query", "SELECT * FROM public.orders WHERE updated_at > '2026-11-15'")
    .load())

Managed connectors and partner tools have no code to show: you configure them in a form. That absence is their selling point.

Governance is the constant

Whatever you choose, the exam expects the result to be governed by Unity Catalog: files in volumes, logins in connections, data in catalog tables, with grants and lineage. A design that reads from an ungoverned path with a pasted-in key is the wrong answer even if the tool is right.

Don't confuse these

Choosing traps

Tool first, source second

Do not start from a favourite tool. Auto Loader is excellent and cannot read a database. Identify the source before anything else.

COPY INTO vs Auto Loader

Both load new files once. Scale and schema change point to Auto Loader. Simplicity, SQL and easy reloads point to COPY INTO.

Managed vs partner

A managed connector is built and run by Databricks. A partner connector is another company's product that writes into Databricks.

Hand-built when managed exists

A custom notebook is rarely the best answer when a managed connector covers the source and no special logic is asked for.

Check yourself

Quiz

1. Millions of JSON files arrive in cloud storage each day and their fields change over time. Which tool fits best?

Scale and schema change are Auto Loader's strengths. COPY INTO suits thousands of files, and JDBC is for databases.

2. A company wants its sales application data in Unity Catalog tables with as little engineering as possible. A managed connector exists. What should it use?

Prefer the most managed option that meets the need. Nothing in the question calls for custom code.

3. A source has no Databricks connector, and the team does not want to write API code. What is the usual answer?

Partner tools exist for exactly this gap: many ready-made connectors without hand-written code.

4. Rows deleted in a source database must disappear from the lakehouse copy. Which approach handles that?

Deletes are only visible in the database's change log, which CDC reads. A high-water mark never sees a row that is gone.

5. In the chooser demo, what changed the answer for "files in cloud storage" from COPY INTO to Auto Loader?

For files, scale and schema change are the deciding tests between the two tools.

Wrap up

Key takeaways

  • Identify the kind of source first. It narrows the choice to one or two tools.
  • Then test volume, frequency, data type and governance.
  • Prefer the most managed option that meets the need.
  • Files: Auto Loader, or COPY INTO when small and simple. Apps and databases: managed connectors.
  • No connector: a partner tool, or a notebook scheduled with Lakeflow Jobs.
