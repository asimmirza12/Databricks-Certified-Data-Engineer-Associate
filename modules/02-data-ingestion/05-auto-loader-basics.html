Auto Loader basics: cloudFiles, checkpoints, triggers

Auto Loader is the main tool for loading files on Databricks. It watches a folder, loads each new file exactly once, and copes with millions of them.

The idea

A stream whose source is a folder

Auto Loader is a file source for Spark's Structured Streaming. You point it at a folder. Every file that appears there is treated as a new piece of the stream, read once and written to a table.

You use it by asking for the format cloudFiles. That name is how you recognise Auto Loader in code, and its options all begin with cloudFiles.

Three things make it work:

  • A checkpoint location: a folder where the stream records which files it has finished. This is its memory. With it, each file is loaded exactly once, even if the job crashes and restarts.
  • A schema location: a folder where Auto Loader stores the column names and types it has worked out from the files, so it does not have to guess again on every run.
  • A trigger: the setting that decides whether the stream processes what is waiting and stops, or keeps running.

Although it is built on streaming, Auto Loader is very often used in a batch style: start on a schedule, load whatever is new, stop. The exam guide calls this "batch modes".

Everyday analogy

A letterbox with a diligent clerk. Post drops through the door at any time. A clerk comes by, opens every envelope not yet in the logbook, files the contents, and writes each envelope's number in the logbook. If the clerk is interrupted halfway, they pick up from the logbook, never opening the same envelope twice. The clerk can come once a day, or stand by the door all day. The logbook is the checkpoint.

How it works

Discover, read, write, record

A file counts as done only when its rows are in the table and it is recorded in the checkpoint. That pairing is what gives exactly-once loading.

Auto Loader does not read a million waiting files in one gulp. It works through them in batches. The option cloudFiles.maxFilesPerTrigger caps how many files go into each batch. Its default is 1000. Recent runtime versions tune it for you.

Code

A complete Auto Loader job

checkpoint = "/Volumes/bakery/ops/checkpoints/web_orders_raw"

(spark.readStream
    .format("cloudFiles")                               # this is Auto Loader
    .option("cloudFiles.format", "json")                  # the format of the incoming files
    .option("cloudFiles.schemaLocation", checkpoint)      # where to keep the inferred schema
    .load("/Volumes/bakery/landing/web_orders/")           # the folder to watch
    .writeStream
    .option("checkpointLocation", checkpoint)             # where to record finished files
    .trigger(availableNow=True)                           # load everything waiting, then stop
    .toTable("bakery.bronze.web_orders_raw"))             # a Unity Catalog table

It is common, as here, to use one folder for both the checkpoint and the schema location. Each stream needs its own, never shared with another stream.

SQL users get the same engine through a streaming table. STREAM read_files(...) is Auto Loader in SQL clothing, and the checkpoint is managed for you.

CREATE OR REFRESH STREAMING TABLE bakery.bronze.web_orders_raw
AS SELECT *, _metadata.file_path AS source_file
FROM STREAM read_files(
  '/Volumes/bakery/landing/web_orders/',
  format => 'json'
);

-- Load whatever has arrived since the last refresh.
REFRESH STREAMING TABLE bakery.bronze.web_orders_raw;
What if I change this?

The options that matter most

ChangeEffect
.trigger(availableNow=True)Processes every file waiting, in as many batches as needed, then stops. This is the batch style. It is also the trigger to use on serverless compute.
.trigger(processingTime="1 minute")The stream stays running and looks for new files every minute.
Delete or change checkpointLocationThe stream forgets every file it loaded. On the next run it loads them all again, and the table gets duplicates.
Leave out cloudFiles.schemaLocation without giving a schemaAuto Loader has nowhere to store what it infers, and the stream cannot start.
cloudFiles.includeExistingFiles = falseFiles already in the folder when the stream first starts are ignored. Only later arrivals are loaded. The default is true. The option is read only at the very first start.
Lower cloudFiles.maxFilesPerTriggerSmaller batches, each using less memory, and more of them.
Point two streams at the same checkpointThey corrupt each other's record. One checkpoint per stream, always.
Overwrite a file in the folder with new content, same nameBy default it is not loaded again: that path is already recorded. Send changed data as a new file.

Real life

Auto Loader in production

ScenarioWhat happensFix
A job crashes after writing half of a large backlogOn restart, finished files are skipped and the rest are loadedNothing to fix. Rerun the job.
Someone "tidies up" by deleting the checkpoint folderThe next run reloads months of files into bronzeTreat checkpoints as part of the table. Never delete one unless you intend a full reload into an emptied table.
A new stream is pointed at a folder holding three years of history that is not wantedBy default all of it is loaded on the first runSet cloudFiles.includeExistingFiles to false before the first start
The first run over a huge backlog runs out of memoryBatches are too large for the computeLower maxFilesPerTrigger, or use larger compute
An hourly job on serverless fails with a trigger errorNo trigger was set, and serverless needs an explicit oneAdd .trigger(availableNow=True)
Don't confuse these

Auto Loader traps

cloudFiles.format vs format

.format("cloudFiles") selects Auto Loader. cloudFiles.format says what the incoming files are: json, csv, parquet.

Checkpoint vs schema location

The checkpoint records progress: which files are done. The schema location records structure: which columns exist. Often the same folder, different jobs.

Streaming code, batch behaviour

readStream with availableNow runs and stops. Auto Loader does not require always-on compute.

Auto Loader vs COPY INTO memory

Auto Loader remembers files in a checkpoint folder. COPY INTO remembers them with the target table.

Check yourself

Quiz

1. How do you tell Spark to use Auto Loader?

Auto Loader is the cloudFiles streaming source. The real file type goes in cloudFiles.format.

2. What does the checkpoint location hold?

It is the stream's memory of progress, which is what makes each file load exactly once.

3. Which trigger loads everything waiting and then stops?

availableNow is the batch-style trigger. The other two keep the stream running.

4. In the demo, what happened after you deleted the checkpoint and ran the stream again?

Without its record, the stream sees every file as new. The table is appended to, so the old rows are doubled.

5. A new stream should ignore files that were already in the folder. Which option does that?

With it set to false before the first start, only files arriving afterwards are processed.

Wrap up

Key takeaways

  • Auto Loader is the cloudFiles streaming source: a stream that reads new files from a folder.
  • The checkpoint records finished files and gives exactly-once loading. Never delete or share it.
  • The schema location stores the columns and types Auto Loader has worked out.
  • availableNow runs it batch style: load what is waiting, then stop.
  • In SQL, a streaming table over STREAM read_files(...) is the same engine.
