Unstructured data: documents, images and other files

Invoices as PDFs, photos of deliveries, scanned forms. They have no rows or columns, yet they still need to be collected, tracked and governed. Here is how.

The idea

Keep the files in a volume, and a table about the files

Unstructured data is any file that is not made of rows and columns: PDFs, images, audio, video, Word documents. You cannot "load" a photograph into columns the way you load a CSV.

So the approach has two parts.

  • The files live in a volume. A volume stores any kind of file and puts it under Unity Catalog's access control.
  • A table describes the files. One row per file, with its path, size and the time it was last changed. Optionally the row also carries the file's raw contents. This table is what makes the files countable, searchable and joinable with the rest of your data.

Spark has a file format made for building that table, called binaryFile. It does not try to understand what is inside. It reads each file as one row.

Later steps can then work on the contents, for example extracting the text from each PDF. That is transformation, not ingestion. Ingestion's job is to get every file registered, once, with nothing missed.

Everyday analogy

A museum store room. The objects sit on shelves. You cannot put a vase into a spreadsheet. But the museum keeps a catalogue: one line per object, with its shelf, its size and the date it arrived. Curators search the catalogue and then fetch the object. The shelves are the volume. The catalogue is the table.

How it works

One row for each file

The content column holds the file itself as raw bytes. The other three columns describe it.

The four columns that binaryFile produces are always the same:

  • path: where the file is.
  • modificationTime: when it was last changed.
  • length: its size in bytes.
  • content: the raw bytes of the file.

Because the engine is still Auto Loader, everything from lessons 02-05 and 02-06 applies: a checkpoint, exactly-once loading, and a choice of file detection mode.

Code

Registering files in a table

checkpoint = "/Volumes/bakery/ops/checkpoints/supplier_docs"

(spark.readStream.format("cloudFiles")
    .option("cloudFiles.format", "binaryFile")     # one row per file, contents not interpreted
    .option("pathGlobFilter", "*.pdf")               # only pick up PDFs
    .load("/Volumes/bakery/landing/supplier_docs/")
    .writeStream
    .option("checkpointLocation", checkpoint)
    .trigger(availableNow=True)
    .toTable("bakery.bronze.supplier_docs"))

The same in SQL, as a streaming table that refreshes hourly:

CREATE OR REFRESH STREAMING TABLE bakery.bronze.supplier_docs
SCHEDULE EVERY 1 HOUR
AS SELECT path, modificationTime, length, content
FROM STREAM read_files(
  '/Volumes/bakery/landing/supplier_docs/',
  format => 'binaryFile',
  pathGlobFilter => '*.pdf'
);

If you only need to know which files exist, leave the contents out and keep the table small:

-- A light catalogue: where each file is, how big, and when it changed.
SELECT path, length, modificationTime
FROM bakery.bronze.supplier_docs
WHERE length > 5000000          -- files larger than about 5 MB
ORDER BY modificationTime DESC;

Turning document contents into text is a separate step. Databricks has an AI function for it, ai_parse_document, which takes the content column. It is outside ingestion, and its options change quickly, so check the docs before using it.

What if I change this?

Options for file ingestion

ChangeEffect
Add pathGlobFilterOnly files whose names match are picked up. Others in the folder are ignored.
Keep the content columnThe table holds a full copy of every file. Handy for processing, but the table becomes as large as all the files together.
Drop the content columnThe table is a small list of files. Anything that needs the contents reads the file from its path in the volume.
Use spark.read instead of Auto LoaderEvery file is read on every run. Fine for a one-off, wasteful for a folder that keeps growing.
Use binaryFile on a CSV fileYou get one row holding the whole file as bytes, not one row per line. binaryFile never parses.
Replace a file with a new version under the same nameBy default it is not picked up again. Deliver new versions under new names.

Don't confuse these

Unstructured data traps

Volume vs table

The files themselves belong in a volume. The table holds information about them. Unstructured data is governed through volumes.

binaryFile does not parse

It gives one row per file, whatever the file is. It does not read text out of a PDF or pixels out of an image.

Semi-structured vs unstructured

JSON has labels and can become columns: semi-structured. A PDF or an image has neither: unstructured.

Ingesting vs understanding

Registering files is ingestion. Extracting meaning from them is a later transformation step.

Check yourself

Quiz

1. Which Unity Catalog object is meant for storing PDF and image files?

Volumes hold files of any kind under governance. Tables hold rows.

2. Reading a folder of 500 PDFs with the binaryFile format gives how many rows?

binaryFile treats each file as a single row and does not look inside.

3. Which columns does binaryFile produce?

Three columns describe the file and one, content, holds its bytes.

4. In the demo, what happened to the table's size when you stopped keeping content?

Without the bytes the table is only a list. The files stay in the volume, untouched.

Wrap up

Key takeaways

  • Unstructured files are stored and governed in Unity Catalog volumes.
  • The binaryFile format reads each file as one row: path, modificationTime, length, content.
  • Auto Loader with binaryFile registers each new file exactly once.
  • pathGlobFilter chooses which files are picked up.
  • Keeping content copies the files into the table. Often the path is enough.
