Auto Loader file detection: directory listing vs file notification

Auto Loader loads new files. But how does it find out that a file is new? There are two ways, and the difference decides how well it copes with a very full folder.

The idea

Go and look, or be told

There are only two ways to learn that something new has arrived.

  • Directory listing: go and look. Auto Loader asks cloud storage for the list of files in the folder and compares it with its checkpoint. Anything not yet recorded is new. This needs no setup at all, and it is the default.
  • File notification: be told. Cloud storage is set up to send a small message every time a file lands. Auto Loader reads the messages. It never has to list the folder.

Listing is fine for a folder with a few thousand files. But cloud storage charges for every list request and returns files a page at a time. Listing a folder of ten million files to find ten new ones is slow and wasteful. Notification costs the same whether the folder holds ten files or ten million, because it only ever hears about the new ones.

File notification itself comes in two forms. The older form has each stream set up its own message queue. The newer, recommended form is called file events: it is switched on once for a Unity Catalog external location, and every stream reading from that location can use it.

Everyday analogy

Finding out whether post has come. Directory listing is walking to the letterbox and looking through everything in it, every time, to spot what is new. Easy when the box holds three letters. Hopeless when it holds a year of unopened post. File notification is a doorbell that rings each time the postman delivers. You only get up when there is something new, however full the box is.

How it works

Two routes to the same answer

Whichever way files are discovered, everything else about Auto Loader stays the same: the checkpoint, the schema handling and the exactly-once guarantee from lesson 02-05.

Code

Choosing the mode

base = (spark.readStream.format("cloudFiles")
    .option("cloudFiles.format", "json")
    .option("cloudFiles.schemaLocation", "/Volumes/bakery/ops/checkpoints/web_orders_raw"))

# 1. DIRECTORY LISTING. Nothing to add: it is what you get by default.
listing = base.load("/Volumes/bakery/landing/web_orders/")

# 2. FILE NOTIFICATION WITH FILE EVENTS (recommended).
# Needs: the folder is inside a Unity Catalog external location that has file events enabled.
events = (base
    .option("cloudFiles.useManagedFileEvents", "true")
    .load("s3://bakery-landing/web_orders/"))

# 3. CLASSIC FILE NOTIFICATION (older). Auto Loader creates a queue and a
# notification for this one stream, which needs extra cloud permissions.
classic = (base
    .option("cloudFiles.useNotifications", "true")
    .load("s3://bakery-landing/web_orders/"))

Do not set both options on one stream. On the newest runtime versions, Auto Loader uses file events by itself when they are available for the location. Check the docs for the runtime you are on.

What if I change this?

Mode and its consequences

ChangeEffect
Stay on directory listing as the folder grows to millions of filesEvery run lists the whole folder. Runs get slower and the bill for list requests climbs.
Set cloudFiles.useManagedFileEvents to trueNew files are discovered from events. Discovery time no longer depends on how full the folder is. Requires file events on the external location.
Set cloudFiles.useNotifications to trueThe older per-stream notification setup. It works, but each stream manages its own cloud resources and needs permission to create them.
Run a file-events stream less than once a weekEvents are only kept for a limited time. If the stream has been away too long, Auto Loader falls back to a full listing to be safe. Run at least every 7 days.
Use directory listing for a one-off load of old filesA good choice. A single listing is cheap, and no setup is needed.

Don't confuse these

Detection traps

Default vs recommended

Directory listing is the default. File notification with file events is what Databricks recommends for most workloads. Exam questions can ask for either.

Detection mode vs trigger

The detection mode is how new files are found. The trigger is when the stream runs. They are independent: either mode works with availableNow.

File events vs file arrival trigger

File events help Auto Loader find files. A file arrival trigger starts a job when files land (Module 04). Related ideas, different features.

Notification is not streaming-only

File notification can be used in batch-style runs too. It changes how files are discovered, not whether the compute stays on.

Check yourself

Quiz

1. Which file detection mode does Auto Loader use if you set nothing?

Directory listing is the default because it needs no setup.

2. A folder holds 20 million files and gains 50 a day. Why is directory listing a poor choice?

Listing still loads only new files, thanks to the checkpoint. The waste is in the discovery step, which scales with the folder's size.

3. What does file notification with file events require?

File events are a feature of external locations. Once enabled there, streams reading from that location can use them.

4. In the demo, what changed between the two modes for the same folder?

Both modes find the same files. Notification simply does far less work to get there when the folder is large.

Wrap up

Key takeaways

  • Directory listing asks storage for the folder's contents. It is the default and needs no setup.
  • File notification hears about each new file from cloud storage, so its cost does not grow with the folder.
  • File events are the recommended form of notification, enabled once per external location.
  • The mode changes how files are found, not how they are loaded or tracked.
  • File-events streams should run at least once every 7 days.
