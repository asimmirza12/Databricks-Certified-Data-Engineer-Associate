Semi-structured data: JSON, nested fields, VARIANT

Real data is rarely a flat grid. An order contains a customer, who has an address, and a list of items. This lesson shows how to store that shape and how to reach inside it.

The idea

Boxes inside boxes

Semi-structured data has labels, but not a fixed, flat shape. JSON is the usual example. A JSON record can contain three kinds of thing that a simple table column cannot:

  • A record inside a record, such as a customer with a name and a city. Data inside other data is called nested.
  • A list of values, such as the items in a basket. One order may have one item, another may have twenty.
  • Fields that are sometimes there and sometimes not, such as an optional gift note.

Delta tables can hold all of this. You have two broad choices when you ingest it.

  • Give it a full schema. Spark has column types made for nesting: a struct is a record with named fields, an array is a list, and a map is a set of key and value pairs. Queries are fast and the shape is checked. But every field must be declared, and the schema must change when the data does.
  • Store it as VARIANT. VARIANT is a column type that holds a whole semi-structured value, whatever its shape. No schema is needed up front. You pull out the fields you want when you query. It is stored in an efficient binary form, so it is much faster than keeping JSON as plain text.
Everyday analogy

Packing for a house move. One way is a labelled crate for every category, with a slot for each item: orderly, quick to find things, and useless when you own something that has no slot. The other way is sturdy boxes that take whatever you put in, with a contents note on the lid: nothing is ever refused, and you unpack only what you need. Structs and arrays are the crates. VARIANT is the box.

How it works

One nested record, two ways to keep it

Reaching inside

  • For a struct, use a dot: customer.city.
  • For an array, use a position in square brackets, counting from 0: items[0] is the first item.
  • For a VARIANT column, or a text column that contains JSON, start with a colon: raw:customer.city. Then say what type you want with a double colon: raw:order_id::int.
  • To turn a list into rows, use explode. Each element of the array becomes its own row, with the other columns repeated.

Ingesting and querying nested data

  
First, the VARIANT route. Auto Loader can put each whole record into one VARIANT column:


checkpoint = "/Volumes/bakery/ops/checkpoints/web_orders_variant"

# The target table must already have a VARIANT column with this name.
spark.sql("CREATE TABLE IF NOT EXISTS bakery.bronze.web_orders_variant (raw VARIANT)")

(spark.readStream.format("cloudFiles")
    .option("cloudFiles.format", "json")
    .option("singleVariantColumn", "raw")          # whole record into one VARIANT column
    .load("/Volumes/bakery/landing/web_orders/")
    .writeStream
    .option("checkpointLocation", checkpoint)
    .trigger(availableNow=True)
    .toTable("bakery.bronze.web_orders_variant"))


-- Pull out fields at query time. ":" navigates, "::" converts to a type.
SELECT raw:order_id::int          AS order_id,
       raw:customer.name::string  AS customer_name,
       raw:items[0].sku::string   AS first_item,
       raw:gift_note::string      AS gift_note      -- NULL when the field is absent
FROM bakery.bronze.web_orders_variant;

-- Turn JSON text you already have into VARIANT.
SELECT parse_json('{"order_id": 501, "customer": {"name": "Ana"}}') AS raw;

  
Second, the typed route. In silver you usually flatten the nesting into ordinary columns and rows:


from pyspark.sql import functions as F

orders = spark.table("bakery.bronze.web_orders_typed")   # customer is a STRUCT, items an ARRAY

order_lines = (orders
    .select(
        "order_id",
        F.col("customer.name").alias("customer_name"),   # dot reaches into a struct
        F.explode("items").alias("item"))                # one row per element of the array
    .select("order_id", "customer_name", "item.sku", "item.qty"))

order_lines.write.mode("overwrite").saveAsTable("bakery.silver.order_lines")


-- The same flattening in SQL.
SELECT order_id, customer.name AS customer_name, item.sku, item.qty
FROM bakery.bronze.web_orders_typed
LATERAL VIEW explode(items) exploded AS item;






  
What if I change this?

  
Small differences that change the result

  

    
ChangeEffect

    
Ask a VARIANT for a field that does not existYou get NULL, not an error. Convenient, and it also hides typing mistakes.

    
Write raw:Customer when the field is customerNULL. Paths into VARIANT are case sensitive.

    
Leave off the ::type castThe result is still a VARIANT. It displays like the value, but should be cast before you compare, add or join on it.

    
Cast to a type the value cannot become, such as "Ana"::intAn error. Use try_cast or try_variant_get to get NULL instead.

    
explode a row whose array is empty or NULLThat row disappears from the result. explode_outer keeps it, with NULL for the item.

    
Use singleVariantColumnEach record is stored whole. There is no schema to evolve, and the rescued data column is not used.

    
parse_json on text that is not valid JSONAn error. try_parse_json returns NULL for bad records instead.

    
Keep the JSON as a plain STRING columnIt works, and : can still navigate it, but every query has to re-read the text. VARIANT is faster.

The nesting types

  

    
STRUCT
A record with a fixed set of named fields. customer.name.

    
ARRAY
An ordered list of values of one type. items[0]. Turn it into rows with explode.

    
MAP
Keys and values, where the keys are not known in advance. attributes['colour'].

  

  
The objective mentions getting this data in "via Lakeflow Connect and other managed connectors". Managed connectors land nested source fields as these same types, or as VARIANT, in the destination streaming tables. What you learned here is how to read them afterwards.

Don't confuse these

  
Nested data traps

  

    
Dot vs colon
A dot reaches into a STRUCT column: customer.name. A colon starts a path into VARIANT or JSON text: raw:customer.name.

    
: vs ::
One colon navigates. Two colons convert to a type. raw:qty::int means "find qty, then make it an integer".

    
explode vs explode_outer
explode drops rows whose array is empty or NULL. explode_outer keeps them.

    
VARIANT vs _rescued_data
VARIANT is a way to store whole records on purpose. The rescued data column catches leftovers that did not fit a schema. With a single VARIANT column there are no leftovers.

  






  
Check yourself

  
Quiz

  

    

      1. A VARIANT column raw holds an order. How do you get the customer's city as text?
      
      
      
      
A colon starts the path into a VARIANT, dots continue it, and ::string converts the result.

    

    

      2. What does explode do to an array column?
      
      
      
      
An order with three items becomes three rows, with the order's other columns repeated on each.

    

    

      3. In the demo, what did raw:loyalty_card return?
      
      
      
      
A path that finds nothing gives NULL. No error is raised for a missing field.

    

    

      4. Incoming JSON changes shape often and you do not want ingestion to break. What is the best bronze design?
      
      
      
      
VARIANT accepts any shape with no schema to maintain. Typing can be applied later, in silver.

    

    

      5. Which Auto Loader option loads each whole JSON record into one VARIANT column?
      
      
      
      
You give it the name of the VARIANT column. The other two options are about typed schemas.

Key takeaways

  
    
    
  • Semi-structured data has nested records, lists and optional fields.
    • 
    
  • STRUCT, ARRAY and MAP give it a checked schema. VARIANT stores any shape with none.
    • 
    
  • Dot reaches into a struct. Colon reaches into VARIANT. Double colon casts.
    • 
    
  • explode turns an array into rows. explode_outer keeps rows with empty arrays.
    • 
    
  • A common design: VARIANT in bronze, typed and flattened columns in silver.
