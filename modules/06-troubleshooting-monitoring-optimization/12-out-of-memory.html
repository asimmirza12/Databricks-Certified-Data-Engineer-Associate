Out-of-memory errors

Spill makes a job slow. Running out of memory makes it fail. The first question is always the same: did the driver run out, or an executor? The answer points straight at the fix.

The idea

Two places memory can run out

An out-of-memory error (OOM) happens when a process needs more memory than it has. In Spark there are two kinds of process, and they fail for different reasons.

The driver plans the work and runs your notebook's plain Python. It runs out when you pull a large result back to it:

  • collect() or toPandas() on a big DataFrame copies every row into the driver.
  • Broadcasting a table that is not small: the driver builds it before sending it out.
  • Many notebooks attached to one cluster all keep their state on the driver.

The compute may stop with the termination reason DRIVER_OUT_OF_MEMORY, or the notebook reports that the driver restarted. Fixes: keep big data distributed (write it to a table, aggregate or limit() first, use display() for a look), or choose a larger driver type.

An executor processes partitions. It usually spills rather than failing, but it can run out when one piece of work cannot be split or spilled: a huge skewed partition, a broadcast table too big for its memory, or very large single values (giant arrays or strings). Tasks fail and the executor may be lost; Spark retries, and after several failures the job fails (verify the exact symptoms and messages in the docs). Fixes: fix skew, avoid oversized broadcasts, use more and smaller partitions, carry fewer columns, or use instance types with more memory.

Everyday analogy

The bakery manager's desk. The bakers (executors) each work at their own bench. If the manager (driver) says "bring me every single receipt from every bench", the desk overflows and the office stops. That is a driver OOM. If one baker is handed a cake too big for any bench, that bench collapses. That is an executor OOM.

How it works

collect() pulls everything to one machine

Writing to a table lets each executor save its own part. Nothing piles up on the driver.

Code

Driver-safe habits

sales = spark.read.table("bakery.silver.sales")   # 200 million rows

# Risky: copies every row into the driver's memory
# rows = sales.collect()
# pdf  = sales.toPandas()

# Safe: shrink first, then bring the small result back
daily = sales.groupBy("store_id").sum("amount")    # 60 rows, one per store
pdf = daily.toPandas()

# Safe: just look at a sample
display(sales.limit(1000))

# Safe: keep big results distributed by writing them out
sales.filter("amount > 100").write.mode("overwrite").saveAsTable("bakery.gold.big_orders")

On serverless notebooks you can switch the notebook to high memory (32 GB instead of 16 GB) for plain Python work. It does not change the memory Spark uses. Exact error messages vary; read the termination reason and the driver logs to confirm which process ran out.

What if I change this?

Changes and their effects

ChangeEffect
Replace collect() with a write to a tableEach executor writes its own part; the driver stays light.
Aggregate before toPandas()Only the small result reaches the driver.
Larger driver typeRoom for bigger results and more attached notebooks. Treats the symptom, costs more.
Broadcast a big tableEvery executor and the driver need room for it all; risk of OOM.
More shuffle partitionsSmaller pieces per task, less chance of executor OOM.
Memory-heavier instance types for workersMore room per task for joins, sorts and aggregations.

Don't confuse these

Memory traps

Spill vs OOM

Spill is slow but finishes. OOM fails.

Driver vs executor

Bigger workers do not help a driver OOM, and a bigger driver does not help an executor OOM.

display vs collect

display() shows a limited sample; collect() brings back everything.

More memory last

Fix the cause first. Bigger machines cost money every run.

Check yourself

Quiz

1. A notebook fails right after df.toPandas() on 300 million rows. Which process most likely ran out?

toPandas() copies all rows into the driver.

2. What is the best first fix for that failure?

Keep big data distributed and only bring small results back.

3. Executors keep failing on one task of a join. What is a likely cause?

Those are pieces of work an executor cannot split or spill.

4. In the demo, what happened with df.write.saveAsTable on 200 million rows?

Writing does not move rows to the driver.

Wrap up

Key takeaways

  • First ask: driver or executor?
  • Driver OOM: collect(), toPandas(), big broadcasts, many notebooks. Keep data distributed; bigger driver if needed.
  • Executor OOM: skew, oversized broadcasts, huge values. Fix skew, smaller partitions, more memory per worker.
  • Spill is the warning; OOM is the failure.
