Data skew

A stage with 200 tasks is only as fast as its slowest task. When one key holds far more rows than the others, one task gets stuck with most of the work while the rest sit idle. That is data skew.

The idea

One task does most of the work

After a shuffle, all rows with the same key go to the same partition. If one key is huge, its partition is huge too. That uneven spread is data skew. In the bakery example, the flagship store sells ten times more than any other, so the task for its partition takes ten times longer.

How to spot it in the Spark UI: open the slow stage and read its Summary Metrics. Compare the Max task duration with the 75th percentile. The Databricks guide says that if Max is 50% or more above the 75th percentile, the stage may be skewed. You can also sort the task list by duration and see one or two tasks far above the rest.

First ask where the skew is, because the fix depends on it:

  • In a join: AQE can fix it for you automatically.
  • In a groupBy aggregation: AQE's skew handling does not apply. It only works on joins. You fix this one yourself, usually with salting.

Usual fixes:

  • AQE skew join handling, on by default. During a join it splits a partition that is much bigger than the others into smaller pieces. Joins only.
  • Salting: add a random number to the hot key so its rows spread over several partitions, then combine the results. For a join, copy the small side once per salt value. For a groupBy, aggregate in two stages: first by key and salt, then by key alone.
  • Remove rows that cannot match anyway, such as NULL join keys in an inner join.
  • If the skew comes from how the table is laid out, liquid clustering can help. For skewed output files, the REBALANCE hint can help.
Everyday analogy

Checkout lanes at the bakery. Five lanes, but one customer has a catering order for 300 rolls. Four cashiers finish in two minutes and wait; one takes twenty. The shop closes when the last lane finishes. Opening extra lanes just for that order (splitting it) is what AQE and salting do.

How it works

The stage waits for the longest task

Five executors finish early and sit idle. The stage takes as long as task 6.

Code

Salting a hot key

from pyspark.sql import functions as F

SALT = 8   # how many pieces to split each key into

sales  = spark.read.table("bakery.silver.sales")
stores = spark.read.table("bakery.silver.stores")

# 1. Give every sales row a random salt from 0 to 7
salted_sales = sales.withColumn("salt", (F.rand() * SALT).cast("int"))

# 2. Copy each store row 8 times, once per salt value
salted_stores = stores.withColumn("salt", F.explode(F.sequence(F.lit(0), F.lit(SALT - 1))))

# 3. Join on the key AND the salt, so store 1's rows spread over 8 partitions
joined = salted_sales.join(salted_stores, ["store_id", "salt"]).drop("salt")
# Skew in a groupBy: AQE will not split it, so salt and aggregate in two stages
partial = (sales
    .withColumn("salt", (F.rand() * SALT).cast("int"))
    .groupBy("store_id", "salt")                       # stage 1: store 1 is split 8 ways
    .agg(F.sum("amount").alias("part_amount")))

totals = (partial
    .groupBy("store_id")                               # stage 2: at most 8 small rows per store
    .agg(F.sum("part_amount").alias("amount")))
-- Check how uneven the keys are before you tune anything
SELECT store_id, COUNT(*) AS rows
FROM bakery.silver.sales
GROUP BY store_id
ORDER BY rows DESC
LIMIT 10;

AQE skew join is controlled by spark.sql.adaptive.skewJoin.enabled (default true). A partition counts as skewed when it is more than 5 times the median partition size and larger than 256 MB. It works for shuffle joins, not broadcast joins, and not for groupBy aggregations. Older skew hints are retired. For simple sums, Spark often adds up rows before the shuffle, which softens skew; confirm in the Spark UI that the stage really is skewed before you salt. Verify current defaults on the AQE page.

Don't confuse these

Skew traps

Max vs 75th percentile

Compare the slowest task with the 75th percentile, not with the average.

Skew vs slow stage

If every task is slow, it is not skew. Look at I/O, spill or the code.

AQE is for joins

Its skew handling splits partitions in shuffle joins only. A skewed groupBy stays skewed until you salt it.

More machines

Do not fix skew; they only help when work is spread evenly.

Check yourself

Quiz

1. A stage's 75th percentile task time is 20 seconds and its Max is 4 minutes. What does that suggest?

Max is far more than 50% above the 75th percentile.

2. Why does adding executors not fix skew?

One task runs on one core, however big the cluster.

3. What does salting do?

The join then uses the key plus the salt.

4. In the demo, with the flagship at 60%, what did AQE skew join do?

The partition was over 5 times the median and over 256 MB, so AQE split it.

5. A nightly groupBy("store_id") has one task running 20 minutes while the rest finish in seconds. AQE is on. What fixes it?

AQE's skew handling only covers joins. A skewed aggregation needs salting in two stages.

Wrap up

Key takeaways

  • Skew: one key has far more rows, so one task runs far longer.
  • Spot it: Max task duration 50% or more above the 75th percentile.
  • Skew in a join: AQE skew join (default on) usually fixes it. Skew in a groupBy: AQE does not help; salt and aggregate in two stages.
  • Other fixes: filtering useless keys, broadcasting a small side.
  • More machines or more partitions do not fix skew.
