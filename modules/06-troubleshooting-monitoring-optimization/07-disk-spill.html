Disk spill

When a task's data does not fit in memory, Spark does not give up. It writes the overflow to local disk and reads it back later. The job still finishes, just much more slowly. That overflow is called spill.

06-05 Shuffle: why moving data is slow
The idea

Not enough room, so use the floor

Shuffles, joins, sorts and aggregations need working memory on each executor. If one task's partition is bigger than the memory it can use, Spark writes part of it to the executor's local disk, then reads it back. That is spill. Disk is far slower than memory, so a spilling stage can take many times longer.

How to spot it in the Spark UI: open the stage. If it spilled, the stage details show two numbers:

  • Shuffle spill (memory): how big the spilled data was while it sat in memory.
  • Shuffle spill (disk): how big it was once written to disk (smaller, because it is stored compactly).

If neither appears, the stage did not spill. Spill is often a warning sign: push the same stage harder and it can become an out-of-memory error.

Fixes from the Databricks guide: let Spark pick the number of shuffle partitions (spark.sql.shuffle.partitions = auto), carry fewer rows and columns into the stage (especially big strings and arrays), give executors more memory (larger instances, or fewer but larger workers), and for streaming, read less per batch. If the cause is one huge key, fix the skew first.

Everyday analogy

Icing cakes on a small table. If the cakes fit on the table, the baker works fast. If there are too many, the baker stacks some on the floor and keeps bending down to fetch them. The work gets done, slowly. A bigger table (more memory) or smaller batches (more partitions) fixes it.

How it works

Memory fills, the rest goes to disk

Every byte that spills is written and read again, on top of the normal work.

Code

Reducing spill

# Let AQE choose the number of shuffle partitions from the data size
spark.conf.set("spark.sql.shuffle.partitions", "auto")

sales = spark.read.table("bakery.silver.sales")

# Carry only what the aggregation needs: drop the long free-text column early
daily = (sales.select("store_id", "sale_date", "amount")
              .groupBy("store_id", "sale_date")
              .sum("amount"))

daily.write.mode("overwrite").saveAsTable("bakery.gold.daily_store_sales")
-- Same idea in SQL: name the columns instead of SELECT *
CREATE OR REPLACE TABLE bakery.gold.daily_store_sales AS
SELECT store_id, sale_date, SUM(amount) AS revenue
FROM bakery.silver.sales
GROUP BY store_id, sale_date;

On a SQL warehouse, the query profile can flag spill as a performance insight. The suggested fix there is a bigger warehouse size, or reading fewer rows and columns.

What if I change this?

Changes and their effect on spill

ChangeEffect
More shuffle partitionsEach task gets less data, so it is more likely to fit in memory. Too many gives lots of tiny tasks.
spark.sql.shuffle.partitions = autoSpark sizes the partitions from the data.
Larger instances (more memory per core)Each task has more room, so less spills.
Select fewer columnsEvery row is smaller, so more rows fit.
Data grows tenfold, settings unchangedPartitions grow tenfold and start spilling.
One skewed keyOne task spills heavily while others do not. Fix the skew.

Don't confuse these

Spill traps

Spill is not failure

The job finishes. It is a performance problem.

Memory vs disk numbers

Spill (memory) is the in-memory size; spill (disk) is the smaller on-disk size of the same data.

No numbers, no spill

If the spill fields are missing, the stage did not spill.

More executors

Adding machines does not shrink a single task's partition. More partitions or more memory per core does.

Check yourself

Quiz

1. What is disk spill?

The job keeps going but spends time on extra disk writes and reads.

2. Where do you see spill in the Spark UI?

If those fields are not shown, the stage did not spill.

3. Which change most directly reduces spill?

Smaller partitions and narrower rows fit in memory more easily.

4. In the demo, with 400 GB and 200 partitions at 2 GB per task, what happened?

2 GB per partition is more than the roughly 1 GB free per task in the model.

Wrap up

Key takeaways

  • Spill happens when a task's data does not fit in working memory; it slows the stage but does not fail it.
  • See it as Shuffle spill (memory) and Shuffle spill (disk) in the stage details.
  • Fix with auto or more shuffle partitions, fewer rows and columns, or more memory per core.
