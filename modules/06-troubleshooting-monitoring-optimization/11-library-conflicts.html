Library conflicts

"It worked yesterday" is often a library problem: two versions of the same package, installed in two places, and the wrong one wins. This lesson explains where libraries come from on Databricks and which one Python actually loads.

The idea

Same package, several places, one winner

A library is a package of code your notebook imports, such as pandas. On Databricks a Python library can come from three main places:

  • Databricks Runtime: every runtime version ships with many libraries already installed. Each runtime's release notes list the exact versions.
  • Compute-scoped libraries: installed on a cluster (from PyPI, Maven, a volume, a requirements.txt file and so on). Every notebook on that cluster sees them.
  • Notebook-scoped libraries: installed with %pip install inside one notebook. Only that notebook session sees them, and they must be installed again in each new session.

When the same package is in several places, Python uses the one highest in this order: notebook-scoped, then compute-scoped, then the runtime's own copy. (Files in the current Git folder come even before notebook-scoped libraries.)

Two more rules cause most surprises:

  • A package that was already imported stays loaded. After installing a new version, restart Python with dbutils.library.restartPython(), or you keep using the old one.
  • A newly installed cluster library is only seen by notebooks after they start a new session.

A conflict happens when two packages need different versions of the same dependency, or when your version breaks something the runtime relies on. The fix is nearly always: pin exact versions, install in one place, restart Python, and read the runtime release notes.

Everyday analogy

Recipe cards in the bakery. There is the head office's recipe book (the runtime), a recipe pinned on the kitchen wall (compute-scoped) and a card in a baker's own pocket (notebook-scoped). If they disagree, the baker follows the pocket card. And if the baker already started mixing from the old card, swapping cards mid-batch does nothing until they start a fresh batch (restart Python).

How it works

Which copy wins

Python takes the first copy it finds, starting from the top.

Which pandas did you get?

The runtime in this demo ships pandas 1.5.3 (an example version; check the release notes for yours). Install other versions in different places, import pandas, and try installing without restarting Python. bakery_utils is a made-up package that needs pandas below 2.

Code

Installing safely in a notebook

# Cell 1: install first, with exact versions (put this at the top of the notebook)
%pip install pandas==2.2.2 openpyxl==3.1.5

# Cell 2: restart Python so the new versions are the ones imported
dbutils.library.restartPython()

# Cell 3: check what you actually got
import pandas, sys
print(pandas.__version__, sys.version)
# requirements.txt kept in a volume, installed the same way
%pip install -r /Volumes/bakery/ops/libs/requirements.txt

Install libraries before any code that imports them, because restarting Python clears your variables. You cannot uninstall a runtime library with %pip; you can only install a different version on top. JAR libraries cannot be notebook-scoped. On serverless notebooks, add dependencies in the Environment side panel, and never install PySpark there.

Don't confuse these

Library traps

Installed vs loaded

A new version on disk does nothing until Python restarts.

%pip wins

Notebook-scoped beats compute-scoped, which beats the runtime.

Restart clears state

restartPython() wipes your variables. Install first, then run the rest.

Pin versions

Unpinned installs drift over time and cause "worked yesterday" bugs.

Check yourself

Quiz

1. The cluster has pandas 2.0.3 installed and your notebook ran %pip install pandas==2.2.2 then restarted Python. Which version does it use?

Notebook-scoped libraries come first.

2. Why call dbutils.library.restartPython() after %pip install?

It restarts only this notebook's Python process.

3. Where do you find which libraries a Databricks Runtime version ships with?

Each release notes page lists the preinstalled library versions.

4. In the demo, you imported pandas, then installed 2.2.2 with %pip and imported again without restarting. What loaded?

Already imported modules stay loaded until Python restarts.

Wrap up

Key takeaways

  • Python libraries come from the runtime, the cluster, or %pip; %pip wins, then cluster, then runtime.
  • Restart Python after installing; new cluster libraries need a new session.
  • Pin versions and check runtime release notes before upgrading.
  • Use notebook-scoped installs when notebooks need different versions.
