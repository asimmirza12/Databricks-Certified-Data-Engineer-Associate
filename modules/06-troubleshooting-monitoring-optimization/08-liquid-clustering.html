Liquid clustering

A query that asks for one store's sales should not have to open every file in the table. Liquid clustering keeps rows with similar values together, so Spark can skip the files it does not need.

The idea

Keep similar rows in the same files

A Delta table is stored as many data files. For each file, Delta records the smallest and largest value of its columns. When a query filters on a column, Spark checks those ranges and skips files that cannot contain a match. This is called data skipping. It only works well if each file covers a narrow range.

Liquid clustering arranges the rows by one or more clustering keys, so each file holds a narrow slice of key values. Queries that filter on those keys read far fewer files.

The main facts:

  • Turn it on with CLUSTER BY (columns) when you create a table, or ALTER TABLE ... CLUSTER BY on an existing unpartitioned table. Up to four keys.
  • Pick the columns your queries filter on most.
  • You can change the keys later without rewriting existing data. New clustering uses the new keys.
  • Clustering happens when OPTIMIZE runs (plain OPTIMIZE is incremental). OPTIMIZE ... FULL reclusters everything, useful after first enabling it or changing keys. Predictive optimization can run OPTIMIZE for you.
  • CLUSTER BY AUTO lets Databricks choose and change the keys from your query history, on Unity Catalog managed tables with predictive optimization.
  • It replaces partitioning and Z-ordering, and cannot be combined with them. Databricks recommends it for all new tables.
Everyday analogy

The bakery's receipt boxes. If receipts are thrown into boxes in random order, finding store 12's receipts means opening every box. If each box holds a narrow range of stores, with the range written on the lid, you open one or two boxes. Liquid clustering is the sorting; the labels on the lids are the file statistics. And you can re-sort by date later without emptying every box at once.

Code

Liquid clustering in SQL and Python

-- New table, clustered by the column most queries filter on
CREATE TABLE bakery.silver.sales (
  sale_id   BIGINT,
  store_id  INT,
  sale_date DATE,
  amount    DECIMAL(10,2)
) CLUSTER BY (store_id);

-- Change the keys later. Existing files are not rewritten now.
ALTER TABLE bakery.silver.sales CLUSTER BY (store_id, sale_date);

-- Cluster new and unclustered data (incremental)
OPTIMIZE bakery.silver.sales;

-- Recluster everything with the current keys (can take a long time on big tables)
OPTIMIZE bakery.silver.sales FULL;

-- Let Databricks choose keys (UC managed table + predictive optimization)
ALTER TABLE bakery.silver.sales CLUSTER BY AUTO;

-- Turn clustering off (no data is rewritten)
ALTER TABLE bakery.silver.sales CLUSTER BY NONE;
# Python: set clustering when creating or overwriting a table
(spark.read.table("bakery.bronze.sales_raw")
      .write.clusterBy("store_id")
      .mode("overwrite")
      .saveAsTable("bakery.silver.sales"))

Liquid clustering is generally available on Databricks Runtime 15.4 LTS and above, and OPTIMIZE FULL needs 16.0 or above. Check version details and allowed column types in the docs.

What if I change this?

Choices and their effects

ChangeEffect
Key = a column you filter onQueries on it skip most files.
Key = a column nobody filters onClustering work with no benefit.
Change keys with ALTER TABLEFast; old files keep their old layout until reclustered.
Run OPTIMIZE FULL after changing keysAll files follow the new keys; can take hours on a large table.
Never run OPTIMIZE (and no predictive optimization)Small appended files stay unclustered and queries read them all.
Try to add CLUSTER BY to a partitioned tableNot allowed: liquid clustering does not mix with partitioning or ZORDER.
Use more keys on a small tableFilters on a single key can get slower. Use only keys you need.

Don't confuse these

Clustering traps

ALTER does not rewrite

Changing keys is instant. Old files are only reclustered by OPTIMIZE FULL.

Not with partitions

Liquid clustering cannot be combined with partitioning or ZORDER.

Max four keys

And choose columns used in filters.

AUTO needs PO

CLUSTER BY AUTO relies on predictive optimization on a UC managed table.

Check yourself

Quiz

1. How does liquid clustering make filtered queries faster?

One folder per value is partitioning. Clustering narrows each file's range.

2. You run ALTER TABLE ... CLUSTER BY with new keys. What happens to existing files?

Changing keys is cheap; reclustering old data is a separate step.

3. Which table can use CLUSTER BY AUTO?

Automatic key selection is done by predictive optimization.

4. In the demo, you clustered by store_id, ran OPTIMIZE, then appended 4 files. How many files did the query read?

New small files cover every store until the next OPTIMIZE clusters them.

Wrap up

Key takeaways

  • Liquid clustering groups rows by up to four keys so queries skip files.
  • Set with CLUSTER BY; change keys without rewriting; recluster with OPTIMIZE or OPTIMIZE FULL.
  • CLUSTER BY AUTO picks keys for UC managed tables with predictive optimization.
  • It replaces partitioning and Z-order and does not mix with them.
