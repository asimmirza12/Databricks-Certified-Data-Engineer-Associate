Tracking run times and failure rates

One bad run is an incident. A job that fails one night in four, or gets a little slower every week, is a trend. This lesson turns run history into two health numbers you can watch.

The idea

Two numbers tell you if a job is healthy

The first number is how long runs take. Look at the typical run (the average or the median) and at the slow end, such as the 90th percentile (p90): the time that 9 out of 10 runs finish within. A rising p90 often warns you before the average moves.

The second number is the failure rate: failed runs divided by finished runs over a time window, such as the last 7 or 30 days. A job that fails now and then and succeeds on retry is called flaky. Its failure rate shows it even when today's run is green.

Where to get them:

  • The job's Runs tab. The matrix view shows each run's duration as bar height and its result as colour, so you can see a trend at a glance.
  • The Runs page under Jobs & Pipelines. It shows a graph of finished runs over the last 48 hours and a table of the most common error types.
  • The jobs system tables, for exact numbers across many jobs and longer periods.
Everyday analogy

The bakery's oven log. One burnt tray is bad luck. But if the log shows 4 burnt trays out of the last 20 and bake times creeping up, the oven needs a service. The log is the run history; "4 out of 20" is the failure rate; creeping bake times are the rising p90.

How it works

From runs to numbers

Long runs are stored as several hourly slices. Add them up per run first, then count and measure.

Code

Failure rate and p90 per job in SQL

-- Health of every job over the last 30 days
WITH runs AS (
  SELECT job_id,
         run_id,
         SUM(timestampdiff(SECOND, period_start_time, period_end_time)) AS seconds,
         MAX_BY(result_state, period_end_time) AS result_state   -- final state is on the last slice
  FROM system.lakeflow.job_run_timeline
  WHERE period_start_time >= current_date() - INTERVAL 30 DAYS
  GROUP BY job_id, run_id
)
SELECT job_id,
       COUNT(*)                                                  AS finished_runs,
       COUNT_IF(result_state IN ('FAILED', 'ERROR', 'TIMED_OUT')) AS bad_runs,
       round(100 * COUNT_IF(result_state IN ('FAILED', 'ERROR', 'TIMED_OUT')) / COUNT(*), 1)
                                                                 AS failure_rate_pct,
       round(avg(seconds) / 60, 1)                               AS avg_minutes,
       round(percentile(seconds, 0.9) / 60, 1)                   AS p90_minutes
FROM runs
WHERE result_state IS NOT NULL            -- skip runs still in progress
GROUP BY job_id
ORDER BY failure_rate_pct DESC;

Join to system.lakeflow.jobs on job_id to show job names. For multi-task jobs the docs warn that the run_duration_seconds column can be 0, so compute duration from the start and end times as above. Verify the column details on the system table page.

What if I change this?

Choices and their effects

ChangeEffect
Window from 30 days to 7Shows recent problems quickly, but a few runs swing the numbers a lot.
Count TIMED_OUT as a failureYour rate includes runs that were stopped for taking too long, which is usually what you want.
Watch p90 as well as the averageYou see the slow tail growing before the typical run changes.
Read run_duration_seconds for a multi-task jobYou may get zeros. Use the start and end times instead.
Do not add hourly slices togetherLong runs look short and are counted several times.
Rely on job-level failure notifications onlyA task that fails and then passes on retry does not send a job failure notification. Add task notifications if you need to know.

Don't confuse these

Measurement traps

Canceled vs CANCELLED

The UI says Canceled; the jobs system tables store CANCELLED.

Average vs p90

The average shows the typical run; p90 shows the slow end.

Unfinished runs

Runs still in progress have no result yet. Leave them out of the rate.

Green is not healthy

A job can be green today and still have a high failure rate.

Check yourself

Quiz

1. A job had 20 finished runs last month and 5 failed. What is its failure rate?

5 divided by 20 is 0.25, which is 25%.

2. Why add up the rows per run_id before measuring durations?

Without adding them, a 3 hour run looks like three 1 hour runs.

3. The average duration is steady but p90 doubled. What does that mean?

p90 watches the slow end, so it moves when a few runs get much slower.

4. In the demo, what happened when you used the run_duration_seconds column?

For multi-task jobs compute duration from start and end times.

Wrap up

Key takeaways

  • Watch two numbers: duration (typical and p90) and failure rate over a window.
  • The Runs tab and Runs page give quick visuals; system tables give exact numbers.
  • Add hourly slices per run, and leave unfinished runs out.
  • A green run today does not mean the job is healthy.
