Job statuses and finding upstream blockers

When a job goes red, many tasks can look broken at once. Usually only one of them actually failed; the rest are just waiting on it. This lesson shows how to read the statuses and walk back to the real cause.

The idea

One real failure, many knock-on statuses

A job's tasks form a task graph. A task normally waits until the tasks before it succeed. If one task fails, the tasks after it never start. They get the status Upstream failed, which means "I did not run because something before me failed".

Statuses you will see for a whole run:

  • Queued, Pending, Running, Canceling: the run is not finished yet.
  • Succeeded: every task succeeded.
  • Succeeded with failures: some tasks failed, but every leaf task (a task with nothing after it) succeeded.
  • Failed: at least one leaf task failed (or did not run because of an upstream failure).
  • Timed Out: the run passed its timeout. Canceled: someone stopped it. Skipped: the run did not start, for example because the maximum number of concurrent runs was reached.

Extra task statuses come from each task's Run if setting. Excluded means the task's condition was not met, so it was left out on purpose (for example an alert task set to run only if something failed). Upstream canceled means a task before it was canceled.

Everyday analogy

The bakery delivery van. The flour delivery is late (the real failure). So the dough is not made, so the bread is not baked, so the shop shelves stay empty. Three things look wrong, but only one actually broke. You fix the flour, not the shelves.

How it works

Walk back along the graph

Start at the red end of the graph and step back until you reach the first task that actually Failed. Its error is the one to read.

Try it

Break a task, then find it

Choose which task fails, run the job, then use "Find the blocker". notify_team is set to Run if "At least one failed", so it only runs when something went wrong. Try switching refresh_dashboard to "All done" to see Succeeded with failures.

Find failed task runs in SQL

In the UI, open the failed run and use the Graph view. To search many runs at once, query the task run system table.

-- Which tasks of the bakery_sales job failed in the last 7 days, and how?
SELECT run_id,
       task_key,
       result_state,          -- set only on the last row of each task run
       termination_code,
       period_end_time
FROM system.lakeflow.job_task_run_timeline
WHERE job_id = '123456789'                       -- made-up id
  AND period_start_time >= current_date() - INTERVAL 7 DAYS
  AND result_state IS NOT NULL
  AND result_state <> 'SUCCEEDED'
ORDER BY period_end_time DESC;
# The same job, defined in a bundle: an alert task that runs only when something fails
tasks:
  - task_key: build_gold
    depends_on: [{ task_key: clean_sales }]
  - task_key: notify_team
    depends_on: [{ task_key: build_gold }]
    run_if: AT_LEAST_ONE_FAILED

The system tables spell it CANCELLED (two Ls) while the UI says Canceled. Check the value names on the system table page.

What if I change this?

Settings and their effects on statuses

ChangeEffect
Run if "All succeeded" (default)The task runs only if everything before it succeeded; otherwise it shows Upstream failed.
Run if "All done"The task runs once everything before it finished, whatever the result. Useful for cleanup.
Run if "At least one failed"The task runs only when something before it failed; otherwise it is Excluded.
A middle task fails but every leaf succeedsThe run shows Succeeded with failures.
A leaf task fails or is upstream failedThe run shows Failed.
Repair runRe-runs failed, canceled and skipped tasks and the tasks after them. Tasks that already succeeded are kept.

Don't confuse these

Status traps

Failed vs Upstream failed

Only Failed tasks have an error worth reading. Upstream failed tasks never ran.

Excluded is not a failure

It counts as success for other tasks' Run if checks.

Leaf tasks decide

The run result comes from the tasks at the end of the graph.

Repair needs 2+ tasks

For a single-task job, just run it again.

Check yourself

Quiz

1. A task shows Upstream failed. What should you do first?

An Upstream failed task never ran, so it has no error of its own.

2. A middle task failed, but both leaf tasks succeeded. What is the run status?

The run result follows the leaf tasks. Some tasks failed, so it is not a plain Succeeded.

3. What does a repair run re-run?

Tasks that succeeded are kept, which saves time and compute.

4. In the demo, with nothing failing, what status did notify_team get?

Its condition "At least one failed" was not met, so it was left out on purpose.

Wrap up

Key takeaways

  • Upstream failed means "did not run because of an earlier task". Find the task that actually Failed.
  • The run result follows the leaf tasks: Failed, Succeeded, or Succeeded with failures.
  • Excluded is intentional, set by a task's Run if condition.
  • Repair run re-runs only what did not succeed, plus what comes after it.
