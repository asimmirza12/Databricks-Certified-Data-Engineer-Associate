Shuffle: why moving data is slow

Most slow Spark stages have one thing in common: data being copied from machine to machine. This lesson shows when that happens, how to see it in the Spark UI, and how to do less of it.

The idea

Rows with the same key have to meet

Spark spreads a table over many executors, one partition each. Some steps only need the rows already on that executor. They are narrow transformations: filter, select, adding a column. They are cheap.

Other steps need all rows with the same key in one place. To add up sales per store, every row for store 7 must end up on the same executor. These are wide transformations: joins, aggregations such as groupBy and distinct, window functions, and repartition. To do them Spark runs a shuffle: each executor writes its rows out sorted by destination, and every executor fetches the rows meant for it.

A shuffle costs disk writes, network transfer, and turning rows into bytes and back. It also needs memory, and if there is not enough, data spills to disk (lesson 06-07). In a query plan a shuffle appears as an Exchange.

Everyday analogy

Sorting the post at three bakery branches. Each branch gets mixed orders for every store. To pack orders per store, every branch has to send its envelopes to the branch that handles that store. Checking an envelope's stamp at the branch where it already is (narrow) is quick. Driving envelopes between branches (shuffle) is what takes the time.

How it works

Write, send, read

In the stage details, the sending side shows Shuffle Write and the receiving side shows Shuffle Read.

Code

Doing the same work with less shuffle

from pyspark.sql import functions as F

sales  = spark.read.table("bakery.silver.sales")
stores = spark.read.table("bakery.silver.stores")      # small: a few hundred rows

# Shuffle-heavy: joins every column of every row, then filters
slow = (sales.join(stores, "store_id")
             .filter(F.col("sale_date") >= "2026-11-01"))

# Lighter: filter and pick columns first, and broadcast the small table
fast = (sales.filter(F.col("sale_date") >= "2026-11-01")
             .select("store_id", "amount")
             .join(F.broadcast(stores.select("store_id", "region")), "store_id"))

fast.explain()    # look for BroadcastHashJoin instead of an Exchange on the big side

Spark's own default limit for an automatic broadcast is 10 MB (spark.sql.autoBroadcastJoinThreshold). On Databricks, AQE can also switch a join to broadcast at run time using spark.databricks.adaptive.autoBroadcastJoinThreshold, 30 MB by default. Verify current values in the docs. Lesson 03-13 covers the setting in detail.

What if I change this?

Changes and their effect on shuffle

ChangeEffect
Filter before a join or groupByFewer rows are shuffled.
Select only needed columns firstEach shuffled row is smaller.
Broadcast a small tableThe small table is copied to every executor; the big table does not move.
Broadcast a big tableEvery executor needs memory for all of it; it can run out of memory.
Add an unneeded repartition()An extra full shuffle for nothing.
Two groupBys on different keysTwo shuffles. Group once on what you need if you can.
Compare

Narrow vs wide

Narrow (no shuffle)

filter, where, select, withColumn, reading files, union. Each partition is handled where it is.

Wide (shuffle)

join (not broadcast), groupBy and other aggregations, distinct, window functions, repartition. Rows move to meet their key.

Join typeWhat movesBest when
Shuffle (sort-merge) joinBoth tables are shuffled by the keyBoth tables are large
Broadcast joinOnly the small table, copied to every executorOne table is small enough to fit in memory

Don't confuse these

Shuffle traps

Shuffle is not a bug

Joins and aggregations need it. The goal is to shuffle less data, not none.

Write vs Read

Shuffle Write is on the sending stage; Shuffle Read on the receiving one.

Exchange = shuffle

In a query plan, look for Exchange.

Broadcast has a limit

Only small tables should be broadcast.

Check yourself

Quiz

1. Which of these causes a shuffle?

Grouping needs all rows with the same key together.

2. What does a broadcast join avoid?

The small table is copied to each executor, so the big table stays where it is.

3. In a query plan, which word marks a shuffle?

Exchange is where rows are redistributed between partitions.

4. In the demo, what happened to the join with a 900 MB stores table?

900 MB is above the broadcast limit, so Spark shuffles both sides.

Wrap up

Key takeaways

  • Wide transformations (join, groupBy, distinct, window, repartition) shuffle; narrow ones do not.
  • Shuffle costs disk, network and memory. See it as Shuffle Read and Write, or Exchange in the plan.
  • Filter and select early, and broadcast small tables, to shuffle less.
