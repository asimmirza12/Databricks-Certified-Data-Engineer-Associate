Cluster startup failures

Sometimes a job fails before any of your code runs, because the compute never started. The cause is almost always written down. This lesson shows where to read it and what the common causes are.

The idea

Startup is a checklist; the log says which step broke

Starting classic compute runs through a series of steps: check the settings against any compute policy, ask the cloud for machines, give them network addresses, connect them to the Databricks control plane, run any init scripts, then start Spark. If any step fails, the compute stops with a termination reason.

Where to look:

  • The event log, a tab on the compute's details page. It lists every start, resize, init script and termination, with details. Events are kept for 60 days.
  • The termination reason, shown on the compute and in the event log, with a code such as INIT_SCRIPT_FAILURE or CLOUD_PROVIDER_LAUNCH_FAILURE.
  • Init script logs, if a script failed: each script writes its own stdout and stderr files.
  • Driver logs, a tab on the compute page, for problems after Spark started.

Common causes: the cloud has no spare machines of that type, the account hit a cloud quota, the subnet has run out of free IP addresses, a network rule blocks the nodes from reaching the control plane, an init script exits with an error, or a permission is missing. Serverless compute avoids most of these, because Databricks runs the machines.

Everyday analogy

Opening the bakery in the morning. Unlock the door, switch on the power, light the ovens, start the mixers. If the ovens will not light, you do not blame the bread recipe. You check the opening checklist to see which step failed. The event log is that checklist, filled in.

Reading the reason from the CLI

# Show the compute's state and termination reason (the JSON includes termination_reason)
databricks clusters get 0123-456789-abcdefgh

# List recent events for the compute, newest first
databricks clusters events 0123-456789-abcdefgh --order DESC --limit 20
#!/bin/bash
# init script kept in a Unity Catalog volume, e.g. /Volumes/bakery/ops/scripts/setup.sh
# Fail loudly and early so the error is easy to find in the init script logs
set -euo pipefail
echo "installing bakery fonts"
apt-get install -y fonts-dejavu-core=2.37-2   # pin versions

The cluster ID above is made up. Check the CLI's exact flags with databricks clusters events --help. Init scripts stored on DBFS are end of life; keep them in volumes or workspace files. Databricks recommends avoiding init scripts where a policy or notebook-scoped library can do the job.

Startup failures in practice

ScenarioWhat happensFix
Nightly job fails with no notebook outputThe job compute never startedOpen the run, then the compute's event log and termination reason
Startup broke after someone edited an init scriptThe script now exits with an errorRead its stderr log; fix and restart
Big clusters fail at 9am every MondayMany jobs start at once and the subnet runs out of IPsStagger schedules or enlarge the subnet
One instance type keeps failing in one regionThe cloud has no spare capacityZone auto, flexible node types, or another type
Don't confuse these

Startup traps

Event log vs driver log

Startup problems are in the event log. Driver logs cover what happened after Spark started.

Not your code

If compute never started, your notebook did not run. Do not debug the notebook first.

Policy edits

Changing a policy does not update existing compute until compliance is enforced or it is edited.

Serverless

No init scripts or policies there, and far fewer startup problems.

Check yourself

Quiz

1. Classic compute failed to start. Where should you look first?

If Spark never started there is no notebook output or Spark UI to read.

2. The termination reason is INIT_SCRIPT_FAILURE. What next?

Each init script writes its own stdout and stderr files.

3. Which setting can help when one zone has no capacity at startup?

Auto can retry in another zone on a capacity error at startup.

4. In the demo, you broke both the subnet IPs and the init script. Which reason was shown?

Startup stops at the first failing step, so later steps never run.

Wrap up

Key takeaways

  • Startup is a series of steps; the first failure sets the termination reason.
  • Read the event log (60 days) and the termination reason; read init script logs when a script failed.
  • Common causes: capacity, quota, subnet IPs, network rules, init scripts, permissions.
  • Serverless avoids most of these.
