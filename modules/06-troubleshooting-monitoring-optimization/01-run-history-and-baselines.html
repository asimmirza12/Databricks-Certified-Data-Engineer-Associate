Run history: comparing a run with its normal

"This run took 40 minutes" means nothing on its own. It only matters when you compare it with how long the same job usually takes. This lesson shows where that history lives and how to use it.

The idea

Slow is only slow compared with normal

Every time a job runs, Lakeflow Jobs keeps a record of that run: when it started, how long it took and how it ended. Put those records side by side and you get the job's run history.

From the history you can work out a baseline: the duration the job normally takes, for example the middle value (median) of its last ten good runs. A new run is "slow" when it is clearly longer than that baseline, not when it passes some number you picked from the air.

Databricks shows the history in three places:

  • The job's Runs tab. It has a matrix view, where each column is one run and a bar shows its duration, and a list view. It shows about 60 days of runs.
  • A duration threshold on the job. You set an expected time, and Databricks raises a duration warning when a run goes over it.
  • The system table system.lakeflow.job_run_timeline. It keeps a much longer history that you can query with SQL.
Everyday analogy

Your morning commute. If the drive to the bakery normally takes 20 minutes, a 35 minute drive is worth asking about. If it normally takes 45, 35 is a good day. The history of past drives is the run history; "about 20 minutes" is the baseline; the phone alert that says "heavier traffic than usual" is the duration warning.

How it works

Each run is compared with the runs before it

The newest run is judged against the middle of the recent runs, not against a fixed guess.

Compare each run with its recent normal in SQL

The Runs tab is good for a quick look. For a longer view, query the jobs system table. A run that lasts more than an hour is stored as several hourly rows, so add the slices up per run first.

-- One row per finished run of the bakery_sales job, with its "normal" next to it
WITH runs AS (
  SELECT run_id,
         MIN(period_start_time) AS started,
         SUM(timestampdiff(SECOND, period_start_time, period_end_time)) / 60 AS minutes,
         MAX_BY(result_state, period_end_time) AS result_state   -- only the last slice has it
  FROM system.lakeflow.job_run_timeline
  WHERE job_id = '123456789'                                    -- made-up id
    AND period_start_time >= current_date() - INTERVAL 30 DAYS
  GROUP BY run_id
)
SELECT run_id,
       started,
       round(minutes, 1) AS minutes,
       round(median(minutes) OVER (ORDER BY started
             ROWS BETWEEN 10 PRECEDING AND 1 PRECEDING), 1) AS normal_minutes
FROM runs
WHERE result_state = 'SUCCEEDED'
ORDER BY started DESC;

Compare minutes with normal_minutes. A ratio well above 1 (say 1.5 or more) is worth a look. Check the column names on the jobs system table page before you rely on them.

What if I change this?

Choices and their effects

ChangeEffect
Set a duration warningA run that passes the expected time raises a duration warning event, which can send a notification. The run keeps going.
Set a timeoutA run that passes the maximum time is stopped and ends as Timed Out.
Warning set too low (below the normal)Every run warns, so people learn to ignore it.
Warning set far too highA run can double in length without anyone hearing about it.
Baseline from fewer runsReacts faster to a real change, but one odd run moves it more.
Use the average instead of the medianOne very long run drags the average up; the median barely moves.

Don't confuse these

Run history traps

Warning vs timeout

A warning only tells you. A timeout stops the run and marks it Timed Out.

Slow vs failed

A slow run can still succeed. Watch duration, not just colour.

Hourly slices

In the system table a long run is several rows. Add them per run before comparing.

60 days vs 395

The Runs tab covers recent runs. For long trends, use the system table.

Check yourself

Quiz

1. A job usually takes 20 minutes. Today it took 34 minutes and succeeded. What is the best reading?

Success does not mean healthy. 34 is about 1.7 times its normal.

2. What does a duration warning do when a run passes it?

Stopping the run is what a timeout does.

3. Why use the median of recent runs as the baseline?

The median is the middle value, so a single odd run does not drag it.

4. In the demo, what happened when you added a 70 minute run with the timeout at 60?

Timed out runs are not good runs, so they do not join the baseline either.

Wrap up

Key takeaways

  • Judge a run against the job's own normal, worked out from recent good runs.
  • The Runs tab matrix view shows duration as bar height for each run and task.
  • A duration warning tells you; a timeout stops the run.
  • For long trends, query system.lakeflow.job_run_timeline, adding hourly slices per run.
