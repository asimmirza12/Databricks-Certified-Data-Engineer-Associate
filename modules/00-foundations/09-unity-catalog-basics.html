Unity Catalog basics

Thousands of tables, hundreds of people. Something has to keep track of what exists and who is allowed to touch it. On Databricks that something is Unity Catalog.

The idea

One index of all your data, with a guard at the door

Unity Catalog is the part of Databricks that does two jobs:

  • It is the index. It knows the name of every table and file area, where its data sits in cloud storage, and who owns it.
  • It is the guard. Every time someone tries to read or change data, Unity Catalog checks whether they are allowed.

Looking after data in this way (who may see it, who changed it, where it came from) is called governance. A table that Unity Catalog looks after is often called a "Unity Catalog-governed table".

Data is organised in levels, like an address. Every table has a three-part name: catalog.schema.table. You have seen one already: bakery.silver.orders.

Everyday analogy

A public library. The library service for the whole city is the metastore. Each building is a catalog. Each room in a building is a schema. Each book is a table. To read a book you need to be let into the building, then into the room, then be allowed to open that book. The librarian at the desk, who checks your card at every step, is Unity Catalog.

How it works

Four levels, three of them in the name

The metastore is not written in the name. Your workspace is attached to exactly one, so it is assumed.

Metastore

The metastore is the top-level container. An organisation normally has one per cloud region, shared by all workspaces there.

Catalog

A catalog is the first level you name. Teams often make one per business area or per environment, such as bakery or dev.

Schema

A schema groups related objects inside a catalog. It is also called a database. This is the "container" meaning of the word from lesson 00-02.

Table, view, volume

The things you actually use. A view is a saved query that looks like a table. A volume holds files that are not tables, such as the CSV files waiting to be loaded.

Permissions

Permission to do something is called a privilege. You give one with the SQL command GRANT and take it away with REVOKE. To read a table, a person needs three privileges, one per level:

  • USE CATALOG on the catalog: permission to enter the building.
  • USE SCHEMA on the schema: permission to enter the room.
  • SELECT on the table: permission to read the book.

Privileges flow downwards. If you grant SELECT on a whole schema, it covers every table in it, including tables created later.

Try it

Be the librarian

The analysts group wants to read bakery.gold.sales_by_shop. Grant privileges one at a time and run the query after each. Then try granting SELECT at a higher level.

Grants held by analysts

The three checks for this query

Code

Names and grants in SQL

-- Make a schema inside the catalog, then a table inside the schema.
CREATE SCHEMA IF NOT EXISTS bakery.gold;

CREATE TABLE bakery.gold.sales_by_shop (shop STRING, total_sales DECIMAL(12,2));

-- The full three-part name always works.
SELECT * FROM bakery.gold.sales_by_shop;

-- Or set a starting point once and use short names after that.
USE CATALOG bakery;
USE SCHEMA gold;
SELECT * FROM sales_by_shop;

-- Let the analysts group read one table. Names with special characters go in backticks.
GRANT USE CATALOG ON CATALOG bakery TO `analysts`;
GRANT USE SCHEMA  ON SCHEMA  bakery.gold TO `analysts`;
GRANT SELECT      ON TABLE   bakery.gold.sales_by_shop TO `analysts`;

-- See who can do what, and take a privilege back.
SHOW GRANTS ON TABLE bakery.gold.sales_by_shop;
REVOKE SELECT ON TABLE bakery.gold.sales_by_shop FROM `analysts`;

Files in a volume also get a governed address, built from the same three names:

# /Volumes/<catalog>/<schema>/<volume>/<path inside the volume>
path = "/Volumes/bakery/landing/till_files/orders/2026/11/16/north.csv"
What if I change this?

Granting at different levels

ChangeEffect
Grant SELECT on the table, but forget USE SCHEMAThe query is refused. All three levels must be passed, like three doors in a row.
Grant SELECT on the schema instead of the tableEvery table and view in that schema becomes readable, including ones created in future.
Grant SELECT on the whole catalogReadable: every table in every schema of the catalog. Convenient, and easy to overdo.
Grant to one person instead of a groupIt works, but each joiner and leaver means more grants to change. Granting to groups is the normal practice.
Use a one-part name such as ordersDatabricks fills in the current catalog and schema. If those are not what you think, you read a different table or get "not found".

Who can be given access

User

One person, identified by their email address.

Group

A named set of users, such as analysts. The recommended target for grants.

Service principal

An identity for a program, not a person. Scheduled jobs run as one (Module 07).

Don't confuse these

Unity Catalog mix-ups

USE CATALOG vs USE CATALOG

As a command, USE CATALOG bakery; sets your current catalog. As a privilege, GRANT USE CATALOG lets someone enter it. Same words, different jobs.

Schema = database

On Databricks the two words mean the same container. And neither is the "column list" meaning of schema from lesson 00-02.

Metastore vs catalog

The metastore is the top container and never appears in a name. A catalog is the first part of the name. Unity Catalog is the whole system.

Volume vs table

A volume governs files. A table governs rows. A CSV file in a volume is not a table until you load it into one.

Check yourself

Quiz

1. In bakery.silver.orders, what is silver?

The order is always catalog, then schema, then the object. The metastore is not part of the name.

2. Which set of privileges lets a group read one table and nothing else?

SELECT alone is not enough without the two "use" privileges above it. SELECT on the catalog would open far more than one table.

3. In the demo, what happened when you granted SELECT on the schema bakery.gold?

Privileges flow down from a container to everything inside it. They do not flow sideways to another schema.

4. Where should raw CSV files that are waiting to be loaded be kept, so access to them is governed?

Volumes are the Unity Catalog object for files that are not tables.

Wrap up

Key takeaways

  • Unity Catalog is the index of all data and the guard that checks access.
  • Levels: metastore, catalog, schema, then tables, views and volumes.
  • Every table has a three-part name: catalog.schema.table.
  • Reading a table needs USE CATALOG, USE SCHEMA and SELECT.
  • Privileges flow downwards. Grant to groups, not to individuals.
