Delta Lake basics

The idea

Data files plus a diary of every change

Lesson 00-06 left us with a problem. Objects in cloud storage cannot be edited, only replaced. So how do you change one row in a table of a billion rows? And what do readers see if a job crashes halfway through writing?

Delta Lake is the answer. It is an open-source way of storing a table as two things in one folder:

  • Data files in Parquet format, holding the rows.
  • A transaction log: a small diary that records, in order, every change ever made. Each entry says which data files were added and which are no longer in use.

The log is the boss. A data file counts as part of the table only if the log says so. To read the table, Spark reads the log first to learn which files to open.

On Databricks, tables are Delta tables by default. You have been looking at Delta tables since lesson 00-01.

Everyday analogy

A club's membership book. Membership cards sit in a drawer (the data files). The book at the front desk (the log) lists who is a member right now. When someone leaves, nobody hunts for their card. The secretary writes "card 17 no longer valid" in the book. The old card stays in the drawer for a while, but the book is what counts. Because every line in the book is dated, you can also work out who was a member last Tuesday.

How it works

A write is two steps, and only the second one counts

If the job crashes after step 1 and before step 2, the new file is never mentioned in the log. Readers never see it.

Each log entry creates a new numbered version of the table, starting at 0. Because old files stay on disk for a while, you can ask for the table as it was at an earlier version. This is called time travel.

Old, unused files do not stay for ever. A clean-up command called VACUUM deletes files that the current version no longer uses and that are older than a retention period.

Code

Everyday Delta commands

-- A new table on Databricks is a Delta table unless you say otherwise.
CREATE TABLE bakery.silver.orders (order_id INT, shop STRING, price DECIMAL(10,2));

INSERT INTO bakery.silver.orders VALUES (101, 'North', 4.50);      -- version 1
UPDATE bakery.silver.orders SET price = 5.50 WHERE order_id = 101;  -- version 2
DELETE FROM bakery.silver.orders WHERE order_id = 101;             -- version 3

-- Read the diary: one line per version, with who did what and when.
DESCRIBE HISTORY bakery.silver.orders;

-- Time travel: read the table as it used to be.
SELECT * FROM bakery.silver.orders VERSION AS OF 2;
SELECT * FROM bakery.silver.orders TIMESTAMP AS OF '2026-11-15 09:00:00';

-- Undo a mistake: make an old version the current one again.
RESTORE TABLE bakery.silver.orders TO VERSION AS OF 2;

-- Clean up data files that are no longer used and are past the retention period.
VACUUM bakery.silver.orders;

The same time travel in Python:

old_orders = spark.read.option("versionAsOf", 2).table("bakery.silver.orders")
What if I change this?

History, clean-up and safety

ChangeEffect
Run VACUUMUnused data files older than the retention period are deleted for good. The default period is 7 days. Time travel to versions that needed those files stops working.
Never run VACUUMEvery old file is kept, and storage costs keep growing. On Databricks, a feature called predictive optimization can run this clean-up for you on managed tables (Module 06).
Want more than 7 days of time travelRaise the table property delta.deletedFileRetentionDuration. Log entries are kept for 30 days by default (delta.logRetentionDuration). The shorter of the two is your real limit, and keeping more costs more storage.
Insert a row whose columns do not match the tableThe write is refused. Delta checks every write against the table's schema. This is called schema enforcement.
Delete data files by hand in cloud storageThe log still points at them, and reads fail. Always change a Delta table through SQL or Spark, never through the storage browser.

ACID: four promises of a reliable table

The guarantees above have a collective name, ACID. A change that keeps all four promises is called a transaction.

Atomicity

A change happens completely or not at all. Never half.

Consistency

The table always obeys its rules, such as its schema, before and after every change.

Isolation

People working at the same time do not see each other's unfinished changes.

Durability

Once a change is confirmed, it stays, even if a machine fails a second later.

Don't confuse these

Delta mix-ups

DELETE vs VACUUM

DELETE removes rows from the current version. The files stay, so you can travel back. VACUUM removes old files from disk. After that, there is no going back.

Delta vs Parquet

Delta stores its data in Parquet files. The log is the extra part. Without the log it is only a folder of files.

Three "Delta" names

Delta Lake is the table format. Delta Live Tables is the old name of a pipeline product, now Lakeflow Spark Declarative Pipelines. Delta Sharing is a way to share data with other organisations.

Time travel vs backup

Time travel depends on old files that VACUUM removes. It is a short-term undo, not a long-term archive.

Check yourself

Quiz

1. What decides which data files are part of a Delta table right now?

Files the log does not list are ignored, even though they sit in the same folder.

2. In the demo, what did readers see after the write that crashed halfway?

The crashed write left a file on disk but no log entry. With no entry, the file is not part of the table.

3. With default settings, how far back should you rely on time travel?

Unused data files are kept for 7 days by default before VACUUM may delete them. The log is kept for 30 days, but the log alone cannot rebuild rows whose files are gone.

4. A colleague wiped a table with a bad DELETE ten minutes ago. What is the quickest safe fix?

RESTORE makes the earlier version current again. VACUUM would do the opposite and destroy the files you need.

Wrap up

Key takeaways

  • A Delta table is Parquet data files plus a transaction log.
  • The log decides which files count, so writes are all-or-nothing.
  • Every change makes a new version. Old versions can be read with time travel.
  • VACUUM deletes old files and, with them, old history. The default retention is 7 days.
  • Delta is the default table format on Databricks.
