Batch vs streaming

Every pipeline has to answer one question: do we process data in big piles now and then, or bit by bit as it arrives?

Before this
00-01 What is data engineering?
The idea

A pile now and then, or a steady trickle

Batch processing means collecting data for a while, then handling the whole pile in one go. For example: every night at 1 am, load all of yesterday's orders.

Streaming means handling each piece of data shortly after it arrives, all day long, without waiting for a pile to build up.

There is a useful middle way. Incremental processing runs now and then like batch, but each run handles only what is new since the last run. It never redoes old work.

The thing you are trading is latency: the delay between something happening and it showing up in your tables. Lower latency costs more money and more care.

Everyday analogy

Washing up. Batch is filling the dishwasher and running it once in the evening. It is efficient, but a plate used at breakfast stays dirty all day. Streaming is washing each plate the moment it is used. Plates are always clean, but someone is at the sink all day. Incremental is running the dishwasher every hour with only the plates used since the last run.

How it works

Three ways for the same orders to travel

The batch block waits a long time, then moves a lot at once. The streaming dots never stop.

How does an incremental or streaming job know what is new? It keeps a bookmark called a checkpoint: a small saved note of how far it has read. Each run starts from the bookmark and moves it forward.

Code

The same job, written three ways

Spark's streaming feature is called Structured Streaming. Its code looks almost the same as batch code: read becomes readStream and write becomes writeStream.

# 1. BATCH, full reload: read everything, replace everything.
(spark.read.table("bakery.bronze.orders_raw")
    .write.mode("overwrite")
    .saveAsTable("bakery.silver.orders"))

# 2. INCREMENTAL: a stream that handles whatever is new, then stops.
(spark.readStream.table("bakery.bronze.orders_raw")
    .writeStream
    .option("checkpointLocation", "/Volumes/bakery/ops/checkpoints/orders_silver")  # the bookmark
    .trigger(availableNow=True)      # process all new data, then stop
    .toTable("bakery.silver.orders"))

# 3. STREAMING: the same stream, left running, checking once a minute.
(spark.readStream.table("bakery.bronze.orders_raw")
    .writeStream
    .option("checkpointLocation", "/Volumes/bakery/ops/checkpoints/orders_silver")
    .trigger(processingTime="1 minute")
    .toTable("bakery.silver.orders"))

The trigger is the setting that says when the stream should look for new data. Changing one line moves you between "run and stop" and "run for ever".

What if I change this?

The trigger and the checkpoint

ChangeEffect
.trigger(availableNow=True)Processes everything that has arrived since the last run, then stops. You schedule it like a batch job and pay only while it runs.
.trigger(processingTime="1 minute")Stays running and checks for new data every minute. Fresher tables, but the compute is on all the time.
No trigger at allThe default is to check again as soon as the previous check finishes. Lowest delay, highest cost. Some compute types do not allow this: on serverless notebooks and jobs you must set a trigger, and only availableNow is supported there. Verify in the docs for the compute you use.
Delete or change the checkpoint locationThe stream loses its bookmark. It starts from the beginning and loads old data again, creating duplicates.
Use mode("overwrite") batch on a table that keeps growingSimple and always correct, but each run redoes all past work. It gets slower and dearer every day.

Two kinds of data

Bounded

Data with an end. "All orders from last year" is a fixed set. Batch suits it naturally.

Unbounded

Data with no end. Orders keep coming for as long as the shops are open. Streaming and incremental loads are built for this.

Don't confuse these

Streaming words that trip people up

Streaming code vs always-on

Writing readStream does not mean the job runs for ever. With the availableNow trigger a stream behaves like an incremental batch job.

Incremental vs full

Both can run on a schedule. Incremental touches only new data. Full reprocesses everything. Exam questions often turn on that one word.

Micro-batch vs real time

By default Spark streams in micro-batches: many very small batches, one after another. That is "near real time", not instant.

Checkpoint vs backup

A checkpoint is a bookmark of progress. It is not a copy of your data and cannot restore a table.

Check yourself

Quiz

1. What does "incremental" processing mean?

Incremental runs skip work that was already done. A checkpoint remembers where the last run stopped.

2. In the demo, what happened after you deleted the checkpoint and ran an incremental load?

Without its bookmark the job believes it has never run, so it starts from the first order.

3. A stream uses .trigger(availableNow=True). What does it do?

This trigger gives you incremental loading with batch-style scheduling: start, catch up, stop.

4. Which need is the best fit for always-on streaming?

Only the alert loses its value if it is late. The other two are fine with scheduled runs.

Wrap up

Key takeaways

  • Batch handles a pile at intervals. Streaming handles data continuously.
  • Incremental means each run handles only what is new.
  • A checkpoint is the bookmark that makes incremental work possible.
  • Lower latency costs more. Pick the slowest option the business can accept.
  • A stream with the availableNow trigger runs, catches up and stops.
