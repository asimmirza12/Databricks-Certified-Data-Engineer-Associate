The idea

A huge rented cupboard for files

"The cloud" means computers and disks owned by a large company, which you rent over the internet instead of buying. The three big providers are Amazon Web Services (AWS), Microsoft Azure and Google Cloud.

Each provider sells a service called object storage. You put files in, and you get them back later. In this world a stored file is called an object. Objects are kept in a top-level container called a bucket.

Object storage has three properties that shaped modern data engineering:

  • It is cheap and has no practical size limit. You pay for what you store.
  • It is separate from the computers that process data. You can switch all your computers off and the data stays put.
  • Objects are replaced, not edited. You cannot change one line in the middle of an object. You upload a new version of the whole thing.
Everyday analogy

A cloakroom at a theatre. You hand over a coat and get a ticket with a number. Later you show the ticket and get the same coat back. You cannot ask the attendant to sew on a button while it hangs there. You must take the coat out, change it and hand it in again. The ticket number is the object's name. The cloakroom has room for everyone's coats, and it stays open when the stage lights are off.

How it works

Storage stays. Compute comes and goes.

The computers that run Spark are called compute. They read objects from storage, work on them and write new objects back. They hold nothing permanent themselves.

The long name of each object is called its key. The slashes make it look like folders, but see below.

Folders are an illusion

A bucket is really one flat list of objects. Each has a name called a key, such as orders/2026/11/16/north.csv. The slashes are simply characters in the name. Tools show them as folders to be friendly.

The start of a key, such as orders/2026/11/, is called a prefix. "Listing a folder" really means "show me every object whose key begins with this prefix".

How storage paths look

Every object has an address. The first part tells you which cloud it is in.

# Amazon S3:      s3://<bucket>/<key>
s3_path   = "s3://bakery-landing/orders/2026/11/16/north.csv"

# Azure ADLS:     abfss://<container>@<storage account>.dfs.core.windows.net/<key>
adls_path = "abfss://landing@bakerydata.dfs.core.windows.net/orders/2026/11/16/north.csv"

# Google Cloud:   gs://<bucket>/<key>
gcs_path  = "gs://bakery-landing/orders/2026/11/16/north.csv"

On Databricks you usually do not use those raw addresses. An administrator connects the bucket once, and you then reach files through a friendlier path that starts with /Volumes/. Lesson 00-09 explains why that is safer.

# List what is under a prefix. Works the same on all three clouds.
files = dbutils.fs.ls("/Volumes/bakery/landing/till_files/orders/2026/11/16/")
for f in files:
    print(f.name, f.size)

# Read every object under the prefix as one DataFrame.
day_orders = (spark.read.format("csv")
    .option("header", "true")
    .load("/Volumes/bakery/landing/till_files/orders/2026/11/16/"))
-- The same listing in SQL.
LIST '/Volumes/bakery/landing/till_files/orders/2026/11/16/';
What if I change this?

Things that behave differently from your laptop

ChangeEffect
Upload to a key that already existsThe old object is replaced as a whole. There is no "append a line" and no warning.
Switch all compute offEvery object is still there. You pay only for storage. Nothing can be queried until compute is back on.
Point a read at a prefix instead of one objectSpark reads every object under that prefix and treats them as one dataset.
"Delete a folder"Really a delete of every object with that prefix. With millions of objects it takes time.
Store data as millions of tiny objectsListing and opening them becomes the slow part of every job. Fewer, larger files are better.

Object storage next to other places for data

Laptop disk

Small, fixed size, real folders, files can be edited in place. Gone if the laptop breaks.

Object storage

Huge, cheap, flat list of keys, objects replaced whole. Kept safe by the cloud provider.

Database

Stores rows, not files. Fast single-row changes. Storage and compute are usually tied together and cost more per gigabyte.

Don't confuse these

Storage words

Folder vs prefix

Object storage has no real folders. A "folder" is a shared beginning of many keys.

Storage vs compute

Storage keeps data and is always on. Compute processes data and is switched on only when needed. They are billed separately.

Bucket vs container

The same thing with two names. AWS and Google say bucket. Azure says container.

Object storage vs table

Storage holds files and knows nothing about rows, columns or schemas. A table is a layer built on top of those files.

Check yourself

Quiz

1. All compute is switched off for a week. What happens to the data in object storage?

Storage and compute are separate. Turning one off does not touch the other.

2. In the demo, you uploaded the same key twice. How many objects were there for that key afterwards?

A key names exactly one object. Uploading again swaps the whole object.

3. Which set lists the object storage services of AWS, Azure and Google Cloud, in that order?

Amazon S3, Azure Data Lake Storage, Google Cloud Storage.

4. What is a prefix?

Listing by prefix returns every object whose key starts with those characters.

Wrap up

Key takeaways

  • Object storage is cheap, huge and always available.
  • S3, ADLS and GCS are the same idea on three clouds.
  • Storage and compute are separate. Data survives when compute is off.
  • Objects are replaced whole. Folders are only key prefixes.
  • Many tiny objects are slow. Fewer large ones are fast.
