Medallion architecture: bronze, silver, gold

The idea

Improve the data in three steps, and keep every step

The medallion architecture is a habit, not a product. It says: do not go from messy source data to a finished report in one jump. Go through three layers of tables, each cleaner than the last, and keep all three.

  • Bronze holds the data exactly as it arrived. Mistakes and all. Nothing is fixed, nothing is thrown away.
  • Silver holds the same data after cleaning: correct types, no duplicates, bad rows dealt with.
  • Gold holds data shaped for one particular use: totals, averages and summaries that a report or a person can read directly.

The names come from medals. Quality goes up as you move from bronze to gold.

Everyday analogy

From wheat to bread. Sacks of wheat arrive from the farm with husks and the odd stone: that is bronze. The mill cleans and grinds it into flour: silver. The baker turns flour into loaves, rolls and cakes for different customers: gold. A sensible bakery keeps some wheat in the store. If a batch of flour turns out bad, it can mill again. Without the wheat, it would have to wait for next year's harvest.

How it works

Data only moves one way

One silver table can feed many gold tables. Each gold table answers one group's questions.

Each layer is built only from the layer before it. Gold never reads from the source directly. That is what makes the next idea possible.

Why keep bronze? Because cleaning rules are written by people, and people make mistakes. If a rule was wrong, you fix the rule and rebuild silver and gold from bronze. If you had cleaned the data on arrival and thrown the raw version away, the rows your bad rule dropped would be gone for good.

Code

Three layers, three statements

A common convention is one schema per layer inside a catalog: bakery.bronze, bakery.silver, bakery.gold. It is a convention, not a rule.

-- BRONZE: land the files as they are. Everything stays text. Record where each row came from.
CREATE OR REPLACE TABLE bakery.bronze.orders_raw AS
SELECT *, _metadata.file_path AS source_file
FROM read_files(
  '/Volumes/bakery/landing/till_files/orders/',
  format => 'csv',
  header => true,
  inferColumnTypes => false   -- do not guess types yet: keep every column as text
);

-- SILVER: one clean row per order, with proper types.
CREATE OR REPLACE TABLE bakery.silver.orders AS
SELECT DISTINCT
  try_cast(order_id AS INT)         AS order_id,   -- try_cast gives NULL, not an error, for a bad value
  initcap(trim(shop))               AS shop,
  try_cast(price AS DECIMAL(10,2))  AS price
FROM bakery.bronze.orders_raw
WHERE try_cast(price AS DECIMAL(10,2)) IS NOT NULL;

-- GOLD: shaped for the finance report.
CREATE OR REPLACE TABLE bakery.gold.sales_by_shop AS
SELECT shop, COUNT(*) AS orders, SUM(price) AS total_sales
FROM bakery.silver.orders
GROUP BY shop;

These statements rebuild each table in full every time, which keeps the example short. Real pipelines load bronze and silver incrementally (lesson 00-04). Modules 02 and 03 show how.

What if I change this?

Bending the pattern

ChangeEffect
Skip bronze and clean data as it arrivesOne table fewer to store. But a wrong cleaning rule now loses data permanently, and you cannot check what the source really sent.
Convert types in bronze (prices as numbers on arrival)A single odd value such as "n/a" can make the load fail or turn into NULL before you have a raw copy. Keeping bronze as plain text is the safe default.
Let analysts query bronze directlyThey meet duplicates and bad values, and each analyst cleans them differently. Two reports then disagree.
Put business summaries in silverSilver stops being a general, reusable clean copy. The next team that needs row-level detail has nowhere to get it.
Build one gold table for everybodyIt grows wide and confusing. Several small gold tables, one per need, are easier to trust and to secure.

What the pattern buys you

A way back

Any layer can be rebuilt from the one before it, right back to the raw data.

One version of clean

Cleaning is done once, in silver. Every report inherits the same rules.

Simpler access rules

Many people can read gold. Few need silver. Almost nobody needs bronze.

Don't confuse these

Medallion misunderstandings

Pattern vs feature

Medallion is a way of organising tables. There is no "medallion" button or setting. Bronze, silver and gold tables are ordinary tables with meaningful names.

Bronze vs the source

Bronze is your own copy of what the source sent, kept in your platform. It is not the source system itself.

Silver vs gold

Silver is clean but still detailed and general. Gold is shaped for one question. "Cleaned and deduplicated" points to silver. "Aggregated for a dashboard" points to gold.

Exactly three?

Three is the usual number, not a law. Some teams add a landing area before bronze or split silver in two. The idea of step-by-step refinement stays the same.

Check yourself

Quiz

1. Which layer should hold data exactly as the source sent it?

Bronze is the untouched raw copy. Cleaning starts in silver.

2. In the demo, why could the lost South orders be recovered when a bronze layer was kept?

The bug only affected what was written to silver. The raw rows were safe in bronze the whole time.

3. A table has one row per shop per day with total sales, built for a finance dashboard. Which layer is it?

It is aggregated and made for one specific use. That is the description of gold.

4. Two teams get different totals from the same source data. What is the usual cause?

Shared cleaning in silver is what gives every downstream table the same starting point.

Wrap up

Key takeaways

  • Bronze is raw, silver is cleaned, gold is shaped for a purpose.
  • Each layer is built only from the one before it.
  • Keeping bronze means any mistake further on can be repaired.
  • Cleaning once in silver gives everyone the same numbers.
  • Medallion is a pattern for organising tables, not a product feature.
