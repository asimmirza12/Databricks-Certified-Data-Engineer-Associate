Looping with For each

The same task often has to run for many things: one load per source table, one report per shop. Writing a task for each would be tedious. A For each task runs one nested task once per item in a list.

The idea

One task definition, many runs

A For each task holds a list of inputs and one nested task. It runs the nested task once for each item. Each run is called an iteration.

Inside the nested task, the current item is available as {{input}}. If the item is an object, its fields are {{input.field_name}}. So one notebook can load every table, using a different table name each time.

Two settings control the loop:

  • Inputs: the list. It can be a JSON array typed into the task, or a reference to a value from an earlier task, such as a list a previous task produced.
  • Concurrency: how many iterations may run at the same time. The default is 1, which runs them one after another.

Typed JSON inputs are limited to about 5,000 characters. For a long list, store the list in a table and read it with a lookup, as the docs describe for large parameter arrays.

Everyday analogy

A teacher marking a pile of papers with one rubric. The rubric is the nested task: the same steps for every paper. The pile is the input list. The teacher picks up one paper at a time (concurrency 1), or puts several markers at separate desks (concurrency higher). Each paper is marked, and the marking is recorded per paper.

How it works

A list in, one run per item out

The nested task is the same in every iteration. Only the value of input changes.

Sequential or parallel

With concurrency 1, iterations run one after another, which is slower but gentle on a shared source. A higher number runs several at once, subject to the limits of the compute and the workspace. If you leave concurrency out of a bundle definition, the iterations may all run in parallel within those limits.

Code

  
A For each task in a job


tasks:
  - task_key: load_each_table
    for_each_task:
      inputs: '["orders", "shops", "prices"]'   # the list to loop over
      concurrency: 2                                   # at most two iterations at once
      task:
        task_key: load_one
        notebook_task:
          notebook_path: /Workspace/bakery/load_table
          base_parameters:
            table_name: "{{input}}"               # the current item


# load_table notebook: read the table name passed in by the loop.
table = dbutils.widgets.get("table_name")
(spark.read.table(f"bakery.landing.{table}")
    .write.mode("overwrite")
    .saveAsTable(f"bakery.bronze.{table}"))

  
Check the exact field names of the for-each block in the bundle reference, and the notebook widget name, before use. The pattern is what matters: a list in, one nested task, and a reference to the current item.






  
What if I change this?

  
The loop settings and what they do

  

    
ChangeEffect

    
Concurrency from 1 to 6The loop finishes sooner, but six loads hit the source at once.

    
Use {{input}} in a notebook pathEach iteration can run a different notebook. Usually one notebook with a parameter is simpler.

    
Use {{input.field}} with a list of objectsEach iteration gets one field of its object, so one loop can carry several values.

    
Type a list longer than about 5,000 charactersToo long to type. Store the list in a table and read it instead.

    
An empty listNothing runs. Check that upstream work produced items before the loop.

    
Put a pipeline task inside the loopIterations of a pipeline task run one at a time, whatever the concurrency setting.

Don't confuse these

  
Loop traps

  

    
Concurrency vs number of items
Concurrency is how many run at once. The number of items is how many runs there are in all.

    
{{input}} vs a parameter
{{input}} is the current item. A job parameter is the same for every iteration.

    
For each vs a loop in code
A For each task creates tracked iterations in the job's run history. A loop in a notebook is one task, with no per-item record.

    
Loops and retries
Each iteration is its own run of the nested task. Check how retries apply to iterations before relying on them.

  






  
Check yourself

  
Quiz

  

    

      1. A For each task has no concurrency set in a bundle definition. What is the default?
      
      
      
      
In a bundle definition, leaving concurrency out lets iterations run in parallel within the platform's limits.

    

    

      2. What does {{input}} refer to inside the nested task?
      
      
      
      
{{input}} is the item for the iteration that is running.

    

    

      3. In the demo, six loads each take two minutes. What is the total time at concurrency 2?
      
      
      
      
Six items at two at a time make three batches of two minutes: six minutes.

    

    

      4. Why store a long list in a table rather than type it into the job?
      
      
      
      
Typed JSON has a size limit, and a list kept in a table can change without editing the job.

    

  






  
Wrap up

  
Key takeaways

  
    
    
  • A For each task runs one nested task once per item in its list.
    • 
    
  • {{input}} carries the current item; {{input.field}} carries one field of an object.
    • 
    
  • Concurrency sets how many iterations run at once. The default is one at a time in the UI.
    • 
    
  • For long or changing lists, read the items from a table.
