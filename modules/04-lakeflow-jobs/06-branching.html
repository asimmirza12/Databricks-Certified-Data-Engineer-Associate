Branching: If/else and run-if conditions

Sometimes the next step depends on the result of the last one. If the data was clean, publish it. If not, quarantine it and alert someone. A job can choose its path, and only one path runs.

The idea

Two ways to choose a path

Branching means a job takes one of several routes. Lakeflow Jobs offers two tools for it.

  • An If/else condition task tests a value and sends the run down a true path or a false path. It is a task of its own, with two outcomes.
  • Run if rules, from lesson 04-03, let a task run or not based on how its upstream tasks finished. They choose by outcome, not by a value.

An If/else condition task compares two operands with an operator. The left operand is usually a task value or a job parameter. The operators are:

  • EQUAL_TO, NOT_EQUAL
  • GREATER_THAN, GREATER_THAN_OR_EQUAL
  • LESS_THAN, LESS_THAN_OR_EQUAL

Downstream tasks are attached to the true or false outcome. Only the tasks on the chosen path run.

Everyday analogy

A fork at the end of a road. At the sign, you check: is the bridge open? If yes, take the left road. If no, take the right. You do not drive both. The sign is the If/else condition; the two roads are the true and false outcomes. A run-if rule is a different sort of sign: "only go this way if the last car made it through".

How it works

A condition, two outcomes, one path

The condition task itself runs, then exactly one of its two paths runs. The other path is skipped, not failed.

Branching by run-if

A run-if rule can also split a graph. Put one task on All succeeded and another on At least one failed, and only one of them runs, depending on how the upstream task finished. That is a branch by outcome, without a condition task.

If the upstream task that provides a condition's value is disabled, the If/else task fails. Make sure the value is always produced.

Code

A branch in a job

tasks:
  - task_key: count_rows
    notebook_task: {notebook_path: /Workspace/bakery/count_rows}

  - task_key: any_bad_rows
    depends_on: [{task_key: count_rows}]
    condition_task:
      left: "{{tasks.count_rows.values.bad_records}}"
      op: GREATER_THAN
      right: "0"

  - task_key: quarantine
    depends_on:
      - {task_key: any_bad_rows, outcome: "true"}     # runs only on the true path
    notebook_task: {notebook_path: /Workspace/bakery/quarantine}

  - task_key: publish_gold
    depends_on:
      - {task_key: any_bad_rows, outcome: "false"}    # runs only on the false path
    notebook_task: {notebook_path: /Workspace/bakery/publish_gold}

The condition task's operands are written as strings in the definition, and the outcome names are true and false. Check the condition task reference for exact field names before use.

What if I change this?

Operators and paths

ChangeEffect
GREATER_THAN to GREATER_THAN_OR_EQUAL, with the right side 0A count of exactly 0 now takes the true path. Check which boundary you mean.
Swap the true and false pathsPublishing and quarantine trade places. A quiet, serious error.
Set the right operand to a value that is not a numberThe comparison fails, and the condition task fails with it.
Remove the depends_on on the condition taskIt may read the value before the count has been set.
Use run-if At least one failed instead of a conditionThe branch now depends on failure, not on a count. Good for errors, not for data quality thresholds.
Make one path depend on both true and false outcomesThe task waits for a path that never runs, and may be marked as unable to run.

Don't confuse these

Branching traps

Skipped vs failed

The path not taken is skipped. Skipped is not a failure. A run can succeed with some tasks skipped.

If/else vs run-if

If/else tests a value. Run-if tests how tasks finished. Choose by what you are branching on.

GREATER_THAN vs GREATER_THAN_OR_EQUAL

They differ exactly at the boundary value. Read the operator carefully.

Branching vs looping

A branch chooses one path. A loop repeats a task (lesson 04-07).

Check yourself

Quiz

1. An If/else condition task is true. What runs?

Exactly one outcome path is followed. The other is skipped.

2. Which operator tests whether the left value is at least the right value?

"At least" includes the boundary, which is what GREATER_THAN_OR_EQUAL does.

3. In the demo, bad_records was 0, the condition was GREATER_THAN 0. Which path ran?

Zero is not greater than zero, so the condition is false and the publish path runs.

4. A task on the false path is not run. How is it shown in the run?

A path not taken is skipped. It is not counted as a failure.

Wrap up

Key takeaways

  • An If/else condition task compares two operands and sends the run down a true or false path.
  • Only one path runs. The other is skipped, not failed.
  • Run-if rules branch by how tasks finished. If/else branches by a value.
  • Make sure the value the condition reads is always set.
