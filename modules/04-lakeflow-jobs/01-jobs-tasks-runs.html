Lakeflow Jobs: jobs, tasks and runs

So far you have written code that runs when you press a button. A job is how that code runs on its own: on a timetable, in order, and with a record of every time it ran.

The idea

A job holds tasks. Each time it runs, it makes a run.

Lakeflow Jobs is the Databricks orchestrator. It was formerly called Databricks Workflows. Orchestration means running steps in the right order at the right time, and recording what happened.

The vocabulary has three levels:

  • A job is the definition: its name, its tasks, its schedule and its settings.
  • A task is one step inside a job. It is one notebook, one SQL query, one pipeline and so on.
  • A run is one execution of the job. Every scheduled start, or manual start, creates a new run. The run records the start time, end time, status and output of each task.

A job can have one task or hundreds. The job defines the plan once. Runs are the record of each time the plan was carried out.

Everyday analogy

A recipe card, a cook and a meal log. The recipe card lists the steps: chop, fry, serve. Each step is a task. The card is the job. Every time you cook from it you create a meal, and the kitchen log records when it was cooked, how long each step took and whether it went well. The log entry is the run. The card is written once; the log grows with every meal.

How it works

Definition, run, and the record of tasks

The job is the plan. The run is the record of one carrying-out. Failures are recorded against the task that failed, not against the whole job.

What a run records

When

The start and end time, and how long each task took. Used to spot slow runs.

How

What started it: the schedule, a file arriving, a table changing, or a person.

Outcome

Each task's status, and the error message for any that failed.

You can see the history of every run in the job's run history. Module 06 uses it to spot slowdowns.

Describing a job

  
A job can be created in the UI, which writes the same description behind the form. Here is the definition in the form used by Declarative Automation Bundles, which Module 05 covers:


name: ingest_bakery_nightly
schedule:
  quartz_cron_expression: "0 0 2 * * ?"     # every night at 02:00
  timezone_id: "Europe/London"
tasks:
  - task_key: load_orders
    notebook_task:
      notebook_path: /Workspace/bakery/load_orders
  - task_key: build_gold
    depends_on:
      - task_key: load_orders
    notebook_task:
      notebook_path: /Workspace/bakery/build_gold

  
Each task has a task_key, a name unique inside the job. Runs refer to tasks by that key, so renaming a key changes the history view.






  
What if I change this?

  
Settings that shape a job and its runs

  

    
ChangeEffect

    
Add a second taskThe job now has two steps. Each run records both separately.

    
Rename a task_keyEarlier runs show under the old name. Dependencies that name the key must be updated too.

    
Change the scheduleFuture runs follow the new timetable. Runs already recorded are unchanged.

    
Start a run by handA run is created outside the schedule and recorded the same way.

    
One task failsThat task is marked failed in the run. Whether the others still run depends on dependencies (lesson 04-03).

    
Remove a task from the job definitionFuture runs no longer include it. The history of earlier runs still shows it.

Don't confuse these

  
Vocabulary traps

  

    
Job vs run
The job is the plan. A run is one carrying-out of it. Editing a job does not change past runs.

    
Task vs notebook
A notebook is code. A task is the job's step that runs it. One notebook can be used by several tasks.

    
Workflows vs Lakeflow Jobs
Same product. Lakeflow Jobs is the current name; Workflows is the former name. Exam questions may use either.

    
task_key vs task name
The task_key is the identifier used in dependencies and runs. Display names are for people.

  






  
Check yourself

  
Quiz

  

    

      1. What is a run?
      
      
      
      
A run is created each time the job starts, whether by schedule or by hand.

    

    

      2. Which of these is a task?
      
      
      
      
A task is one step of a job. The schedule and the history belong to the job.

    

    

      3. You edit a job so a task is removed. What happens to the history of earlier runs?
      
      
      
      
Runs are a record. Editing the definition affects future runs only.

    

    

      4. In the demo, when build_gold failed, what did the run history show?
      
      
      
      
Each task's status is recorded inside the run, so failures can be traced to the task.
