Dependencies and the task graph (DAG)

Tasks are not a simple list. They form a graph: some wait for others, some run side by side, and each one decides whether to run based on how the tasks before it finished. The graph is the job's real logic.

The idea

A directed acyclic graph

A job's tasks form a DAG: a directed acyclic graph. Directed means each dependency points one way, from a task that must come first to a task that waits. Acyclic means there are no loops back: no task can wait, directly or indirectly, for itself.

A dependency is written as depends_on. A task that lists another in depends_on waits for it. Tasks with no dependency between them can run at the same time.

Two things decide whether a downstream task runs. The first is whether the upstream tasks finished. The second is its Run if condition. The default is All succeeded: the task runs only if every task it depends on succeeded.

The Run if options are:

  • All succeeded (default): every upstream task succeeded.
  • At least one succeeded: one or more upstream tasks succeeded.
  • None failed: no upstream task failed. Skipped tasks do not count as failures.
  • All done: every upstream task has finished, whatever its result.
  • At least one failed: one or more upstream tasks failed. Used for alerts and clean-up.
  • All failed: every upstream task failed.
Everyday analogy

Building a house. The roof cannot go on until the walls are up, so the roof depends on the walls. The plumber and the electrician can work at the same time, since neither waits for the other. And the inspector visits only when the building work is done, whether or not every job went smoothly. The dependencies are the arrows. The Run if rule is the inspector's rule: "only if everything before me passed", or "whether or not anything passed".

How it works

A graph, and what each run-if rule does

The arrow from alert to the two loads is hidden here for space. In a real job alert would depend on both loads, and would run only if one of them failed.

What happens to a task whose condition is not met

For the success-based rules, the task is marked Upstream failed. For the failure-based rules, it is marked Excluded. Either way it does not run, and the tasks that depend on it follow the same logic.

Code

Dependencies and run-if in a job

tasks:
  - task_key: load_orders
    notebook_task: {notebook_path: /Workspace/bakery/load_orders}

  - task_key: load_shops
    notebook_task: {notebook_path: /Workspace/bakery/load_shops}

  - task_key: combine
    depends_on:                              # waits for both loads
      - {task_key: load_orders}
      - {task_key: load_shops}
    run_if: ALL_SUCCESS                      # the default; shown for clarity
    notebook_task: {notebook_path: /Workspace/bakery/combine}

  - task_key: alert
    depends_on:
      - {task_key: load_orders}
      - {task_key: load_shops}
    run_if: AT_LEAST_ONE_FAILED             # runs only when a load failed
    notebook_task: {notebook_path: /Workspace/bakery/notify_team}

The graph must stay acyclic. A job that makes task A wait for B while B waits for A is rejected. Check the exact key names for run-if in the bundle reference before use.

What if I change this?

Each dependency and rule

ChangeEffect
Remove a depends_on entryThe task may start before its input is ready. Often the cause of "file not found" errors.
Add a dependency that creates a loopThe job is invalid. No run can start, because each task would wait for itself.
Leave combine on All succeeded and one load failsCombine is marked Upstream failed and does not run. Nothing is combined.
Set combine to None failedCombine runs if the failed load was the only problem and nothing actually failed. Skipped tasks do not block it. Use with care: it runs on partial input.
Set combine to All doneCombine runs whatever the loads did, even if both failed. Only sensible for clean-up tasks.
Set alert to All failedThe alert runs only if every load failed. A single failure does not alert anyone.
Set alert to At least one failedThe alert runs on any failure. The usual choice for notifications.

Parallel or sequential?

Parallel

Tasks with no dependency between them run at the same time. Faster, if they are independent.

Sequential

A chain of dependencies runs one after another. Needed when each step uses the last one's output.

Don't confuse these

Graph traps

Upstream failed vs Excluded

Both mean "did not run". Upstream failed follows a success-based rule. Excluded follows a failure-based rule.

None failed vs All succeeded

None failed tolerates skipped tasks. All succeeded does not. The difference matters after a skip.

Dependency vs schedule

A dependency orders tasks inside one run. A schedule decides when a run starts. They are separate.

DAG vs loop

A DAG has no loops between tasks. A For each task repeats one task over a list inside one step: lesson 04-07.

Check yourself

Quiz

1. What does the default Run if rule, All succeeded, do?

All succeeded is the default: every upstream task must have succeeded.

2. In the demo, one load failed and combine was on All succeeded. What happened to combine?

A success-based rule that is not met gives Upstream failed.

3. Which rule runs a clean-up task whatever the earlier tasks did?

All done waits for every upstream task to finish, then runs, whatever their result.

4. Which rule is the usual choice for an alert that fires on any failure?

At least one failed runs as soon as any upstream task failed. All failed needs every one to fail.

5. What is a DAG in Lakeflow Jobs?

Tasks are nodes and depends_on entries are arrows. No task may wait for itself.

Wrap up

Key takeaways

  • Tasks form a directed acyclic graph through depends_on.
  • Tasks with no path between them can run in parallel.
  • Run if decides whether a task runs, based on how its upstream tasks finished.
  • Success-based rules skip with Upstream failed. Failure-based rules skip with Excluded.
  • Use At least one failed for alerts and All done for clean-up.
