Retries

Networks blink. A source is busy for a minute. A file is still being written. Many failures are temporary, and a job that retries a failed task a little later often succeeds without anyone noticing.

The idea

Try again, but not forever

A retry is the job starting a failed task again by itself. You set how many times it may retry, and how long to wait before each attempt.

The settings are:

  • max_retries: the most times a failed task is run again. Zero, or leaving it out, means no retries.
  • min_retry_interval_millis: the minimum wait, in milliseconds, between the start of a failed attempt and the next attempt. The default is zero, which retries straight away.
  • retry_on_timeout: whether a task that hit its time limit should be retried. The default is false.

Retries only help with failures that will go away. A typo in a table name fails the same way every time, and retrying it wastes time and compute. Retries are for the temporary kind.

Everyday analogy

Redialling a busy phone line. If the line is busy, you hang up and try again in a minute. You do not redial every second for ever, and you stop after three attempts and leave a message. If the number itself is wrong, redialling changes nothing. The wait between calls is the retry interval; the number of tries is max retries.

How it works

One task, a limited number of attempts

Each attempt is recorded in the run. A task that eventually succeeds shows it took more than one attempt.

Timeouts and retries together

A task can also have a time limit. If you set both, the time limit applies to each attempt separately, not to all attempts together. A task that hangs can therefore be retried, but only if retry_on_timeout is true.

Code

Retry settings in a job

tasks:
  - task_key: load_orders
    notebook_task: {notebook_path: /Workspace/bakery/load_orders}
    max_retries: 3                  # try again up to three times
    min_retry_interval_millis: 60000  # wait at least one minute between attempts
    retry_on_timeout: false         # do not retry a task that hit its time limit
    timeout_seconds: 1800           # each attempt may run for 30 minutes

A notebook can also protect itself, so that a retry is safe. A retry runs the whole task again, so a half-finished load must not leave bad data behind:

# A retry reruns the whole task. Make the write safe to repeat: overwrite a whole batch.
(orders_today.write
    .mode("overwrite")
    .option("replaceWhere", "order_date = '2026-11-16'")  # replace only today's rows
    .saveAsTable("bakery.silver.orders"))

Check the exact field names and limits in the job reference before use. The replaceWhere option is one way to make a retry safe, shown here as an idea rather than the only method.

What if I change this?

Retry settings and their effects

ChangeEffect
max_retries set to 0The first failure is final. Good for tasks that must run at most once.
max_retries raised to 10A permanent error is retried ten times, using compute each time and delaying the alert.
min_retry_interval_millis set to 0Retries happen at once. Useless if the cause needs time to clear, such as a busy source.
Interval raised to ten minutesEach retry waits longer. Gives a busy source time to recover, but delays the whole night's work.
retry_on_timeout set to trueA task that hit its time limit is tried again. Useful if slowness is occasional; harmful if the task is always too slow.
A retried task writes to a table with appendEach attempt that wrote rows before failing leaves duplicates behind. Make the write safe to repeat.
Retries on a continuous jobNot supported. Retry policies do not apply to continuous jobs.

Which failures to retry

Retry

Network timeouts, busy sources, a file still being written, brief service outages.

Do not retry

A wrong table name, a bad credential, a code error, a rule violation. The same failure will happen again.

Real life

Retries in practice

ScenarioWhat happensFix
A nightly load fails once in ten runs, with a timeout to the sourceA brief network problemSet max_retries to 2 and a short interval
A job retries five times, and each attempt inserts half the rows againThe write is not safe to repeatMake the write overwrite its batch, or use MERGE
A bad column name fails four retries in a row, and the alert is an hour lateThe error is permanent, so retries only delayed the alertUse no retries for code errors. Alert on the first failure.
A slow query times out, and retrying it never finishesretry_on_timeout is on, and the task is always too slowFix the query or raise the time limit. Retries cannot make it faster.
Don't confuse these

Retry traps

Retry vs repair

A retry happens by itself, inside the run. A repair is a person rerunning failed tasks after the run ended.

Interval vs timeout

The interval is the wait between attempts. The timeout is the longest one attempt may run.

Max retries vs attempts

Max retries of 2 means up to three attempts in all: the first, plus two retries.

Retry is not a fix

A retry hides a temporary fault. It does not repair a bug. Find out why the first attempt failed.

Check yourself

Quiz

1. A task has max_retries set to 2. How many attempts can it make in total?

The first attempt plus two retries makes three attempts.

2. What does min_retry_interval_millis control?

It is the minimum gap between attempts. The time limit is a separate setting.

3. In the demo, which failure did no number of retries fix?

A permanent error fails the same way on every attempt. Retries only help with temporary failures.

4. Why is retry_on_timeout false by default?

Retrying a task that always runs past its limit does not make it finish.

Wrap up

Key takeaways

  • Retries are for temporary failures. Use max_retries and min_retry_interval_millis.
  • max_retries counts retries, so the total attempts is one more.
  • retry_on_timeout is off by default.
  • A retry reruns the whole task, so make the task's writes safe to repeat.
  • Retry policies do not apply to continuous jobs.
