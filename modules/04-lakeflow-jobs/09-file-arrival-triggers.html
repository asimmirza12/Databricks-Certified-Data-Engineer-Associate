File arrival triggers

Often the right moment to run is not a fixed time, but the moment the data lands. A file arrival trigger watches a folder and starts the job when new files appear. It can also wait for a quiet period, so a batch of files is processed once, not file by file.

The idea

Run when the files arrive

A file arrival trigger watches a location: a Unity Catalog external location or a volume path. When new files appear there, it starts a run of the job.

Two settings stop it running too often:

  • Wait after last change (a debounce). Each new file resets a timer. The run starts only after no new file has arrived for this long. A batch of ten files that land over five minutes triggers one run, not ten.
  • Minimum time between triggers (a cooldown). After a run starts, no other run starts until this much time has passed. It caps how often the job can run, whatever the arrivals.

Both are measured in seconds, and the docs set a minimum of 60 seconds for each.

For better performance, the docs recommend turning on file events for the external location, so Databricks is told about new files rather than having to search for them. Lesson 02-06 explains the two detection methods.

Everyday analogy

A doorbell that waits for the delivery to finish. A courier drops parcels one at a time over ten minutes. A sensible household waits until the van has been gone for a few minutes before carrying everything in (the debounce). And it will not answer the door more than once an hour, however many vans come (the cooldown).

How it works

Arrivals, a quiet period, then one run

The run waits for the quiet period, then starts once. If a run started recently, the cooldown holds the new run back until it has passed.

Choosing the values

The wait should be longer than the gap between files of one batch, so that a batch is not split. The cooldown should be no shorter than the time a run takes, so that runs do not pile up. Both are in seconds, with a 60-second floor.

Code

A file arrival trigger in a job

name: ingest_on_arrival
trigger:
  pause_status: "UNPAUSED"
  file_arrival:
    url: "s3://bakery-landing/supplier_drop/"   # an external location or volume path to watch
    min_time_between_triggers_seconds: 900      # at most one run every 15 minutes
    wait_after_last_change_seconds: 60         # start after a quiet minute
tasks:
  - task_key: load_supplier_files
    notebook_task: {notebook_path: /Workspace/bakery/load_supplier}

The docs show 900 seconds between triggers and 60 seconds of wait as a combined example. Check the field names in the job reference, and whether your location needs file events enabled, before use.

What if I change this?

The two settings and their effects

ChangeEffect
Wait after last change set to 0 or very shortA batch that arrives over several minutes may start several runs, each with part of the data.
Wait after last change set too longRuns start late after data lands. Fine for a nightly batch, poor for near-live data.
Minimum time between triggers set very shortRuns can start back to back, and may overlap if a run takes longer than the cooldown.
Minimum time between triggers set very longArrivals wait a long time for their run, even when the previous run finished quickly.
Files overwritten under the same nameThey do not count as new arrivals in the usual way. Deliver new versions under new names.
Turn on file events for the locationDiscovery is faster and cheaper, which suits frequent arrivals and large folders.

Time-based or data-driven?

Time-based

Runs at fixed times. Best when the data arrives on a known schedule, or when reports must be ready at a set hour.

Data-driven

Runs when data arrives. Best when arrival times vary, and the work should follow the data (lesson 04-11).

Don't confuse these

Trigger traps

Wait vs cooldown

The wait is the quiet time after the last arrival. The cooldown is the gap between runs. They do different jobs, and you usually want both.

Trigger vs schedule

A file arrival trigger starts on data. A scheduled trigger starts on the clock. A job has one trigger setting.

Arrival vs processing

A trigger starts a run. Which files the run processes is decided by the loader, such as Auto Loader, and its checkpoint.

Floor of 60 seconds

Neither setting can go below 60 seconds. For faster reaction, use a different design.

Check yourself

Quiz

1. Ten files arrive over six minutes. The wait is five minutes. How many runs start from this batch?

Each arrival resets the timer, so the run waits until the files stop. Then one run starts.

2. What does minimum time between triggers do?

It is a cooldown: no new run starts until this much time has passed since the last one.

3. In the demo, with a 5-minute wait, when did a run start after a file arrived at minute 1?

The timer counts from the last arrival. Five quiet minutes after minute 1 is minute 6.

4. Which trigger type would you choose for a job that must run at 9 am whatever the data does?

A fixed time needs the clock. Data-driven triggers start when data changes, which cannot promise a time.

Wrap up

Key takeaways

  • A file arrival trigger starts a run when new files appear in a watched location.
  • Wait after last change waits for a quiet period, so a batch runs once.
  • Minimum time between triggers caps how often runs start.
  • Both settings are in seconds, with a 60-second minimum. File events are recommended.
  • Choose time-based for fixed hours and data-driven for work that should follow the data.
