Choosing a trigger: time-based or data-driven

You now know four ways to start a job. Choosing between them is a design decision, and the exam asks it as a scenario. This lesson gives you the test to apply.

The idea

Time or data: which one drives the job?

A time-based trigger starts a run at a set time, whether or not new data has arrived. A scheduled trigger is time-based.

A data-driven trigger starts a run when data arrives or changes. A file arrival trigger and a table update trigger are data-driven.

The test is one question: does the business need the output at a fixed time, or as soon as the data is ready? Then check the data's own behaviour: does it arrive on a known timetable, or unpredictably? And what must finish before this job can start?

Everyday analogy

A bakery that bakes at 5 am, or when the flour arrives. If the shop must open at 7 with bread, the baker bakes at 5, flour or not, because the deadline is fixed. If the baker only needs to bake when the flour is delivered, bake on delivery, and the shop's stock is fresh whenever the van comes. The first is time-based. The second is data-driven.

How it works

A decision path

The trade-off

Time-based

Predictable. Easy to plan and to explain. Can run when nothing changed, or start before the data is ready if it arrives late.

Data-driven

Runs when there is work, and as soon as it is ready. Timing depends on the data, so a fixed deadline needs care.

Many good designs combine them: data-driven triggers keep the work current, and a time-based check confirms that the expected data arrived by the deadline.

The deciding question

Code

Two triggers on one job

A job has one trigger setting, so a combined design usually uses two jobs: one data-driven and one time-based check. Here is the time-based check as a scheduled job:

name: check_gold_ready_9am
schedule:
  quartz_cron_expression: "0 0 9 * * ?"      # 09:00 every day
  timezone_id: "Europe/London"
tasks:
  - task_key: confirm_gold
    notebook_task: {notebook_path: /Workspace/bakery/confirm_gold_updated_today}
# confirm_gold_updated_today: fail loudly if gold was not refreshed today.
latest = spark.sql("DESCRIBE HISTORY bakery.gold.sales_by_shop LIMIT 1").first()
if latest.timestamp.date() < date.today():
    raise RuntimeError("gold not refreshed today")

The check reads the table's history (lesson 01-02). Adapt the test to what "refreshed" means for your tables.

What if I change this?

How the trigger choice changes the design

ChangeEffect
A fixed-time report becomes data-driven onlyIt may run late, or not at all on a quiet day. Add a scheduled check.
Files arrive on a schedule that never variesA scheduled trigger is simpler and more predictable. File arrival still works, but adds no value.
A time-based job runs every hour on unchanged dataWasted compute. A data-driven trigger runs only when there is something to do.
A data-driven job depends on late upstream dataIts runs may start on partial input. Use an all-condition or a wait, and check completeness.
Both a schedule and a file trigger added to one jobNot how this is designed: one job has one trigger setting. Use two jobs.

Real life

Choosing well

ScenarioWhat happensFix
A bank runs its risk report at 6 am, and the data may land lateA fixed deadline, and unreliable arrivalScheduled trigger at 6 am, with a check that the data is complete
A shop's gold dashboard must always show the latest salesOutput should follow the dataTable update trigger on silver
A weekly job runs even in weeks with no new data, and costs moneyTime-based on data that rarely changesFile arrival or table update trigger instead
A job starts before the upstream pipeline finishes, and reads half a tableA table trigger fires on each partial updateSet a quiet period, or trigger on the pipeline's completion
Don't confuse these

Choice traps

Time-based is not "less smart"

A deadline is a real requirement. A clock is the right tool for it, and data-driven is not automatically better.

Data-driven is not "always on"

A data-driven job starts only when its signal arrives. It is not a streaming job.

One trigger per job

A job has one trigger setting. Combine trigger types with separate jobs, not one job.

Exam wording

"Fixed time" or "by 9 am" points to time-based. "When the data is ready" or "as files arrive" points to data-driven.

Check yourself

Quiz

1. A board report must be ready at 8 am every weekday. Which trigger type fits best?

The deadline is fixed. A scheduled trigger starts at the set time every weekday.

2. Gold tables must refresh whenever silver tables change. Which fits?

The output should follow the data, so a table update trigger on the silver tables is the data-driven choice.

3. What is the main risk of a purely data-driven job for a fixed deadline?

Data-driven timing depends on arrivals. Without a clock, a late arrival means a late output.

4. A job must both react to changes and confirm a 9 am deadline. What is a good design?

One job has one trigger setting. Two jobs, each with the right trigger, do the two things.

Wrap up

Key takeaways

  • Time-based triggers start on the clock. Data-driven triggers start on a signal in the data.
  • Choose by the deadline and by how the data arrives.
  • Data-driven triggers avoid wasted runs. Time-based triggers give predictable timing.
  • Combine them with two jobs, and check completeness before a deadline.
