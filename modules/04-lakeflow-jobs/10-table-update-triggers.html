Table update triggers

Sometimes the signal that work is ready is not a file but a table: the orders table has just been refreshed. A table update trigger watches one or more tables and starts the job when they change.

The idea

Run when the tables change

A table update trigger names the tables it watches, using their full Unity Catalog names such as bakery.silver.orders. When one of them changes, the trigger starts a run of the job.

The trigger can watch Unity Catalog Delta and Iceberg managed tables, external Delta tables, materialized views, streaming tables and views built on supported tables. The job's run-as identity needs SELECT on every table it watches.

Three settings decide when the run starts:

  • Condition: any monitored table updated, or all of them updated since the last run.
  • Wait after last change: a quiet period. Each update resets the timer, so a run starts only once the tables have settled.
  • Minimum time between triggers: a cooldown between runs, as with file arrival triggers in 04-09.

The run can read the list of tables that changed since the last run, through the dynamic reference {{job.trigger.table_update.updated_tables}}, and act only on those.

Everyday analogy

A kitchen that cooks when the stock is restocked. The chef does not wait for a clock. The chef watches the shelves: "whenever the flour or the eggs are restocked, start the cake". "Any" means one delivery is enough. "All" means the cake waits until both have arrived. And the chef waits until the deliveries stop before starting, so the cake is made once, not once per box.

How it works

Watch, settle, then run

Two updates in two minutes make one run, not two. The run knows which tables changed.

Any or all

With any, one changed table is enough to start a run. With all, the run waits until every watched table has changed since the last run. Use all when the job needs every input to be fresh together.

Runs

Code

A table update trigger in a job

name: rebuild_gold_on_change
trigger:
  pause_status: "UNPAUSED"
  table_update:
    table_names:                           # fully qualified names
      - "bakery.silver.orders"
      - "bakery.silver.shops"
    condition: ANY_UPDATED                  # or ALL_UPDATED
    wait_after_last_change_seconds: 300   # start after a quiet 5 minutes
tasks:
  - task_key: build_gold
    notebook_task:
      notebook_path: /Workspace/bakery/build_gold
# In the task: act only on the tables that changed since the last run.
changed = "{{job.trigger.table_update.updated_tables}}"   # passed in as a parameter from the job
for table in changed.split(","):
    # rebuild only the gold objects that depend on this table
    rebuild_for(table)

The docs note a Beta SQL condition that starts a run only when data is ready, and the API exact field names. Check the Jobs API reference for the trigger object before copying these fields.

What if I change this?

Condition, timers and watched tables

ChangeEffect
Condition changed from any to allA run waits until every watched table has changed. Fewer runs, but a table that never updates blocks them all.
Wait after last change set to 0 or left outA run may start while a batch of updates is still arriving, and then again for the rest.
Minimum time between triggers set very shortRuns can follow each other closely, and may overlap if the job is slower than the gap.
Watch a view that filters out most changesThe view can fire on updates its filter would exclude. Watch the underlying tables if you need exact behaviour.
Add more monitored tablesMore changes will start runs, and the limit on tables per trigger applies (views count their sources).
The run-as identity loses SELECT on one tableThe trigger cannot watch it properly, and runs may fail or not start.

Don't confuse these

Table trigger traps

Table trigger vs table dependency

A table update trigger starts a job when a table changes. A task dependency orders tasks inside one run (04-03). Different things.

Any vs all

Any starts on one change. All waits for every table. Pick deliberately.

Updated vs changed rows

A table counts as updated when it changes at all. The trigger does not check which rows changed.

Full names only

Table names must be catalog.schema.table. Short names are not accepted.

Check yourself

Quiz

1. A job must run only when both the orders and the shops tables have changed. Which condition?

ALL_UPDATED waits until every watched table has changed since the last run.

2. What does the run-as identity need on each watched table?

The trigger must be able to read each monitored table, so the run-as identity needs SELECT.

3. In the demo, two updates happened inside the quiet period. How many runs started?

Each update resets the wait timer, so one run starts after the updates settle.

4. What does {{job.trigger.table_update.updated_tables}} give a task?

It lists the tables that changed since the previous run, so the task can act only on those.

Wrap up

Key takeaways

  • A table update trigger starts a run when watched tables change.
  • Use the full catalog.schema.table names. The run-as identity needs SELECT.
  • Any starts on one change. All waits for every table.
  • Wait after last change and minimum time between triggers stop runs from piling up.
  • The run can read which tables changed, and act only on those.
