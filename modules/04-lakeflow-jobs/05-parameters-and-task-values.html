Parameters and task values

A job should not hard-code the date it processes, or the file it reads. Parameters pass values into a job from outside. Task values pass results from one task to the next. Together they let one job do many different jobs.

The idea

Two ways values travel

A job parameter is a value supplied when the job runs: a date, an environment name, a file path. The same job can then process today's data, last week's, or the test copy, with no code change.

A task value is a small result one task produces for the tasks after it: a row count, a file name, a flag. Task A sets the value, and task B reads it.

Both are referenced with double curly braces in the job definition, so the job fills them in when a run starts:

  • {{job.parameters.run_date}} reads a job parameter.
  • {{tasks.count_rows.values.bad_records}} reads a value set by the task named count_rows.

A task value is limited to about 48 KiB of JSON. Pass small facts through task values, and pass the data itself through tables.

Everyday analogy

A parcel with a label, and a note inside. A job parameter is the address label written before the parcel leaves the office: it tells the courier where to go. A task value is the note tucked inside a parcel by one team and read by the next: "twelve items checked, two missing". Neither changes the parcel's contents; both carry information along the route.

How it works

Set once, read later

The references are filled in at run time, so the same definition produces a different report on each day it runs.

Reading values inside a notebook

A notebook task can read the job's parameters from widgets, and can set and read task values with the dbutils.jobs.taskValues helper. The helper works in Python notebooks.

Code

  
Parameters and task values in a job


tasks:
  - task_key: count_rows
    notebook_task:
      notebook_path: /Workspace/bakery/count_rows
      base_parameters:
        run_date: "{{job.parameters.run_date}}"   # pass the job parameter in

  - task_key: report
    depends_on:
      - {task_key: count_rows}
    notebook_task:
      notebook_path: /Workspace/bakery/report
      base_parameters:
        run_date: "{{job.parameters.run_date}}"
        bad_records: "{{tasks.count_rows.values.bad_records}}"


# Inside count_rows: set the task value that later tasks can read.
run_date = dbutils.widgets.get("run_date")        # the value passed in from the job
bad = (spark.table("bakery.silver.orders")
       .filter(f"order_date = '{run_date}' AND price IS NULL").count())
dbutils.jobs.taskValues.set(key="bad_records", value=bad)

# Inside report: read the value a task set earlier.
bad = dbutils.jobs.taskValues.get(taskKey="count_rows", key="bad_records")

  
taskValues.get works, but the docs advise the double-brace reference in the job definition instead. Then a task rename changes one place, not every notebook that reads the value. Check the exact widget and helper names for your notebook language.






  
What if I change this?

  
Parameters, values and their effects

  

    
ChangeEffect

    
Change a job parameter's value when starting a runThat run uses the new value. Other runs and the job definition are unchanged.

    
Rename the task that sets a valueReferences to the old name break. Update every reference that names it.

    
Set a task value that is larger than 48 KiBRejected. Store the data in a table and pass only its name or a count.

    
Read a task value from a task that did not runThe value is missing. Downstream logic must handle it, or it fails.

    
Hard-code the date in the notebook instead of a parameterThe job works only for that date. Every other day needs a code change.

    
Read a task value with get in a notebook, not a referenceWorks, but renaming the task means finding every notebook that uses it.

Real life

  
Values in practice

  

    
ScenarioWhat happensFix

    
The same job is copied for each country, with the country name written into the codeFive copies to keep in stepOne job with a country parameter

    
A backfill for last month must run without touching today's dataThe job used today's dateStart a run with the run_date parameter set to the backfill date

    
The report says "0 bad records" when the check task was skippedA missing task value was read as zeroHandle the missing value explicitly, and fail the report if the check did not run

    
A task value holds a whole table of rows, and the run failsIt is above the size limitWrite the rows to a table and pass the table's name

  






  
Don't confuse these

  
Value traps

  

    
Parameter vs task value
A parameter comes into the run from outside. A task value is produced inside the run by an earlier task.

    
Reference vs notebook widget
A double-brace reference is filled in by the job. A widget is a value the notebook reads at run time.

    
Task value vs table
Task values are for small facts. Data belongs in a table, which the next task reads.

    
Missing vs zero
A value that was never set is not the same as zero. Check for it before using it.

  






  
Check yourself

  
Quiz

  

    

      1. Which reference reads a value passed into the job when it starts?
      
      
      
      
Job parameters use the job.parameters form. Task values use the tasks form.

    

    

      2. What is a task value meant for?
      
      
      
      
Task values are small. Large data goes in a table, and secrets go in a secret store.

    

    

      3. In the demo, what happened when the first task was skipped and no value was set?
      
      
      
      
A value that was never set is missing, not zero. A careful report checks for it.

    

    

      4. Why is the double-brace reference preferred over a taskValues.get call in each notebook?
      
      
      
      
The reference lives in the job definition, so a rename is handled in one place.
