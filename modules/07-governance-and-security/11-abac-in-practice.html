ABAC in practice: central row filters and column masks

The idea

A few central policies instead of many table rules

The bakery wants two rules across the whole bakery catalog:

  • Regional managers see only their own region's rows, in any table that holds regional data.
  • Nobody except data admins sees customer emails.

With ABAC that is two policies on the catalog:

  • A row filter policy for tables tagged scope = regional. MATCH COLUMNS has_tag_value('geo', 'region') AS r finds the region column in each table, whatever it is called, and USING COLUMNS (r) passes it to the filter function.
  • A column mask policy for columns tagged pii = email, as in the last lesson.

How policies behave in practice:

  • Central: a policy on the catalog applies to every matching table below. A table owner cannot switch it off.
  • No clashes: a user can have only one distinct row filter per table and one mask per column. Two different rules for the same table and user (for example a policy and a table-level filter) cause an error, not a silent pick.
  • Fail closed: if a function or governed tag the policy needs is deleted, or the compute is too old, queries fail instead of showing unprotected data.
  • Exemptions: use EXCEPT for trusted identities only, such as the ETL service principal that must write full data.
  • Limits: there are quotas, such as 100 policies per catalog and 50 per table; check the docs for current values.
Everyday analogy

Head office rules for every branch. Head office says "each manager sees only their own branch's books" and "card numbers are always covered". Every branch follows it, including branches opened next year, and a branch manager cannot override it. If two rules ever disagree, staff stop and ask rather than guessing, and if the rulebook goes missing, the books stay locked.

How it works

Two policies across a catalog

The region column is called region in one table and area in another. The tag, not the name, connects them to the policy.

Code

The bakery's two catalog policies

-- Tag the data
ALTER TABLE bakery.gold.sales      SET TAGS ('scope' = 'regional');
ALTER TABLE bakery.gold.sales      ALTER COLUMN region SET TAGS ('geo' = 'region');
ALTER TABLE bakery.ops.deliveries  SET TAGS ('scope' = 'regional');
ALTER TABLE bakery.ops.deliveries  ALTER COLUMN area   SET TAGS ('geo' = 'region');

-- Filter function: the reader sees a row if they are in that region's group
CREATE OR REPLACE FUNCTION bakery.gov.own_region(r STRING)
RETURNS BOOLEAN
RETURN (r = 'North' AND is_account_group_member('region_north'))
    OR (r = 'South' AND is_account_group_member('region_south'));

-- Row filter policy for every regional table in the catalog
CREATE POLICY regional_rows
ON CATALOG bakery
ROW FILTER bakery.gov.own_region
TO `account users` EXCEPT `6f1c2b7e-0a4d-4c1e-9b8a-2d3e4f5a6b7c`, `data_admins`
FOR TABLES
WHEN has_tag_value('scope', 'regional')
MATCH COLUMNS has_tag_value('geo', 'region') AS r
USING COLUMNS (r);

-- Mask policy for every email column in the catalog
CREATE POLICY mask_emails
ON CATALOG bakery
COLUMN MASK bakery.gov.hide_email
TO `account users` EXCEPT `data_admins`
FOR TABLES
MATCH COLUMNS has_tag_value('pii', 'email') AS e
ON COLUMN e;

-- What applies to one table?
SHOW EFFECTIVE POLICIES ON TABLE bakery.gold.sales;

The tag keys scope and geo are made-up governed tags, and so is the service principal ID. With many regions, a mapping table (lesson 07-09) inside the filter function scales better than one line per region. Check the CREATE POLICY reference for the full syntax.

What if I change this?

Situations and their effects

ChangeEffect
Add a table-level row filter to a table a policy already filtersConflicting filters: queries error.
Two policies with identical functions and argumentsAllowed: they are not distinct rules.
Delete a governed tag or function a policy usesQueries on matching tables fail (fail closed).
Query from a runtime too old for ABACFails closed; no data returned.
Forget to tag a region columnThe policy cannot match it; that table is not filtered.
Put the ETL principal in EXCEPTIt reads and writes full data.

Don't confuse these

Practice traps

Conflict means error

Two distinct filters for one table and user do not combine; they fail.

Owners cannot override

A catalog or schema policy applies even to the table owner, unless they are in EXCEPT.

WHEN vs MATCH COLUMNS

WHEN picks tables by table tags; MATCH COLUMNS picks columns by column tags.

Untagged means unprotected

Policies only see what is tagged.

Check yourself

Quiz

1. A catalog row filter policy and a table-level row filter both apply to the same table for a user. What happens?

Only one distinct row filter per table and user is allowed.

2. How does a row filter policy find the region column when tables name it differently?

Tags connect the policy to columns, whatever they are called.

3. What does "fail closed" mean for ABAC?

Safety first: no data rather than unprotected data.

4. In the demo, what happened when you queried deliveries with area not tagged?

Untagged data is invisible to policies, so tagging is part of security.

Wrap up

Key takeaways

  • A few policies on a catalog can filter rows and mask columns across every tagged table.
  • WHEN matches tables by tag; MATCH COLUMNS finds columns by tag and passes them with USING COLUMNS or ON COLUMN.
  • Distinct conflicting rules error; missing tags, functions or supported runtimes fail closed.
  • Exempt only trusted identities with EXCEPT, and tag new data as part of creating it.
