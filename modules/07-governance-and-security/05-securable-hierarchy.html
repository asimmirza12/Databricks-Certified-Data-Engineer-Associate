The security hierarchy and privilege inheritance

Unity Catalog objects sit inside each other like folders. A privilege granted on a container flows down to everything inside it, including things created later. But reaching a table also needs permission to open each container on the way.

The idea

Grants flow down; usage opens the doors

Every object you can grant on is a securable. They nest: metastore, then catalog, then schema, then tables, views, volumes, functions and models. Some securables sit beside this tree, such as external locations, storage credentials and connections.

Privilege inheritance: give a group SELECT on the bakery catalog and it can read every table in every schema there, including tables made next month. A grant on a schema applies to all its objects. (Grants on the metastore itself do not flow down.)

To touch anything inside a container you also need the usage privileges: USE CATALOG for the catalog you are entering and USE SCHEMA for the schema inside it. They give no data access by themselves; they just let you through. So reading a table needs three things: USE CATALOG, USE SCHEMA and SELECT.

Some special privileges:

  • Owner: every object has one (a user, group or service principal). The owner can do everything on it, grant to others, and drop it.
  • MANAGE: lets someone who is not the owner grant and revoke, rename, drop and change the owner. It does not by itself give data access.
  • BROWSE: see that objects exist and read their metadata, without usage privileges or data access. Often granted on a catalog to account users.
  • ALL PRIVILEGES: every privilege that applies to the object (for a table: SELECT, MODIFY, APPLY TAG), but not MANAGE.
Everyday analogy

The bakery building. A key to the whole building (catalog grant) opens every room and every cupboard inside, even ones added next year. But to reach a cupboard you still need to be allowed through the front door (USE CATALOG) and the room door (USE SCHEMA). A cupboard key alone does not get you into the building.

How it works

The tree and the path to a table

SELECT on gold reaches every gold table. USE CATALOG and USE SCHEMA open the path to them.

Try it

Grant at different levels

The bakery-analysts group starts with nothing. Grant privileges at different levels, create a new table, and test what an analyst can query.

Grants to bakery-analysts

Effective on the chosen table

Code

Granting at the right level

-- Let analysts read every table in gold, including future ones
GRANT USE CATALOG ON CATALOG bakery      TO `bakery-analysts`;
GRANT USE SCHEMA  ON SCHEMA  bakery.gold TO `bakery-analysts`;
GRANT SELECT      ON SCHEMA  bakery.gold TO `bakery-analysts`;

-- Let everyone discover what exists, without reading data
GRANT BROWSE ON CATALOG bakery TO `account users`;

-- Let the data admins manage permissions on the whole catalog
GRANT MANAGE ON CATALOG bakery TO `data_admins`;

-- Make a group the owner, so nothing depends on one person
ALTER SCHEMA bakery.gold OWNER TO `data_admins`;

-- See what is granted, including inherited privileges
SHOW GRANTS `bakery-analysts` ON TABLE bakery.gold.daily;

Don't confuse these

Hierarchy traps

Three things to read

USE CATALOG + USE SCHEMA + SELECT.

Future objects

Grants on a container cover objects created later too.

MANAGE is not data access

It controls permissions, not reading.

ALL PRIVILEGES

Does not include MANAGE.

Check yourself

Quiz

1. A user has SELECT on bakery.gold.daily but gets permission denied. What is most likely missing?

The path to the table must be open as well.

2. You grant SELECT on schema bakery.gold. A new table is created there next week. Can the grantee read it?

Inheritance applies to current and future child objects.

3. Which privilege lets someone see what tables exist without reading any data?

BROWSE shows metadata without usage privileges or data access.

4. In the demo, what happened when the owner created gold.forecast after you granted SELECT on schema gold?

The schema grant flows down to new tables automatically.

Wrap up

Key takeaways

  • Metastore, catalog, schema, then tables, views, volumes, functions.
  • Grants on a container flow down to current and future children.
  • Reading needs USE CATALOG + USE SCHEMA + SELECT.
  • Owners and MANAGE holders control permissions; BROWSE shows metadata only.
