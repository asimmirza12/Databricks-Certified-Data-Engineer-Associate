Lineage: table and column level

Before you change or drop a table, you want to know what depends on it. When a dashboard shows a wrong number, you want to know where it came from. Unity Catalog records those connections for you, all the way down to single columns.

The idea

A family tree for your data, kept automatically

Lineage is the record of how data flows: which tables and files feed a table, which notebooks, jobs and pipelines change it, and which tables and dashboards read it. Unity Catalog captures it automatically for queries run on Databricks, with no setup in your code. It works across every workspace attached to the same metastore.

It is kept at two levels:

  • Table level: silver.orders was built from bronze.orders_raw.
  • Column level: gold.daily_sales.revenue was calculated from silver.orders.qty and silver.orders.price.

Where to see it:

  • Catalog Explorer: open a table, go to the Lineage tab, then See Lineage Graph. Expand nodes to go further upstream or downstream. Click a column to highlight the columns it came from and feeds.
  • System tables: system.access.table_lineage and system.access.column_lineage, which you can query with SQL. They keep about 395 days of events.

Lineage respects permissions. You need at least BROWSE on a table's catalog to explore its lineage. A related table you have no access to appears as a masked node: you can see that something is there, but not what it is.

Typical uses are impact analysis (what breaks if I change this?), finding the root cause of a bad number (where did it come from?), and showing auditors where sensitive data travels.

Everyday analogy

Ingredient tracing at the bakery. Every tray records which batch of dough it came from, and every batch records which sacks of flour went in. If one flour sack is recalled, you can list every cake that used it (impact analysis). If a cake tastes wrong, you can trace back to the exact sack (root cause). Column lineage is going one step finer: this cake's sweetness came from that bag of sugar.

Why

Code

Query lineage with SQL

-- Impact analysis: what reads from silver.orders?
SELECT DISTINCT target_table_full_name, entity_type, entity_id
FROM system.access.table_lineage
WHERE source_table_full_name = 'bakery.silver.orders'
  AND target_table_full_name IS NOT NULL;     -- reads without a write have no target

-- Root cause: which columns feed gold revenue?
SELECT DISTINCT source_table_full_name, source_column_name
FROM system.access.column_lineage
WHERE target_table_full_name = 'bakery.gold.daily_sales'
  AND target_column_name = 'revenue';

-- Who touched a sensitive table in the last 30 days, and with what?
SELECT event_time, created_by, entity_type, target_table_full_name
FROM system.access.table_lineage
WHERE source_table_full_name = 'bakery.silver.customers'
  AND event_date >= current_date() - INTERVAL 30 DAYS
ORDER BY event_time DESC;

The lineage system tables must be enabled by an admin. entity_type tells you what ran the query, such as NOTEBOOK, JOB, PIPELINE or DBSQL_QUERY. Check the system table reference for every column.

What if I change this?

Situations and their effects

ChangeEffect
You lack access to a downstream tableIt shows as a masked node; you cannot expand it.
Grant BROWSE on a schemaThe grantee can explore lineage for every table in that schema, without reading data.
Rename a table or columnLineage is not carried over to the new name.
Build a table through a temporary tableThe temporary table is not shown; the permanent tables on each side are linked directly.
Write data with RDDs, or from a tool outside DatabricksNot captured.
Insert literal values with no source tableNo column lineage, because nothing upstream fed those values.
Query events older than about 395 days in the system tablesGone: the system tables keep a rolling window.

Don't confuse these

Lineage traps

Automatic

No code changes are needed; Unity Catalog records lineage for queries run on Databricks.

Masked, not hidden

You see that a node exists even without access, but not its name or details.

BROWSE is enough

To explore lineage you need BROWSE, not SELECT. Lineage shows structure, not data.

Renames break it

Lineage does not follow a renamed table or column.

Quiz

column_lineage has source_column_name and target_column_name.

3. What is the minimum privilege to explore a table's lineage?

BROWSE shows metadata, including lineage, without data access.

4. In the demo, what did pat (SELECT on gold.daily_sales only) see upstream of daily_sales?

Lineage follows permissions: tables pat cannot access appear masked.

Wrap up

Key takeaways

  • Unity Catalog records lineage automatically, at table and column level, across workspaces on a metastore.
  • See it in Catalog Explorer's Lineage tab, or query system.access.table_lineage and column_lineage.
  • BROWSE is enough to explore it; objects you cannot access show as masked nodes.
  • Use it for impact analysis, root cause and audits; renames, RDDs and outside writes are not tracked.
