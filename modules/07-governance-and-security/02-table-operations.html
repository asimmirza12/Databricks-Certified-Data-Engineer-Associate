Creating, changing and dropping tables

A handful of SQL statements cover a table's whole life: create it, fill it, change its shape, rename it, hand it to another owner, and finally drop it. One choice matters more than it looks: replacing a table versus dropping and recreating it.

The idea

The table life cycle in SQL

  • Create: CREATE TABLE with a column list, or CTAS (CREATE TABLE ... AS SELECT) to create and fill it from a query in one step. Add IF NOT EXISTS to skip quietly when it already exists.
  • Change: ALTER TABLE adds or renames columns, renames the table (within the same catalog), sets table properties, and changes the owner.
  • Replace: CREATE OR REPLACE TABLE swaps the table's contents and shape in one step. On Delta tables it keeps the table's history, its privileges, and any row filters and column masks.
  • Drop: DROP TABLE removes it (lesson 07-01 covers what happens to the files).

Databricks recommends CREATE OR REPLACE over DROP then CREATE. Dropping first throws away the history and the grants, so everyone loses access until someone grants it again, and queries running in between fail.

Each statement needs the right privilege: CREATE TABLE on the schema to create, MODIFY to change columns or properties, and ownership or MANAGE to drop, rename or change the owner (plus USE CATALOG and USE SCHEMA to reach the table at all).

Everyday analogy

Changing the bakery's menu board. Replacing the board's contents keeps the frame, its spot on the wall and the list of people allowed to edit it (CREATE OR REPLACE). Taking the whole board down and putting up a new one leaves a blank wall for a while and nobody has the keys to it yet (DROP then CREATE).

How it works

Replace keeps history and grants

Readers of the replaced table never see a missing table.

Code

The statements

-- Create and fill in one step (CTAS). Managed, because there is no LOCATION.
CREATE TABLE IF NOT EXISTS bakery.gold.daily_sales AS
SELECT store_id, sale_date, SUM(amount) AS amount
FROM bakery.silver.sales
GROUP BY store_id, sale_date;

-- Change the shape
ALTER TABLE bakery.gold.daily_sales ADD COLUMN region STRING;
ALTER TABLE bakery.gold.daily_sales RENAME COLUMN amount TO revenue;   -- needs column mapping on Delta; verify in the docs

-- Properties, name and owner
ALTER TABLE bakery.gold.daily_sales SET TBLPROPERTIES ('quality' = 'gold');
ALTER TABLE bakery.gold.daily_sales RENAME TO bakery.gold.store_daily_sales;  -- same catalog only
ALTER TABLE bakery.gold.store_daily_sales SET OWNER TO `data_admins`;

-- Rebuild the contents without losing history or grants
CREATE OR REPLACE TABLE bakery.gold.store_daily_sales AS
SELECT store_id, sale_date, SUM(amount) AS revenue
FROM bakery.silver.sales
GROUP BY store_id, sale_date;

-- Remove it
DROP TABLE IF EXISTS bakery.gold.store_daily_sales;

On Delta tables, a new column cannot be given a DEFAULT in the ADD COLUMN itself; set it afterwards with ALTER COLUMN ... SET DEFAULT. Check the ALTER TABLE reference for each clause's rules.

What if I change this?

Choices and their effects

ChangeEffect
IF NOT EXISTSNo error if the table exists; the statement does nothing.
CREATE OR REPLACENew contents and shape, same table: history, grants, filters and masks kept.
DROP then CREATEHistory and grants lost; a gap where queries fail.
RENAME TO another catalogNot allowed in Unity Catalog; stays in the same catalog.
SET OWNER TO a groupThe group gets full control; good so tables do not depend on one person.
ADD COLUMN on a big tableFast: existing rows read the new column as NULL without a rewrite.

Don't confuse these

Table statement traps

REPLACE vs DROP

REPLACE keeps history and grants. DROP then CREATE loses both.

MODIFY vs ownership

MODIFY changes data and columns. Dropping or changing owner needs owner or MANAGE.

CTAS shape

CTAS takes column names and types from the query.

Rename scope

A table can be renamed within its catalog, not moved to another.

Check yourself

Quiz

1. A job rebuilds a gold table every night. How should it do this so analysts keep access?

Replace keeps grants and history; drop throws them away.

2. Which privilege lets you add a column to a table you do not own?

Column changes and table properties need MODIFY on the table.

3. What does CTAS do?

CREATE TABLE ... AS SELECT.

4. In the demo, after DROP then CREATE, what happened when the analyst ran SELECT?

A new table starts with no grants except its owner's.

Wrap up

Key takeaways

  • CREATE TABLE (or CTAS), ALTER TABLE, CREATE OR REPLACE, DROP TABLE cover the life cycle.
  • Prefer CREATE OR REPLACE: history, grants, filters and masks stay.
  • MODIFY for column and property changes; owner or MANAGE for drop, rename and owner changes.
