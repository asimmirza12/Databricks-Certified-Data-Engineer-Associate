DENY: what it does and where it applies

DENY sounds like the opposite of GRANT, and in older Databricks permissions it was: a hard "no" that beat any "yes". Unity Catalog works differently. Knowing where DENY applies, and where it does not, is a classic exam question.

The idea

A hard "no", but only in the legacy catalog

In the legacy Hive metastore (the hive_metastore catalog, using the older table access control), DENY blocks a privilege for a principal. A DENY beats any GRANT, direct or through a group. Denying on a schema or catalog also denies on everything below it. To undo a DENY, you REVOKE the same privilege.

In Unity Catalog, the DENY statement is not supported. Unity Catalog permissions are additive: a principal can do something if any grant (on the object, a parent, or through any group) allows it. There is no general "deny SELECT". To stop someone reading a table you:

  • Revoke the grant where it was made, or remove them from the group that has it.
  • Grant at a narrower level (the schema or table) instead of broadly (the catalog).
  • Use row filters and column masks, or ABAC policies, when people may see the table but not every row or value.

One newer exception: ABAC DENY policies (Beta) can deny MANAGE ACCESS CONTROL, so selected people cannot change permissions on tagged objects even if they would normally be allowed. They do not deny SELECT or MODIFY.

Everyday analogy

Two bakeries with different rules. The old shop keeps a "banned" list at the door: if your name is on it, no key you hold works (DENY). The new shop has no banned list. You get in if you hold any valid key, so to keep someone out you take back every key they hold, or never hand one to their whole team.

How it works

Deny-wins vs grant-only

In Unity Catalog, block access by not granting it, not by denying it.

sam's access

Code

DENY in the legacy catalog, alternatives in Unity Catalog

-- Legacy hive_metastore only (table access control)
DENY SELECT ON TABLE hive_metastore.default.sales TO `sam@example.com`;
REVOKE SELECT ON TABLE hive_metastore.default.sales FROM `sam@example.com`;  -- removes the DENY

-- Unity Catalog: DENY is not supported. Instead...
-- 1. Grant narrowly, so only the right people get access
REVOKE SELECT ON CATALOG bakery FROM `bakery-analysts`;
GRANT  SELECT ON SCHEMA  bakery.gold TO `bakery-analysts`;

-- 2. Hide rows or values inside a table (lessons 07-08 and 07-09)
ALTER TABLE bakery.gold.daily SET ROW FILTER bakery.gov.region_filter ON (region);

-- 3. Beta: stop people changing permissions on sensitive objects
CREATE POLICY no_regrant ON CATALOG bakery
  TO `account users` EXCEPT `data_admins`
  DENY MANAGE ACCESS CONTROL
  FOR TABLES WHEN has_tag('sensitive');

ABAC DENY policies were in Beta when this lesson was written and need recent runtimes; check the docs before relying on them. SHOW GRANTS does not list them; use SHOW EFFECTIVE POLICIES.

Don't confuse these

DENY traps

UC has no DENY SELECT

The DENY statement is not supported by Unity Catalog.

Legacy DENY wins

In hive_metastore a DENY beats any GRANT.

Additive model

In Unity Catalog, any grant that applies allows access.

REVOKE where granted

Revoking from a user does nothing if a group still grants it.

Check yourself

Quiz

1. Where does the DENY statement apply?

Unity Catalog does not support DENY.

2. In hive_metastore, a group has SELECT and one member is denied SELECT. Can that member read?

In the legacy model, DENY beats any explicit or inherited grant.

3. In Unity Catalog, how do you stop one person reading a table their group can read?

Permissions are additive, so the group grant still lets them in.

4. In the demo, in Unity Catalog, what happened when you revoked SELECT from sam only?

sam never had a direct grant; access came from the group.

Wrap up

Key takeaways

  • DENY applies only to the legacy hive_metastore, where it beats any grant.
  • Unity Catalog has no DENY SELECT: permissions are additive.
  • Block access by granting narrowly, revoking where granted, and using groups carefully.
  • Hide rows or values with filters, masks or ABAC; ABAC DENY policies (Beta) only cover MANAGE ACCESS CONTROL.
