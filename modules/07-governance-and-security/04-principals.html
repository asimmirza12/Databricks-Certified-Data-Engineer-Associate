Principals: users, groups, service principals

Before you can give anyone access, you need to know who "anyone" can be. In Unity Catalog, access is granted to principals. There are three kinds, and one kind of group that cannot be used at all.

The idea

Three kinds of "who"

A principal is anything that can be given a privilege:

  • User: a person, named by their email address, such as `sam@example.com`.
  • Group: a named set of users and service principals, such as `bakery-analysts`. Grant to groups, not individuals: when someone joins or leaves, you change the group, not dozens of grants.
  • Service principal: a non-human identity for jobs and tools such as CI/CD pipelines. In SQL it is named by its application ID, a long string of letters and numbers.

Groups come in two kinds, and the difference matters:

  • Account groups are defined once for the whole Databricks account (often synced from your company's identity system). They can be granted Unity Catalog privileges.
  • Workspace-local groups are a legacy kind that exists in one workspace only. They cannot be granted Unity Catalog privileges. The built-in users group is one of them; use `account users` instead to mean everyone in the account.

In SQL, wrap names that contain characters such as @, hyphens or spaces in backticks.

Everyday analogy

Keys at the bakery. You can hand a key to a named baker (user), to "all morning-shift staff" (group), or to the delivery robot (service principal). Handing keys to the shift is easier than to each baker. A list of staff written on one shop's notice board (workspace-local group) is not recognised by head office, so keys cannot be issued to it.

How it works

Grants go to principals; people inherit through groups

One grant to the group covers every member, now and in future.

Code

Naming principals in SQL

-- An account group (backticks because of the hyphen)
GRANT SELECT ON TABLE bakery.gold.daily_sales TO `bakery-analysts`;

-- A user, by email
GRANT SELECT ON TABLE bakery.gold.daily_sales TO `sam@example.com`;

-- A service principal, by its application ID (made-up value)
GRANT MODIFY ON TABLE bakery.gold.daily_sales TO `6f1c2b7e-0a4d-4c1e-9b8a-2d3e4f5a6b7c`;

-- Everyone in the account (not the workspace-local `users` group)
GRANT BROWSE ON CATALOG bakery TO `account users`;

-- In a notebook or SQL function: is the current person in an account group?
SELECT is_account_group_member('bakery-analysts');

A name made only of letters, digits and underscores, such as data_admins, needs no backticks. Users, groups and service principals are managed in the account console or workspace admin settings.

What if I change this?

Choices and their effects

ChangeEffect
Grant to a group instead of each userOne grant; joiners get access automatically, leavers lose it.
Grant to a person for a job's accessThe job breaks when they leave. Use a service principal.
Grant to workspace group usersFails: workspace-local groups cannot hold Unity Catalog privileges.
Forget backticks around bakery-analystsSyntax error: the hyphen is read as minus.
Remove a user from a groupThey lose every privilege that came only through that group.
Compare

The principal types

User

A person. Named by email. Use for individual work, but prefer granting through groups.

Group

A set of principals. Account groups only for Unity Catalog. The normal target of grants.

Service principal

A robot identity for jobs and pipelines. Named by application ID. Keeps automation independent of people.

Don't confuse these

Principal traps

users vs account users

users is workspace-local and unusable for Unity Catalog. account users works.

SP name

A service principal is named by its application ID, not its display name.

Backticks

Needed for emails and hyphenated names.

Groups first

Grant to groups; manage people through membership.

Check yourself

Quiz

1. Which principal should a scheduled production job run as?

Service principals are made for automation and do not leave the company.

2. Which group cannot be granted Unity Catalog privileges?

Workspace-local groups are legacy and only exist in one workspace.

3. How is a service principal named in a GRANT statement?

The application ID uniquely identifies it.

4. In the demo, after removing sam from bakery-analysts, could sam still read the table?

Access through the group goes with membership; a direct grant stays.

Wrap up

Key takeaways

  • Principals: users (email), groups (name), service principals (application ID).
  • Only account groups, including account users, can hold Unity Catalog grants.
  • Grant to groups; run automation as service principals.
  • Use backticks for names with special characters.
