The idea

Everything that can be protected has a place in one tree

In Unity Catalog, anything you can give permissions on is called a securable object, or securable for short. A table is a securable. So is a schema, a catalog and a volume.

All securables hang from one tree. At the top is the metastore. You already know one branch: catalog, then schema, then tables, views, volumes and functions.

There is a second set of branches that beginners often miss. These objects sit directly under the metastore, beside the catalogs, and they describe how Databricks reaches the outside world:

  • A storage credential holds the cloud login that lets Databricks into a storage bucket.
  • An external location pairs one storage path with a storage credential. It says "this folder in the cloud may be used, with that login".
  • A connection holds the details for reaching another database system.
  • A share is a bundle of data offered to another organisation.

Unity Catalog does three jobs with this tree: it controls access, it records who did what (the audit trail), and it tracks where data came from (lineage).

Everyday analogy

A hospital's records office. Patient files are arranged by department, then ward, then patient: that is catalog, schema, table. But the office also keeps the keys to the archive rooms (storage credentials), a list of which rooms it may use (external locations), a visitors' book of everyone who opened a file (audit), and notes showing which report was built from which test results (lineage). The files matter most, but the office could not work without the rest.

How it works

The full tree

The green dot shows the purpose of the right-hand branch: it is how Unity Catalog is allowed to reach the storage that holds the data on the left.

Managed or external: who looks after the files?

Every table is one of two kinds. Module 07 covers them fully. You need the outline now.

  • A managed table lets Unity Catalog decide where the files go and look after them. Drop the table and the files are removed too. This is the default and the recommended kind.
  • An external table points at files in a path that you chose. Drop the table and Unity Catalog forgets it, but the files stay.

Where do the files of a managed table go?

Unity Catalog needs a place to put them, called a managed storage location. One can be set at three levels. When a table is created, Unity Catalog looks from the bottom up and uses the first one it finds:

  1. the schema's location, if the schema has one,
  2. otherwise the catalog's location,
  3. otherwise the metastore's location.

The more specific level wins. Databricks recommends setting it at catalog level, so each catalog's data is kept apart. A metastore-level location is optional, and newer workspaces may be created without one.

Code

Exploring the tree with SQL

-- Walk down the tree.
SHOW CATALOGS;
SHOW SCHEMAS IN bakery;
SHOW TABLES IN bakery.silver;
SHOW VOLUMES IN bakery.landing;

-- Everything about one table: columns, owner, type (MANAGED or EXTERNAL), storage location.
DESCRIBE TABLE EXTENDED bakery.silver.orders;

-- A new catalog that keeps its managed data in its own storage path.
-- The path must lie inside an external location that already exists.
CREATE CATALOG IF NOT EXISTS bakery
  MANAGED LOCATION 's3://bakery-lakehouse/managed/';

CREATE SCHEMA IF NOT EXISTS bakery.silver
  COMMENT 'Cleaned, deduplicated data';

Every catalog also contains a ready-made schema called information_schema. It holds tables that describe the catalog itself, so you can query the structure with plain SQL.

-- List every table in the bakery catalog, with its kind.
SELECT table_schema, table_name, table_type
FROM bakery.information_schema.tables
WHERE table_schema <> 'information_schema'
ORDER BY table_schema, table_name;

There is also a built-in catalog named system, present in every metastore. Its tables record how the platform is used. An administrator must give you access before you can read them.

-- Who touched data recently? (audit trail)
SELECT event_time, user_identity.email, action_name
FROM system.access.audit
WHERE event_date = current_date()
LIMIT 20;

-- Which tables were built from bakery.silver.orders? (lineage)
SELECT DISTINCT target_table_full_name
FROM system.access.table_lineage
WHERE source_table_full_name = 'bakery.silver.orders';
What if I change this?

Choices in the object model

ChangeEffect
Give a schema its own managed locationNew managed tables in that schema go there, not to the catalog's location. Tables that already exist do not move.
Set no managed location at any levelA managed table has nowhere to go, so it cannot be created. Someone must set a location first.
Drop a managed tableThe table's files are removed as well, after a retention period (Module 07 has the details).
Drop an external tableOnly the entry in Unity Catalog goes. The files stay in your storage path.
Attach a second workspace to the same metastoreIt sees the same catalogs, subject to permissions. Data is shared without copying.
Leave out the catalog in a nameThe current catalog is used. In unattended jobs, write all three parts so the meaning cannot shift.

Three things Unity Catalog gives you beyond names

Access control

One set of permissions, defined once, applied in every workspace attached to the metastore.

Audit

A record of who accessed or changed what and when, readable in system tables.

Lineage

An automatic record of which tables and columns were used to build which others.

Three special names you will run into

information_schema

A schema inside every catalog that describes that catalog's own tables, columns and privileges.

system

A catalog in every metastore holding usage records: audit, lineage, billing and more.

hive_metastore

A catalog that shows tables from the older, pre-Unity Catalog system. It is legacy. New work belongs in Unity Catalog.

Don't confuse these

Object model traps

Storage credential vs external location

The credential is the key. The external location is the statement "this key opens that path". You need both to reach storage outside the managed area.

Managed vs external

Managed: Unity Catalog owns the files, and dropping the table removes them. External: you own the files, and dropping the table leaves them.

Metastore vs workspace

A metastore serves a region and can be shared by many workspaces. A workspace is attached to only one metastore.

information_schema vs system

information_schema describes the structure of one catalog. system records activity across the whole account.

Check yourself

Quiz

1. A catalog and one of its schemas both have a managed storage location. Where do the files of a new managed table in that schema go?

Unity Catalog looks from the bottom up and takes the first location it finds. The most specific level wins.

2. Which objects sit directly under the metastore, not inside a catalog?

Objects that govern access to outside storage and systems hang from the metastore. Data objects always live in a schema inside a catalog.

3. You drop an external table. What happens to its data files?

For an external table Unity Catalog only keeps a pointer. Dropping the table removes the pointer, not the files.

4. Where would you look to find which tables are built from bakery.silver.orders?

Lineage records the flow of data from table to table. DESCRIBE HISTORY shows changes to one table only.

5. How many metastores can one workspace be attached to?

Each workspace is assigned to a single metastore. It works the other way round for sharing: one metastore can serve many workspaces.

Wrap up

Key takeaways

  • Everything you can grant on is a securable object in one tree under the metastore.
  • Data objects live at catalog, schema, object. Credentials, external locations, connections and shares sit under the metastore.
  • Managed tables are looked after by Unity Catalog. External tables point at files you look after.
  • Managed storage location is resolved schema first, then catalog, then metastore.
  • Unity Catalog also provides audit records and automatic lineage.
