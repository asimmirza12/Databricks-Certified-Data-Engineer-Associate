The idea

Every change is one numbered entry, and entries cannot collide

The transaction log is a folder called _delta_log that sits next to the table's data files. Each change to the table adds one small file to it. That file is called a commit. Commits are numbered 0, 1, 2 and so on, and the number is the table's version.

A commit is a short list of actions. The two that matter most are:

  • add: "this data file is now part of the table".
  • remove: "this data file is no longer part of the table".

To find the current table, a reader starts from nothing and replays the commits in order. Whatever files have been added and not removed are the table.

The clever part is the rule for writing a commit: only one writer can create commit number N. If two writers both try to write commit 7, exactly one succeeds. The other must look at what changed and try again as commit 8. That single rule is what gives Delta its safety.

Everyday analogy

A numbered ticket roll at a deli counter. There is only one ticket 7. Two customers can reach for the roll together, but only one hand comes away with 7. The other gets 8. Nobody is served twice and nobody is skipped. The ticket roll is the log, and taking a ticket is committing.

How it works

Inside the _delta_log folder

Commit file names are the version number padded with zeros to 20 digits, ending in .json.

Replaying thousands of commits would be slow. So every so often Delta writes a checkpoint: one Parquet file that sums up the whole state of the table at that version. How often is controlled by the table property delta.checkpointInterval. The default differs between open-source Delta and Databricks runtime versions, so verify in the docs before quoting a number.

Two writers at once

Delta does not lock the table while someone writes. Instead it uses optimistic concurrency control. "Optimistic" means it assumes writers will rarely clash, lets them all work, and only checks at the last moment:

  1. Read. The writer notes the current version, say 6.
  2. Write. It writes its new data files. Nobody can see them yet.
  3. Check and commit. It tries to create commit 7. If commit 7 already exists, it reads what that other commit did. If the two changes do not touch the same data, it commits as 8. If they do, it fails with a conflict error and the work must be run again.

ACID, explained by the log

Atomicity

A commit file either exists or it does not. There is no half-written change.

Consistency

Every write is checked against the table's schema and rules before it may commit.

Isolation

A reader picks one version and sees only that. A commit that lands mid-query does not change its answer.

Durability

Commits and data files are objects in cloud storage, which survives any machine failing.

Code

Looking at history, and changing data safely

-- One row per commit: version, timestamp, user, operation and its details.
DESCRIBE HISTORY bakery.silver.orders;

-- Facts about the table as it is now: format, storage location, number of files, size.
DESCRIBE DETAIL bakery.silver.orders;

-- Time travel by version number or by time.
SELECT * FROM bakery.silver.orders VERSION AS OF 12;
SELECT * FROM bakery.silver.orders TIMESTAMP AS OF '2026-11-15';

-- What changed between two versions? Compare them like any two tables.
SELECT * FROM bakery.silver.orders VERSION AS OF 12
EXCEPT
SELECT * FROM bakery.silver.orders VERSION AS OF 11;

-- Put the table back to how it was. This is itself a new commit.
RESTORE TABLE bakery.silver.orders TO VERSION AS OF 11;

One statement deserves special attention. MERGE updates rows that already exist and inserts rows that do not, in a single commit. This "update or insert" is often called an upsert.

-- Apply today's corrections: change existing orders, add new ones. One atomic commit.
MERGE INTO bakery.silver.orders AS target
USING bakery.bronze.order_corrections AS source
ON target.order_id = source.order_id
WHEN MATCHED THEN UPDATE SET target.price = source.price
WHEN NOT MATCHED THEN INSERT (order_id, shop, price)
                       VALUES (source.order_id, source.shop, source.price);

And in Python, letting a new column into the table on purpose:

# By default a DataFrame with an extra column is refused (schema enforcement).

(orders_with_loyalty.write

What if I change this?

Schema, history and housekeeping

ChangeEffect
Append a DataFrame with an extra column, no optionsRefused. Schema enforcement protects the table from accidental changes.
The same append with .option("mergeSchema", "true")Accepted. The table gains the new column, and older rows show NULL in it. This is schema evolution. The option works on DataFrame writes, not on a plain SQL INSERT INTO.
Run RESTORE to an old versionThe table's current state matches the old version again. History is not erased: the restore appears as a new commit on top.
Run OPTIMIZE on a table made of many small filesSmall files are rewritten into fewer large ones, so reads are faster. The old small files stay on disk until VACUUM removes them.
Two jobs update the same rows at the same timeThe first to commit wins. The second gets a conflict error and must be run again. Nothing is half-applied.
Two jobs only insert new rows at the same timeBoth succeed. Inserts add new files and do not disturb each other.

What a commit can contain

add / remove

Which data files join or leave the table. Each "add" also carries simple statistics about the file, such as the smallest and largest value in each column.

metaData

The table's schema and properties. A schema change is recorded here.

commitInfo

Who did it, when, and with which operation. DESCRIBE HISTORY shows this.

Don't confuse these

Delta details that get tested

Checkpoint vs checkpoint

A Delta log checkpoint is a summary file inside _delta_log. A streaming checkpoint (lesson 00-04) is a stream's bookmark. Unrelated things with one name.

Schema enforcement vs evolution

Enforcement is the default: mismatched writes fail. Evolution is opt-in: you allow the table's schema to grow.

RESTORE vs time travel

Time travel reads an old version and changes nothing. RESTORE makes the old version the current one for everybody.

Optimistic vs locking

Delta does not lock a table while writing. Writers work in parallel and conflicts are caught at commit time.

Check yourself

Quiz

1. What does one commit file in _delta_log record?

Commits are small. They describe what changed, not the data itself. Permissions belong to Unity Catalog, not to the log.

2. In the demo, Ana and Raj both updated North prices. What happened to the second one to commit?

Both rewrote the same data. The second writer's work was based on a version that no longer existed, so it was rejected instead of quietly losing the first writer's change.

3. Why does Delta write checkpoint files in the log?

A log checkpoint sums up the table state so far. It is not a backup and it is not the streaming kind of checkpoint.

4. An append fails because the incoming data has one new column. Which option lets the write through and adds the column?

mergeSchema turns on schema evolution for that write. Overwrite mode would replace the data, which is not what was asked.

5. After RESTORE TABLE ... TO VERSION AS OF 11 on a table at version 14, what is the table's version?

A restore is recorded as a new commit. The content matches version 11, but the version number moves forward.

Wrap up

Key takeaways

  • Each change is one numbered commit file in _delta_log, listing files added and removed.
  • Only one writer can create a given commit number. That rule gives atomic, isolated writes.
  • Writers do not lock the table. Conflicts are detected at commit time.
  • Schema enforcement is the default. mergeSchema opts in to schema evolution.
  • DESCRIBE HISTORY shows every commit. RESTORE rolls back by adding a new one.
