The idea

Three questions, in order

A workload is simply a piece of work that needs compute: a dashboard, a nightly job, an afternoon of exploring data. To choose compute for one, ask three questions.

  1. Is it SQL for dashboards, reports or analysis? Then use a SQL warehouse, and prefer the serverless type.
  2. If not: does a person run it by hand, or does a schedule run it? By hand means interactive. By schedule means a job.
  3. Does it need something serverless cannot do? For example R, the RDD API, or special machine and Spark settings. If not, use serverless. If so, use classic compute: all-purpose for interactive work, jobs compute for scheduled work.

Notice the default. Databricks recommends serverless first, and classic compute only when there is a reason. And notice what never appears as an answer: all-purpose compute for scheduled work.

Everyday analogy

Choosing a tool from a toolbox. You do not start by admiring every tool. You ask what the job is. Hanging a picture? Hammer. If the wall is concrete, the hammer will not do, so you fetch the drill. The drill is not "better". It is what you use when the simple tool hits a limit. Serverless is the hammer. Classic compute is the drill.

How it works

The decision path

Most workloads end at one of the two shaded serverless boxes. The classic box is for the exceptions.

Reasons to leave serverless

A language or interface it lacks

R, Scala in notebooks, or code written against the RDD API.

Settings you must control

A particular machine type such as one with a GPU, a specific runtime version, or Spark settings that serverless does not let you change.

A rule about where data is processed

Company policy may require processing inside your own cloud account and network. That means the classic compute plane.

It is not available

Serverless is not offered in every region or enabled in every workspace.

How the choice shows up in a job definition

In a job, each task says which compute it runs on. Here is one job with two tasks that made different choices. Module 04 and Module 05 explain job files properly. For now, look only at the compute lines.

name: bakery_nightly

# Classic jobs compute, defined once and created fresh for each run.
job_clusters:
  - job_cluster_key: r_cluster
    new_cluster:
      spark_version: "16.4.x-scala2.12"
      node_type_id: "m5.xlarge"
      num_workers: 2
      data_security_mode: "SINGLE_USER"   # the setting behind Dedicated access mode

tasks:
  # No compute named: where serverless is enabled, this notebook task runs on serverless.
  - task_key: load_orders
    notebook_task:
      notebook_path: /Workspace/bakery/load_orders

  # This task runs an R notebook, which serverless cannot do, so it names the classic cluster.
  - task_key: forecast_in_r
    depends_on:
      - task_key: load_orders
    job_cluster_key: r_cluster
    notebook_task:
      notebook_path: /Workspace/bakery/forecast

Field names and allowed values change between releases. Check them in the jobs compute documentation before copying. The point to remember is the pattern: serverless by default, classic jobs compute for the task that needs it, and no all-purpose compute anywhere.

For SQL work, the choice is made by picking a warehouse. A dashboard or a SQL task simply names the SQL warehouse it should use.

What if I change this?

How one detail changes the answer

ChangeEffect
A Python notebook job becomes an R notebook jobServerless is ruled out. The answer moves to classic jobs compute with Dedicated access mode.
A hand-run notebook is put on a scheduleThe answer moves from interactive compute to job compute: serverless jobs, or classic jobs compute. Never keep it on all-purpose.
A Python job is rewritten as pure SQL feeding a dashboardA SQL warehouse becomes the natural home.
Policy now says "process only in our cloud account"Every serverless answer becomes a classic one. For SQL, that means a pro SQL warehouse.
The job only runs for 90 seconds every few minutesStart-up time dominates on classic compute. Serverless becomes the clear choice if nothing rules it out.
Several analysts must share one interactive clusterClassic all-purpose compute with Standard access mode, which isolates users from one another.

What you are balancing

Simplicity

Serverless needs no sizing, no patching and no waiting. Fewer things to get wrong.

Control

Classic compute lets you choose machines, versions and settings. More power, more to manage.

Cost

Match the lifetime of the compute to the lifetime of the work. Idle compute is the most common waste.

Don't confuse these

Wrong answers that look right

"It already exists, so use it"

An all-purpose cluster that happens to be running is tempting for a scheduled job. It is the wrong answer on cost and on design.

SQL warehouse for everything SQL-ish

A SQL warehouse runs SQL only. A notebook that mixes SQL cells with Python cells needs serverless or classic compute.

Serverless is always cheapest

Usually simplest, often cheapest for short or bursty work. Not automatically cheapest for long, steady, heavy jobs. Compare total cost.

Classic is the safe default

It was once. Current guidance is the reverse: start with serverless and move to classic only for a stated reason.

Check yourself

Quiz

1. A team needs compute for business dashboards used by many people through the day. What fits best?

Dashboards are SQL workloads, and SQL warehouses are built for them. The serverless type starts fast and scales quickly as users arrive.

2. A Python notebook must run every night with no special requirements. Which is the recommended choice?

Scheduled, not SQL-only, nothing that serverless lacks. All-purpose compute is never the right home for scheduled work, and a SQL warehouse cannot run Python.

3. The same nightly job is rewritten in R. What changes?

Serverless does not support R. For scheduled work the classic option is jobs compute, with Dedicated access mode for R.

4. Why should a scheduled job not run on all-purpose compute?

It would work, which is what makes it a trap. It simply costs more and is not optimised for automated workloads.

5. In the demo, what was recommended for SQL dashboards when processing had to stay inside the company's own cloud account?

Pro and classic SQL warehouses run in your cloud account. The serverless type runs in the Databricks account, so the policy rules it out.

Wrap up

Key takeaways

  • SQL for reports and dashboards: a SQL warehouse, serverless type first.
  • Everything else: serverless first, for both interactive and scheduled work.
  • Go classic only for a reason: R, RDDs, special machines or settings, policy, or availability.
  • Classic by hand is all-purpose compute. Classic on a schedule is jobs compute.
  • Never run scheduled work on all-purpose compute.
