Compute types: all-purpose, jobs, SQL warehouses, serverless

Databricks offers several kinds of compute. They all run your code, but each is built for a different way of working. This lesson is the tour.

01-01 Platform architecture
The idea

Two questions sort every kind of compute

Compute is the set of machines that runs your code. To place any compute type, ask two things.

1. Who sets it up?

  • Classic compute: you choose the machine size, the number of workers and the software version. The machines run in your cloud account and take minutes to start.
  • Serverless compute: Databricks chooses everything. The machines run in the Databricks account and are ready in seconds.

2. What is it for?

  • All-purpose compute is for people working by hand in notebooks. It stays on between commands so you do not wait each time.
  • Jobs compute is for scheduled work. It is created when a job run starts and removed when the run ends.
  • A SQL warehouse runs SQL only. It serves the SQL editor, dashboards and reporting tools.

Put the answers together and you get the full menu: serverless compute for notebooks, jobs and pipelines; classic all-purpose compute; classic jobs compute; and SQL warehouses, which come in serverless, pro and classic types.

Everyday analogy

Getting around a city. All-purpose compute is your own car: always ready outside, set up how you like it, and costing you money even while parked. Jobs compute is a hired van for one delivery: it turns up, does the trip and goes. A SQL warehouse is a bus on a fixed route: it only goes one way (SQL), but it carries many passengers at once. Serverless is a taxi: there in seconds, nothing to maintain, and you pay only while riding.

How it works

When is each one switched on?

Filled blocks are time the compute is on. The moving line is the clock. All-purpose compute keeps running after the person stops, until its idle timer switches it off.

Settings you meet on classic compute

Databricks Runtime

The Databricks Runtime is the bundle of software on the machines: a version of Spark plus libraries. You pick a version. Those marked LTS (long-term support) are maintained for longer.

Access mode

The access mode decides who can use the compute. Standard (formerly Shared) lets several users share it safely. Dedicated (formerly Single user) is assigned to one user or one group.

Autoscaling

You give a smallest and largest number of workers. Databricks adds workers when the load rises and removes them when it falls.

Auto termination

The compute switches itself off after a set time with no activity. You can set it between 10 and 10,000 minutes, or turn it off.

Photon

Photon is a faster engine for running SQL and DataFrame code. It is a tick-box on classic compute and is on by default in current runtime versions.

Pools

A pool keeps a few machines waiting, idle and ready, so classic compute that draws from it starts faster.

What classic compute settings look like

You normally create compute by filling in a form. Behind the form is a short description like the one below. You will meet this shape again in Module 05, where compute is defined in files.

# A classic jobs compute definition for the nightly bakery load.
# Illustrative values: machine type names differ on each cloud.
new_cluster:
  spark_version: "16.4.x-scala2.12"     # which Databricks Runtime to install
  node_type_id: "m5.xlarge"              # size of each machine (an AWS example)
  autoscale:
    min_workers: 2                      # never fewer than 2 workers
    max_workers: 6                      # never more than 6
  data_security_mode: "USER_ISOLATION"  # the setting behind Standard access mode
  runtime_engine: "PHOTON"              # use the Photon engine

Check the exact field names and allowed values in the compute configuration reference before using them. For serverless compute there is nothing like this to write, which is the point of it.

From inside a notebook you can see what you are running on:

# The Spark version of the compute this notebook is attached to.
print(spark.version)
What if I change this?

Turning the dials

ChangeEffect
Standard access mode to DedicatedOnly one user or one group can use the compute. In return, things Standard mode does not allow become available, such as R and the RDD API.
Fixed size to autoscalingThe number of workers follows the load between your minimum and maximum. Quiet periods cost less. Sudden bursts wait a little while workers are added.
Turn off auto termination on all-purpose computeIt runs until someone stops it by hand. Forgetting is expensive.
Attach classic compute to a poolStart-up is faster because machines are already waiting. The waiting machines still cost cloud provider charges.
Classic SQL warehouse to serverless SQL warehouseStart-up drops from a few minutes to a few seconds, and it scales up and down more quickly.
Pick a non-LTS runtime versionYou get newer features sooner, and must upgrade sooner because support ends earlier.

Three types of SQL warehouse

Serverless

Starts in seconds, scales quickly, has every performance feature. The recommended type and the default in the UI where available.

Pro

Runs in your cloud account and takes a few minutes to start. Used where serverless is not available or special networking is needed.

Classic

Also in your account. Entry-level performance with the fewest features.

Don't confuse these

Compute names that blur together

All-purpose vs jobs compute

All-purpose is interactive and long-lived. Jobs compute is automated and lives for one run. Both are classic.

Standard vs Dedicated

Standard (formerly Shared) is for many users. Dedicated (formerly Single user) is for one user or group and allows more. Exam questions may use either the old or the new names.

Serverless vs serverless SQL warehouse

"Serverless compute" for notebooks and jobs runs Python and SQL. A "serverless SQL warehouse" is a SQL warehouse type and runs SQL only.

Classic compute vs classic SQL warehouse

"Classic compute" means any compute in your own account. "Classic" is also the name of the most basic SQL warehouse type.

Check yourself

Quiz

1. Which compute is created when a job run starts and removed when it ends?

Jobs compute exists for the length of one run. All-purpose compute and SQL warehouses stay up until they are stopped or have been idle long enough.

2. What can a SQL warehouse run?

SQL warehouses are specialised for SQL. Python, Scala and R need other compute.

3. What is the current name for the access mode formerly called "Single user"?

Single user became Dedicated, and it can now be assigned to a group as well as one user. Shared became Standard.

4. In the demo, which work could serverless compute for notebooks not run?

Serverless handles Python and SQL, interactive or scheduled. R is not supported there.

5. Roughly how long does a serverless SQL warehouse take to start, compared with a pro one?

Fast start-up is the headline benefit of serverless. Pro and classic warehouses must first start machines in your account.

Wrap up

Key takeaways

  • Classic compute: you configure it, it runs in your account, it starts in minutes.
  • Serverless compute: Databricks runs it, it starts in seconds, it has fewer settings and some limits.
  • All-purpose is for people. Jobs compute is for scheduled runs. SQL warehouses are for SQL.
  • Standard access mode is for sharing. Dedicated is for one user or group and allows more.
  • SQL warehouses come as serverless, pro and classic.
