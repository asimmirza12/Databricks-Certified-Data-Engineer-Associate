Joins: inner and left

Useful answers usually need two tables at once: the orders and the shops they came from. A join puts them side by side. The kind of join decides what happens to rows that have no partner.

The idea

Match rows on a shared value

A join combines two tables sideways. For each row in the first table, it looks for rows in the second table that share a value in a chosen column, and glues the matching rows together into one wider row.

The shared column is called the join key. If orders have a shop_id and shops have a shop_id, that is the key.

The two tables are called left and right, simply by the order you write them. The different kinds of join differ in one thing only: what to do with a row that finds no match.

  • An inner join keeps only rows that found a match. Unmatched rows from either side disappear.
  • A left join keeps every row from the left table. Where there is no match on the right, the right-hand columns are filled with NULL.

Those two are by far the most used. Their relatives follow the same logic: a right join keeps everything from the right, and a full join keeps everything from both.

Everyday analogy

Matching party invitations to replies. You have a list of people invited and a pile of reply cards. An inner join gives you only the guests who replied: invitation and reply together. A left join, starting from the invitations, gives you everyone you invited, with the reply beside their name if there is one and a blank if not. That blank is exactly how you spot who has not answered.

How it works

Which rows survive

One row can match many

A join does not promise one output row per input row. If a key value appears twice on the right, each matching left row is output twice. If it appears twice on both sides, you get four rows. This is the commonest cause of numbers that are mysteriously too high after a join.

Before joining, ask: is the key unique in the table I am looking things up in? A shops table should have one row per shop. If it has two rows for North, every North order is counted twice.

Code

Writing joins

orders = spark.table("bakery.silver.orders")     # order_id, shop_id, price
shops  = spark.table("bakery.silver.shops")      # shop_id, shop_name, city

# INNER: only orders whose shop is known. "inner" is the default if you leave it out.
known = orders.join(shops, on="shop_id", how="inner")

# LEFT: every order. shop_name and city are NULL where the shop is unknown.
all_orders = orders.join(shops, on="shop_id", how="left")

# When the key columns have different names, spell out the condition.
all_orders = orders.join(shops, orders.shop_id == shops.id, "left")

# A quick data check: which orders point at a shop that does not exist?
orphans = orders.join(shops, on="shop_id", how="left_anti")
-- The same in SQL.
SELECT o.order_id, o.price, s.shop_name
FROM bakery.silver.orders AS o
INNER JOIN bakery.silver.shops AS s
  ON o.shop_id = s.shop_id;

SELECT o.order_id, o.price, s.shop_name
FROM bakery.silver.orders AS o
LEFT JOIN bakery.silver.shops AS s
  ON o.shop_id = s.shop_id;

-- Check that the lookup key really is unique before trusting a join.
SELECT shop_id, COUNT(*) AS n
FROM bakery.silver.shops
GROUP BY shop_id
HAVING COUNT(*) > 1;

Joining with on="shop_id" gives one shop_id column in the result. Joining with a condition such as orders.shop_id == shops.shop_id keeps both, and you then have two columns with the same name to sort out.

how="inner", or nothingOnly rows with a match on both sides. Unmatched rows are dropped without warning.
how="left"Every left row is kept. Right-hand columns are NULL where there was no match.
how="right"The mirror image: every right row is kept.
how="full"Every row from both sides, with NULLs wherever one side had no partner.

Don't confuse these

Join traps

Inner vs left

Inner loses unmatched rows. Left keeps all left rows. If a question says "without losing any orders", the answer is a left join from orders.

Left anti vs left join with a filter

left_anti and "left join, then keep rows where the right key is NULL" give the same rows. The anti join says it directly.

Join vs union

A join adds columns by matching rows. A union stacks rows on top of each other (lesson 03-06).

More rows after a join

Not a bug in Spark. It means a key was not unique. Every match produces a row.

Check yourself

Quiz

1. Orders has 100 rows. Five of them have a shop_id that is not in shops. How many rows does an inner join return, if shop IDs are unique in shops?

An inner join keeps only matched rows, so the five orphans are dropped.

2. The same two tables with a left join from orders. How many rows?

Every left row is kept. The five orphans have NULL in the shop columns.

3. Which join type lists the orders that have no matching shop?

An anti join returns left rows that found no partner. A semi join returns the ones that did.

4. In the demo, what happened to the result when the shops table held North twice?

Each order matched two shop rows, so it was output twice. Spark raises no error for this.

5. In PySpark, what is the default join type if how is left out?

The default is inner, which is why unmatched rows can vanish unnoticed.

Wrap up

Key takeaways

  • A join matches rows from two tables on a key and puts them side by side.
  • Inner keeps only matches. Left keeps every left row, with NULLs where there is no match.
  • Inner is the default, and it drops unmatched rows silently.
  • A key that is not unique multiplies rows and inflates totals.
  • Use left_anti to find rows with no partner.
