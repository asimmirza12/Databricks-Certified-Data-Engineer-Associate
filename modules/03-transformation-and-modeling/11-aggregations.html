Aggregations: count, approx_count_distinct, mean, summary

Nobody reads a million rows. They read "total sales by shop". Aggregation is how many rows become a few numbers, and it is the heart of every gold table.

The idea

Many rows in, one number out

To aggregate is to boil many rows down into one summary value. Count them. Add up a column. Find the average, the smallest, the largest.

On its own, an aggregate turns a whole table into a single row. More often you want one summary per something: per shop, per day, per item. That is grouping. You name a column to group by. Spark sorts the rows into piles that share a value in that column, and works out the aggregates for each pile. The result has one row per pile.

The exam names four aggregates in particular:

  • count: how many rows.
  • approx_count_distinct: roughly how many different values a column has. It gives up a little accuracy to be much faster on big data.
  • mean (also called avg): the average.
  • summary: not one number but a ready-made table of statistics for every numeric column, handy for a first look at data.
Everyday analogy

Counting the day's takings. You tip the till onto the table. Counting every coin as one heap gives a single total. Sorting coins into piles by type first, then counting each pile, gives a total per type. Sorting into piles is the grouping. Counting each pile is the aggregate. And if someone only asks "roughly how many different kinds of coin are there?", a glance is quicker than an exact inventory.

How it works

Sort into groups, then summarise each

One output row per group. Grouping needs a shuffle, because rows of the same shop must be brought together.

Counting has three meanings

  • count(*) counts rows, whatever is in them.
  • count(price) counts rows where price is not NULL.
  • count(DISTINCT customer) counts how many different customers there are.

The third is expensive on large data, because Spark has to remember every distinct value it has seen. approx_count_distinct replaces that memory with a clever small sketch. The answer is an estimate, by default within about 5% of the truth, and it is produced far more quickly.

Code

Aggregating in both languages

from pyspark.sql import functions as F

orders = spark.table("bakery.silver.orders")

# The whole table as one row.
orders.agg(F.count("*").alias("orders"), F.mean("price").alias("avg_price"))

# One row per shop, with several aggregates.
by_shop = (orders
    .groupBy("shop")
    .agg(
        F.count("*").alias("orders"),                               # rows
        F.count("price").alias("priced_orders"),                    # rows with a price
        F.countDistinct("customer_id").alias("customers"),          # exact, slower
        F.approx_count_distinct("customer_id").alias("customers_est"),  # estimate, faster
        F.sum("price").alias("total_sales"),
        F.mean("price").alias("avg_price"),
        F.min("price").alias("cheapest"),
        F.max("price").alias("dearest")))

# Keep only some groups: filter AFTER aggregating.
busy = by_shop.filter(F.col("orders") >= 100)

# A quick statistical look at every numeric column.
display(orders.summary())                         # count, mean, stddev, min, 25%, 50%, 75%, max
display(orders.select("price").summary("count", "mean", "max"))   # just the ones you name
display(orders.describe())                        # the shorter version: no percentiles
SELECT
  shop,
  COUNT(*)                           AS orders,
  COUNT(price)                       AS priced_orders,
  COUNT(DISTINCT customer_id)        AS customers,
  approx_count_distinct(customer_id) AS customers_est,
  SUM(price)                         AS total_sales,
  AVG(price)                         AS avg_price
FROM bakery.silver.orders
WHERE order_date >= '2026-11-01'       -- filters ROWS, before grouping
GROUP BY shop
HAVING COUNT(*) >= 100                 -- filters GROUPS, after aggregating
ORDER BY total_sales DESC;
What if I change this?

What each choice does

ChangeEffect
count("*") to count("price")Rows where price is NULL are no longer counted.
countDistinct to approx_count_distinctMuch less memory and time on large data. The answer may be a few per cent off.
approx_count_distinct("customer_id", 0.01)The second argument is the allowed error. Smaller means more accurate and more costly. The default is 0.05, about 5%.
Group by a column that contains NULLsThe NULLs form a group of their own, shown with NULL as its label.
Select a column that is neither grouped nor aggregatedAn error. Each output row stands for many input rows, so Spark cannot know which value to show.
Filter with WHERE instead of HAVINGWHERE removes rows before the totals are worked out. HAVING removes whole groups afterwards. They answer different questions.
mean of a column with NULLsNULLs are skipped. The average is over the rows that have a value.
summary() to describe()You lose the 25%, 50% and 75% values. describe gives count, mean, standard deviation, min and max only.
Group by many columns at onceOne row per combination that occurs. With enough columns you are barely summarising at all.

The everyday aggregates

count

How many. count(*) for rows, count(col) for non-NULL values.

sum / mean

The total and the average. Both skip NULLs. avg is another name for mean.

min / max

The smallest and largest. They also work on dates and text.

What summary() shows

For each numeric column: count of non-NULL values, mean, stddev (standard deviation, a measure of how spread out the values are), min, the 25%, 50% and 75% points (a quarter, half and three quarters of values lie below them; 50% is the median), and max.

Don't confuse these

Aggregate traps

count(*) vs count(col)

count(*) counts rows. count(col) skips rows where that column is NULL.

WHERE vs HAVING

WHERE filters rows before grouping. HAVING filters groups after it.

summary vs describe

Both give count, mean, stddev, min and max. Only summary adds the 25%, 50% and 75% values.

distinct vs count distinct

distinct() returns the different rows. countDistinct returns how many there are.

Check yourself

Quiz

1. A table has 10 rows and 2 of them have a NULL price. What do count(*) and count(price) return?

count(*) counts every row. count(price) counts only rows with a price.

2. When is approx_count_distinct the better choice?

It trades a little accuracy for a large saving in time and memory.

3. Which clause keeps only shops whose total sales exceed 1,000?

Conditions on aggregates go in HAVING, which runs after the groups are formed.

4. What does summary() give that describe() does not?

Both give count, mean, stddev, min and max. The percentiles are extra in summary.

5. In the demo, grouping by shop, why was North's count(price) lower than its count(*)?

A NULL price is a row, so it is counted by count(*), but it is not a value, so count(price) skips it.

Wrap up

Key takeaways

  • Aggregates reduce many rows to summary values. Grouping gives one result row per group.
  • count(*) counts rows. count(col) skips NULLs. Sums and means skip NULLs too.
  • approx_count_distinct estimates distinct values quickly, within about 5% by default.
  • WHERE filters rows before grouping. HAVING filters groups after.
  • summary() gives count, mean, stddev, min, quartiles and max for a first look.
