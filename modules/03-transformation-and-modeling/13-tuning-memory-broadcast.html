The idea

How much room, and when to broadcast

Spark runs on a driver and a number of executors (lesson 00-05). Each is a program with a fixed amount of working memory.

  • spark.executor.memory is how much memory each executor has. Executors hold the partitions they are working on. Too little, and big partitions must be written to disk and read back, or the task fails.
  • spark.driver.memory is how much the driver has. The driver holds the plan, results you pull back to it, and tables that are about to be broadcast. Too little, and collecting a large result or broadcasting a large table crashes it.

Running out of memory is called an out-of-memory error, often shortened to OOM.

The third setting is about joins:

  • spark.sql.autoBroadcastJoinThreshold is a size limit. If Spark estimates that one side of a join is smaller than this, it uses a broadcast join automatically. The default is 10 MB. Setting it to -1 turns automatic broadcasting off.

These three are linked. A broadcast table is first gathered on the driver, then copied to every executor. Raise the threshold, and bigger tables get broadcast, which needs more driver and executor memory. Tuning one without thinking of the others is how jobs start to fail.

Everyday analogy

Desks and handouts. Each worker has a desk (executor memory) and the manager has one too (driver memory). A rule says: "any reference sheet under ten pages gets photocopied for everyone" (the threshold). Raise it to "under a thousand pages" and suddenly the manager's desk is buried under a thousand-page original, and every worker's desk is buried under a copy. Either get bigger desks, or keep the rule sensible.

How it works

Where the memory is used

How you set memory on Databricks

The memory settings are fixed when compute starts. You cannot change them from a running notebook. And in practice you rarely type them at all. On Databricks you choose a machine type for the driver and for the workers, and Databricks sets the memory to suit that machine. Its advice is not to hard-code spark.executor.memory or spark.driver.memory, because that can undo its own tuning. To give Spark more memory, pick a larger machine type.

On serverless compute you cannot set them at all. Databricks sizes everything.

A second threshold

Spark's first size estimate is made before the query runs and can be wrong. Adaptive query execution (lesson 03-12) checks again while the query runs, using real sizes. On Databricks that run-time check has its own limit, 30 MB by default. So a join can be switched to a broadcast partway through, even if it was not planned as one.

Code

Reading, setting and checking

# The broadcast threshold can be read and changed in a running session.
print(spark.conf.get("spark.sql.autoBroadcastJoinThreshold"))     # 10485760b = 10 MB

spark.conf.set("spark.sql.autoBroadcastJoinThreshold", "100MB")  # broadcast tables up to 100 MB
spark.conf.set("spark.sql.autoBroadcastJoinThreshold", "-1")     # never broadcast automatically

# Memory can be READ in a session, but not changed. It was fixed when the compute started.
print(spark.conf.get("spark.executor.memory"))
print(spark.conf.get("spark.driver.memory"))

How do you know which join Spark chose? Ask for the plan. explain() prints it without running anything.

orders   = spark.table("bakery.silver.orders")
products = spark.table("bakery.silver.products")

joined = orders.join(products, on="product_id")
joined.explain()
# Look for one of these words in the output:
#   BroadcastHashJoin   -> a broadcast join
#   SortMergeJoin       -> a shuffle join
-- The same check in SQL.
EXPLAIN
SELECT * FROM bakery.silver.orders AS o
JOIN bakery.silver.products AS p ON o.product_id = p.product_id;

If memory really must be set by hand on classic compute, it goes in the compute's Spark configuration box before it starts, one setting per line:

spark.driver.memory 16g
spark.executor.memory 32g

Prefer choosing a bigger machine type to writing those two lines. And do the measuring loop from lesson 03-12 around any change you make here too.

What if I change this?

Each setting, up and down

ChangeEffect
Raise autoBroadcastJoinThreshold a little, so a 50 MB lookup table qualifiesThat join becomes a broadcast join and avoids shuffling the large table. Often a big speed-up.
Raise it to several gigabytesSpark tries to broadcast very large tables. The driver runs out of memory collecting them.
Set it to -1No automatic broadcast joins. Every join shuffles, unless you add a broadcast hint yourself.
Spark's size estimate for a table is wrongIt may broadcast something too big, or fail to broadcast something small. A hint (lesson 03-05) or the run-time check corrects it.
More executor memory, by choosing a larger worker machineBigger partitions fit without spilling to disk. Shuffles and aggregations get faster and more reliable.
More driver memory, by choosing a larger driver machineLarger results can be collected and larger tables broadcast without a crash.
Set spark.executor.memory with spark.conf.set in a notebookNo effect, or an error. It can only be set before the compute starts.
Fix a driver OOM by raising executor memoryNo help. They are separate. Find out which one ran out first.
Call collect() on a very large DataFrameAll rows are pulled to the driver. A common cause of driver OOM that no setting should be used to paper over.

Driver or executor: who ran out?

Driver OOM

Typical causes: collect() or toPandas() on a large result, or broadcasting a table that is too big. The whole job stops.

Executor OOM

Typical causes: partitions that are too large, or one key with far more rows than the rest (skew). A task fails and is retried.

Don't confuse these

Memory and broadcast traps

Driver vs executor memory

Separate settings for separate machines. Collecting and broadcasting stress the driver. Big partitions stress executors.

Threshold vs hint

The threshold lets Spark decide by size. A hint is you deciding for one particular join.

-1 does not mean unlimited

For the broadcast threshold, -1 means "off": never broadcast automatically.

Run-time vs start-up settings

Shuffle partitions and the broadcast threshold can change in a session. Memory and default parallelism cannot.

Check yourself

Quiz

1. What is the default value of spark.sql.autoBroadcastJoinThreshold?

Tables estimated to be under 10 MB are broadcast automatically. 200 is the default for shuffle partitions.

2. What does setting that threshold to -1 do?

-1 disables automatic broadcasting. A hint can still request one.

3. A notebook crashes when it calls collect() on a huge DataFrame. Which memory ran out?

collect() brings every row to the driver, which is a single machine.

4. How do you give executors more memory on Databricks classic compute, in the recommended way?

Memory is fixed at start-up and sized from the machine type. It cannot be changed in a running session.

5. In the demo, what happened when the threshold was raised to 10 GB with a 6 GB products table and an 8 GB driver?

The table qualified for broadcast under the new threshold, but was far too large for the driver to hold.

Wrap up

Key takeaways

  • Executor memory holds partitions being processed. Driver memory holds collected results and tables being broadcast.
  • On Databricks, memory follows the machine type. Pick a bigger machine instead of hard-coding it.
  • spark.sql.autoBroadcastJoinThreshold defaults to 10 MB. -1 switches automatic broadcasting off.
  • Raising the threshold helps with small tables and breaks things with large ones.
  • Use explain() to see which join was chosen, and always measure before and after.
