Tuning: shuffle partitions and default parallelism

Joins and group-bys make Spark move data between machines. How many pieces it cuts that data into is a setting you can change, and the right number makes the difference between a quick job and a painful one.

The idea

How many pieces after a shuffle?

Recall from lesson 00-05 that Spark works on data in chunks called partitions, one task per partition.

Some operations need related rows to be in the same place. To add up sales per shop, all of North's rows must meet. To join orders to customers, matching keys must meet. Spark achieves this by redistributing every row to a new partition chosen by its key. That redistribution is a shuffle.

After a shuffle the data sits in a fresh set of partitions. How many? That is decided by one setting:

spark.sql.shuffle.partitions: the number of partitions used after a shuffle in DataFrame and SQL work. Its default is 200.

200 is a fixed guess that knows nothing about your data. For a tiny table it is far too many: Spark creates 200 tasks to handle a handful of rows each, and spends longer organising than working. For a huge table it is far too few: each partition is enormous, does not fit in memory, and has to be written to disk partway through.

The second setting in the exam objective is a relative:

spark.default.parallelism: the default number of partitions for the older, low-level RDD interface. It does not control DataFrame or SQL shuffles.

Everyday analogy

Sorting post into pigeonholes. A sorting office must split the day's letters among a wall of pigeonholes. With 200 pigeonholes and 20 letters, clerks walk the length of the wall to place one letter each: lots of walking, little sorting. With 200 pigeonholes and 20 million letters, every hole overflows onto the floor. The right number of holes depends on how much post there is today.

How it works

Too few, about right, too many

Let Spark choose

Modern Spark has a feature called adaptive query execution, or AQE. It watches a query while it runs. After a shuffle it looks at how much data actually arrived and merges small partitions together, so a starting value of 200 no longer hurts small jobs so much.

Databricks goes one step further. If you set spark.sql.shuffle.partitions to the word auto, Spark picks the number itself from the size of the data. On serverless compute, auto is already the default. This is why the usual advice today is: do not hand-tune this number unless you have measured a problem.

The tuning loop

The objective says to "re-measure". Tuning is not guessing a better number. It is a loop:

  1. Measure the job as it is. Note the run time, and look at the shuffle in the Spark UI.
  2. Change one setting. Only one, or you will not know what made the difference.
  3. Measure again on the same data, and compare.
  4. Keep the change only if it helped.

Code

Reading and setting the values

# What is it now?
print(spark.conf.get("spark.sql.shuffle.partitions"))

# Change it for this session. It applies to shuffles that happen from now on.
spark.conf.set("spark.sql.shuffle.partitions", "64")

# On Databricks: let Spark choose from the size of the data.
spark.conf.set("spark.sql.shuffle.partitions", "auto")
-- The same from SQL.
SET spark.sql.shuffle.partitions;            -- show the current value
SET spark.sql.shuffle.partitions = auto;     -- change it

And the measuring half of the loop:

import time
from pyspark.sql import functions as F

def timed_run(label):
    start = time.time()
    (spark.table("bakery.silver.orders")
        .groupBy("shop", "order_date")          # this is the shuffle
        .agg(F.sum("price").alias("sales"))
        .write.mode("overwrite").saveAsTable("bakery.gold.daily_sales"))   # an action, so it really runs
    print(label, round(time.time() - start, 1), "seconds")

timed_run("baseline")                                          # 1. measure
spark.conf.set("spark.sql.shuffle.partitions", "auto")        # 2. change ONE thing
timed_run("after change")                                      # 3. measure again

spark.default.parallelism is different: it is fixed when the compute starts, in the compute's Spark configuration. You cannot change it from a running notebook, and it does not affect the DataFrame code above anyway.

What if I change this?

The setting and its side effects

ChangeEffect
Leave spark.sql.shuffle.partitions at 200 for a small tableUp to 200 tiny tasks. AQE usually merges them, which hides most of the cost.
Leave it at 200 for a very large shuffleEach partition is many gigabytes. Tasks run out of memory and spill to disk, or fail.
Raise it for a large shuffleSmaller partitions that fit in memory. Usually much faster.
Raise it far too highTens of thousands of tiny tasks. The driver spends its time scheduling them, and writing a table can create a flood of tiny files.
Set it to autoSpark sizes the shuffle from the data. The sensible default on Databricks, and the actual default on serverless.
Change spark.default.parallelism to speed up a DataFrame joinNo effect. That setting is for RDD operations.
Change the setting partway through a notebookOnly shuffles run afterwards use the new value.
Change two settings at once and re-measureYou cannot tell which change helped, or whether one helped and the other hurt.
Try to set other Spark settings on serverlessMost are not allowed there. Shuffle partitions is one of the few that is.

Signs that the number is wrong

Too few partitions

A few very long tasks. "Spill" figures in the Spark UI. Out-of-memory failures in a shuffle stage.

Too many partitions

Thousands of tasks that each take milliseconds. A long pause before stages start. Output tables made of very many small files.

Don't confuse these

Tuning traps

shuffle.partitions vs default.parallelism

The first is for DataFrames and SQL and can be changed at run time. The second is for RDDs and is fixed at start-up.

200 is a default, not a recommendation

It is a guess made without seeing your data. It is right only by accident.

Shuffle partitions vs table partitions

Shuffle partitions are temporary chunks during a query. Partitioning a table is a way of arranging its stored files. Unrelated.

More is not better

Both too few and too many are slow. The goal is partitions that comfortably fit in memory, and no smaller than that.

Check yourself

Quiz

1. What is the default value of spark.sql.shuffle.partitions on classic compute?

The default is 200. On serverless compute the default is auto.

2. Which setting controls the number of partitions after a DataFrame groupBy?

DataFrame and SQL shuffles use spark.sql.shuffle.partitions. default.parallelism is for RDDs.

3. A very large shuffle with too few partitions typically shows what?

Each partition is too big for memory, so tasks spill or fail. Thousands of tiny tasks is the sign of too many partitions.

4. In the demo, was the best partition count for 1 GB also the best for 500 GB?

A fixed number cannot suit every data size. auto chooses from the data.

5. What is the correct way to check whether a tuning change helped?

One change at a time, with a before and an after, is the only way to know what helped.

Wrap up

Key takeaways

  • A shuffle redistributes rows by key for joins, grouping and sorting.
  • spark.sql.shuffle.partitions sets the number of partitions afterwards. The default is 200.
  • Too few means huge partitions and spilling. Too many means overhead and tiny files.
  • On Databricks, auto lets Spark choose. It is the default on serverless.
  • spark.default.parallelism is for RDDs and does not affect DataFrame shuffles.
  • Tune in a loop: measure, change one thing, measure again.
