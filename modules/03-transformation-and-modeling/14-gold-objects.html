Gold objects: tables, views, materialized views, streaming tables

The gold layer is what people actually read. Four kinds of Unity Catalog object can hold it, and each stores data differently and refreshes differently. Choosing well is an exam favourite.

The idea

Four ways to hold the same answer

A gold object answers a business question, such as "sales by shop by day". Unity Catalog offers four kinds, and the difference is in two questions: does it store its own data? and how does it catch up when the source changes?

  • A view stores no data. It is a saved query. Every time someone reads it, the query runs against the current source.
  • A materialized view stores its results. It is refreshed to match the source, on a schedule or on demand, so reads are fast but can be a little behind.
  • A streaming table stores its results and processes each new source record once, as it arrives. It suits append-only sources such as new files or events.
  • A plain table stores whatever you write into it, by any method, and changes only when you change it.
Everyday analogy

Four ways to give someone the football score. A view is re-reading the match report every time someone asks: always current, but you pay the reading time each time. A materialized view is printing the scores on the noticeboard and reprinting at half time: quick to read, a little behind. A streaming table is a ticker that adds each goal the moment it happens and never adds the same goal twice. A plain table is a handwritten card you update when you feel like it.

How it works

Stored or computed, and how it catches up

On Databricks, the three that are declared with SQL are created with CREATE VIEW, CREATE MATERIALIZED VIEW and CREATE STREAMING TABLE. A plain table comes from CREATE TABLE or CREATE TABLE ... AS SELECT.

Code

Creating each kind

-- VIEW: a saved query. Nothing is stored; each read runs the query.
CREATE OR REPLACE VIEW bakery.gold.sales_by_shop_v AS
SELECT shop, SUM(price) AS total_sales
FROM bakery.silver.orders
GROUP BY shop;

-- MATERIALIZED VIEW: results are stored and refreshed to match the source.
CREATE OR REPLACE MATERIALIZED VIEW bakery.gold.sales_by_shop_mv AS
SELECT shop, SUM(price) AS total_sales
FROM bakery.silver.orders
GROUP BY shop;

-- Bring it up to date now. Standalone materialized views refresh on a serverless pipeline.
REFRESH MATERIALIZED VIEW bakery.gold.sales_by_shop_mv;

-- STREAMING TABLE: processes new rows of an append-only source, once each.
CREATE OR REFRESH STREAMING TABLE bakery.bronze.web_orders
AS SELECT * FROM STREAM read_files('/Volumes/bakery/landing/web_orders/', format => 'json');

-- PLAIN TABLE: whatever the statement writes, nothing more.
CREATE OR REPLACE TABLE bakery.gold.sales_by_shop_t AS
SELECT shop, SUM(price) AS total_sales
FROM bakery.silver.orders
GROUP BY shop;

The exam expects you to know the purpose of each, not every option. Check the syntax for your runtime in the docs; the pipeline-based forms are often written with the pipeline's own SQL dialect.

What if I change this?

Consequences of each choice

ChangeEffect
Replace a materialized view with a viewResults are always current, but every dashboard refresh re-runs the aggregation. Slower for busy BI.
Replace a view with a materialized viewReads are fast, but the results are only as fresh as the last refresh. Someone must schedule it.
Source rows are updated or deleted, and the gold object is a streaming tableStreaming tables assume append-only input. Changes to old rows are not reflected the way a materialized view would reflect them. Use a materialized view.
Source only ever receives new filesA streaming table is the efficient choice: each new file is processed once.
Use a plain table and forget to rebuild itIt silently goes stale. Nothing refreshes it for you.
Create a view on top of a view on top of a viewEach read runs the whole chain. Deep chains are slow and hard to change.
Refresh a materialized view on a schedule that is slower than the source changesUsers see yesterday's figures. Match the refresh schedule to how fresh BI users need the data.

Where each usually sits

Bronze

Streaming tables for arriving files and events.

Silver

Tables written by pipelines and jobs, cleaned and typed.

Gold

Materialized views for summaries. Views for simple shared logic. Plain tables where full control matters.

Metric views

A newer kind of object defines business measures, such as revenue or conversion rate, once, in one place, so every dashboard and report computes them the same way. It is built on top of gold tables or views, and it does not replace them.

Real life

Choosing a gold object

ScenarioWhat happensFix
Dashboards are slow because every page re-adds three years of ordersA view is doing the aggregation on each readMaterialized view refreshed on a schedule
Finance sees yesterday's total after a late correctionThe materialized view has not been refreshed since the correctionRefresh after corrections, or on a tighter schedule
A bronze feed of new event files is loaded into a materialized viewThe design re-reads all history on each refreshUse a streaming table for the append-only feed
Five gold reports all need the same "net sales" ruleEach copy of the rule can drift apartPut the rule in one view, or in a metric view, and build the reports on it
An analyst wants to try a new calculation without touching the team's tableA plain table would be changed for everyoneCreate a view for the experiment
Don't confuse these

Gold object traps

View vs materialized view

A view stores no data and is always current. A materialized view stores results and is current only as of its last refresh.

Streaming table vs materialized view

A streaming table processes new rows once. A materialized view recomputes results to match the source, including changes to old rows.

Table vs view

A plain table holds data. A view holds only a query. Dropping a view leaves the data it read from untouched.

Metric view vs view

A metric view holds business measures and their definitions. A view holds a query. Both are read with SQL.

Check yourself

Quiz

1. Which gold object stores no data of its own?

A view is a saved query. Each read runs it against the current source.

2. A dashboard needs fast reads of an aggregate that is refreshed nightly. Which object fits?

The results are stored and read quickly, and the nightly refresh keeps them up to date enough.

3. Which object is designed for new files arriving continuously, with each processed once?

Streaming tables process each new record of an append-only source exactly once.

4. In the demo, a new sale arrived. What did reading the view show straight away?

A view is always as current as its source at the moment it is read.

5. In the demo, why did the materialized view not show the new sale until it was refreshed?

A materialized view keeps stored results. They change when it is refreshed, not when the source changes.

Wrap up

Key takeaways

  • Gold objects differ in whether they store data and how they catch up with the source.
  • A view runs its query on every read. A materialized view stores results and refreshes.
  • A streaming table processes each new record of an append-only source once.
  • A plain table changes only when you write to it.
  • Summaries for BI are usually materialized views. Shared logic is often a view.
