Joins: multiple keys, cross join, broadcast join

Three more things about joins. Sometimes one column is not enough to match on. Sometimes you want every combination. And sometimes the way Spark performs the join matters more than the join itself.

The idea

Three separate ideas

Joining on multiple keys. One column does not always identify a row. A price list might have one row per item per shop, because the same loaf costs more in one shop than another. To find the right price for an order you must match on both the item and the shop. Match on the item alone and each order finds several prices.

Cross join. A cross join has no key at all. It pairs every row of one table with every row of the other. Three shops crossed with four dates gives twelve rows: every shop on every date. That is useful for building a complete grid. It is also dangerous: a thousand rows crossed with a thousand rows is a million.

Broadcast join. This is not a different result. It is a different way of doing a join, and it gives the same answer faster when one table is small.

Normally, to join two big tables, Spark must rearrange both so that rows with the same key end up on the same executor. That rearranging is called a shuffle, and moving data between machines is the slowest thing Spark does. But if one table is small, Spark can skip all of that. It sends a complete copy of the small table to every executor. Each executor then joins its share of the big table against its own local copy. Nothing in the big table has to move. Sending one thing to everyone is called broadcasting, so this is a broadcast join.

Everyday analogy

Marking exam papers with a price list. Ten markers each have a pile of order slips and need to look up prices. The slow way: gather all slips and all price cards into one hall and sort both by item so they can be paired. The fast way: photocopy the one-page price list and give a copy to each marker, who stays at their desk. That photocopy is the broadcast. It only works because the price list is small. You would not photocopy a telephone directory for everyone.

How it works

Shuffle join against broadcast join

Spark often chooses a broadcast join by itself, when it can see that one table is under a size limit (lesson 03-13). You can also ask for one with a hint: a note in your code that tells Spark which table to broadcast.

Code

Writing each kind

from pyspark.sql import functions as F

orders = spark.table("bakery.silver.orders")       # order_id, item, shop, qty
prices = spark.table("bakery.silver.prices")       # item, shop, price: one row per item per shop
shops  = spark.table("bakery.silver.shops")        # small: a handful of rows

# MULTIPLE KEYS: a list of column names. Both must match.
priced = orders.join(prices, on=["item", "shop"], how="left")

# The same with an explicit condition, joined by & ("and").
priced = orders.join(prices,
    (orders.item == prices.item) & (orders.shop == prices.shop), "left")

# CROSS JOIN: every shop paired with every date. Gives a complete grid.
dates = spark.sql("SELECT explode(sequence(DATE'2026-11-01', DATE'2026-11-30')) AS day")
grid  = shops.select("shop").crossJoin(dates)       # rows = shops x 30

# BROADCAST JOIN: same result as a normal join, done without shuffling orders.
with_shop = orders.join(F.broadcast(shops), on="shop", how="left")
-- Multiple keys in SQL.
SELECT o.order_id, o.qty * p.price AS amount
FROM bakery.silver.orders AS o
LEFT JOIN bakery.silver.prices AS p
  ON o.item = p.item AND o.shop = p.shop;

-- Cross join.
SELECT s.shop, d.day
FROM bakery.silver.shops AS s
CROSS JOIN bakery.silver.calendar AS d;

-- Broadcast hint: a comment-like note right after SELECT.
SELECT /*+ BROADCAST(s) */ o.order_id, s.city
FROM bakery.silver.orders AS o
LEFT JOIN bakery.silver.shops AS s ON o.shop = s.shop;
What if I change this?

Consequences

ChangeEffect
Join on one key when rows are identified by twoEach row matches several rows on the other side. The result has too many rows and amounts are counted several times.
Join on two keys when one would doHarmless if both are right. But a mismatch in the extra key, such as a stray space, now makes rows fail to match.
crossJoin two large tablesThe row count is the two sizes multiplied. A job that never finishes, or runs out of memory.
Write a join and forget the conditionIt becomes a cross join by accident. Always check the row count after a join.
Broadcast a small tableThe shuffle of the big table is avoided. The join is often several times faster.
Broadcast a table that is too bigThe copies do not fit in memory. The job fails with an out-of-memory error, or is slower than a shuffle would have been.
Add a broadcast hint to the big sideSpark tries to do as you ask, with the bad result above. Hint the small side.
Leave the choice to SparkIt broadcasts automatically when a table is under its size threshold. A hint is for when you know better than its estimate.

Three ideas, kept apart

Multi-key

About matching: two or more columns must all be equal.

Cross

About the result: no matching, every combination.

Broadcast

About performance: how the join is carried out. The result does not change.

Don't confuse these

Join traps, part two

Broadcast is not a join type

You still choose inner or left. Broadcast only decides how Spark performs it. The rows returned are the same.

Cross join vs full join

A full join still matches on a key and keeps unmatched rows. A cross join matches on nothing and pairs everything with everything.

& vs and

In PySpark conditions, combine with & and wrap each part in brackets. Python's word and does not work on columns.

Hint vs command

A hint is a strong suggestion. Spark normally follows it, which is why a wrong hint does real damage.

Check yourself

Quiz

1. A cross join of a 20-row table and a 50-row table returns how many rows?

Every row is paired with every row: 20 times 50.

2. What does a broadcast join avoid?

The small table is copied to each executor, so the large table's rows can be joined where they already are.

3. Which table should be broadcast when joining a 2-billion-row fact table to a 300-row lookup table?

Only a table small enough to fit in memory on every executor can be broadcast.

4. In the first demo, joining on the item alone gave too many rows. Why?

The price list is unique per item and shop together, not per item. Both columns are needed to pick one row.

5. How do you ask for a broadcast join in PySpark?

The join type stays inner or left. F.broadcast marks which side to copy to the executors.

Wrap up

Key takeaways

  • Join on every column needed to identify one row. Too few keys multiplies rows.
  • A cross join pairs everything with everything. Its size is the two row counts multiplied.
  • A broadcast join copies a small table to every executor and avoids a shuffle.
  • Broadcast changes speed, not results. Broadcast only the small side.
  • Spark broadcasts small tables automatically. A hint overrides its judgement.
