Building gold objects for BI and analytics

A gold table is built for the questions people ask. The usual shape is a central table of events (facts) surrounded by tables that describe them (dimensions). Getting this shape right makes every report simpler and every number easier to trust.

The idea

Facts in the middle, descriptions around

A fact table records things that happened, one row per event: a sale, a delivery, a visit. Each row holds numbers to add up (quantity, amount) and the keys that point to who, what, where and when.

A dimension table describes one of those keys: one row per shop, per product, per customer, per calendar day. It holds the names and attributes that reports group and filter by.

Put together, a fact table in the middle and dimensions around it look like a star, so this layout is called a star schema. It is the most common shape for BI.

Two decisions come first, before any SQL is written:

  • The grain. What does one fact row represent? One sale line? One order? One shop per day? Write it down in one sentence. Every later choice depends on it.
  • The questions. Which numbers will people ask for, and which words will they slice them by? Those words become dimensions.
Everyday analogy

A school register. Each lesson is a fact: who attended, which class, what time. The pupil list, the class list and the calendar are the dimensions. A teacher who wants "attendance by class by term" just joins the register to the class list and groups it. The register is kept at the finest grain, one line per pupil per lesson, so any question can be answered from it later.

How it works

A star, built in order

The gold summary is built by joining the fact table to its dimensions and grouping by the attributes people choose. Each step is one of the skills from earlier lessons: joins (03-04), aggregations (03-11) and column names chosen for readers.

Code

Building a star and its gold summary

from pyspark.sql import functions as F

sales  = spark.table("bakery.silver.sales")        # grain: one row per sale line
shops  = spark.table("bakery.silver.shops")        # one row per shop
dates  = spark.table("bakery.silver.dim_date")     # one row per calendar day

# Attach the descriptions to each sale line. Left joins keep every sale.
enriched = (sales
    .join(shops, on="shop_id", how="left")
    .join(dates, on="sale_date", how="left"))

# The gold summary: names people read, grouped by what they ask about.
gold = (enriched
    .groupBy("shop_name", "month_name")
    .agg(F.sum("amount").alias("total_sales"),
         F.count("*").alias("sale_lines")))

gold.write.mode("overwrite").saveAsTable("bakery.gold.sales_by_shop_month")
-- The same summary as a materialized view, so BI reads a stored result.
CREATE OR REPLACE MATERIALIZED VIEW bakery.gold.sales_by_shop_month AS
SELECT s.shop_name, d.month_name,
       SUM(f.amount) AS total_sales,
       COUNT(*)       AS sale_lines
FROM bakery.silver.sales AS f
LEFT JOIN bakery.silver.shops AS s ON f.shop_id = s.shop_id
LEFT JOIN bakery.silver.dim_date AS d ON f.sale_date = d.sale_date
GROUP BY s.shop_name, d.month_name;

Naming matters for BI: plain, readable column names such as total_sales and shop_name, consistent across gold tables, and the grain written into the table comment. Grant the analysts group SELECT on the gold schema rather than on silver (lesson 01-03).

What if I change this?

Modelling decisions

ChangeEffect
Make the grain coarser (shop per month instead of sale line)Far fewer rows and faster reports. Questions about single sales can no longer be answered from this table.
Keep the finest grain in the fact tableEvery question can be answered. Summaries are built on top, as views or materialized views.
Group by a dimension with duplicate keysTotals are inflated (lesson 03-04). Check key uniqueness in each dimension first.
Use an inner join to the shop dimensionSales at unknown shops disappear from every report. A left join keeps them visible.
Store the dimension attributes in the fact table tooSimpler queries, but the table becomes wide and every shop rename must be applied to many rows.
Add a column that users never ask forClutter. Gold tables should answer the agreed questions, nothing more.
Change a column name a report depends onThe report breaks. Rename with a view that keeps the old name, or announce the change.

Summary levels

Fine grain

One row per event. Flexible, large, the basis for everything else.

Daily or monthly

One row per shop per period. The usual dashboard level.

Headline

One row per region or company. Quick, but answers only a few questions.

Real life

Gold tables in use

ScenarioWhat happensFix
Two dashboards show different totals for the same monthOne joined the shop dimension with an inner join, the other with a left joinUse one agreed gold table, with left joins, for both
A shop was renamed and its history splits into two namesThe shop name was copied into the fact tableJoin to the dimension so the current name applies to the whole history

Don't confuse these

Modelling traps

Fact vs dimension

Facts record events and hold numbers. Dimensions describe the things the events refer to.

Grain first

Decide what one row means before anything else. Mixing grains in one table gives wrong totals.

Star vs snowflake

A star keeps each dimension flat. A snowflake splits dimensions into sub-tables. Stars are simpler for BI.

Gold is for readers

Silver keeps detail for engineers. Gold is shaped for the people who read reports, with readable names.

Check yourself

Quiz

1. In a star schema, what does a fact table hold?

Facts record what happened. Dimensions hold the descriptions the facts point to.

2. Which decision must be made first when designing a gold table?

Every other choice depends on what one row means.

3. Why use a left join from sales to the shop dimension?

An inner join would silently drop sales whose shop is missing from the dimension.

4. In the demo, what stayed the same as the grain got coarser?

Grouping only regroups the same sales. The total is preserved; the row count and the per-group counts change.

5. Why avoid a gold summary that groups by a dimension with duplicate keys?

A duplicate key matches the same sale more than once in the join.

Wrap up

Key takeaways

  • Choose the grain first, then the questions, then the shape.
  • Facts hold events and numbers. Dimensions hold the descriptions.
  • Use left joins so that no event disappears from the totals.
  • Gold summaries are built by joining, grouping and aggregating, with readable names.
  • Store a stable, documented grain, so every report answers the same question the same way.
