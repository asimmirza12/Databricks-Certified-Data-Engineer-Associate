Standardising data types and writing silver tables

In bronze, almost everything is text. A price is the characters "4.50". A date is the characters "16/11/2026". This lesson turns text into real numbers and dates, then saves the result as a silver table.

The idea

Make every column the type it claims to be

A column's data type tells Spark what kind of thing it holds. Types matter because they decide what you can do. You can add numbers, but not text. You can ask "which is later?" of two dates, but not of two pieces of text that happen to look like dates.

Changing a value from one type to another is called casting. Casting text "4.50" to a decimal gives the number 4.50.

The catch is values that cannot be converted. What is "n/a" as a number? There are two possible reactions, and you choose which you want:

  • cast is strict. Where the strict setting called ANSI mode is on, a value that cannot be converted makes the whole query fail.
  • try_cast is forgiving. A value that cannot be converted becomes NULL and the query carries on.

"Standardising" also means making text consistent, so that "north ", "NORTH" and "North" all become the same value. Otherwise a report shows three shops where there is one.

When the columns are clean and correctly typed, you write the result to a silver table.

Everyday analogy

Sorting a drawer of loose change from a holiday. Everything is a "coin" until you sort it. Then pounds go in one pile, euros in another, and the button that was in there goes aside. Only after sorting can you count how much money you have. Casting is the sorting. The button is the value that will not convert.

How it works

From text to typed columns

The types you will use most

Whole numbers

INT and, for very large values, BIGINT. IDs and counts.

Exact decimals

DECIMAL(10,2): up to 10 digits, 2 of them after the point. The right type for money.

Approximate decimals

DOUBLE. Fast, but can be off in the last decimal place. Fine for measurements, not for money.

Text

STRING. Anything.

Dates and times

DATE is a calendar day. TIMESTAMP is a day and a time.

True or false

BOOLEAN.

Code

Bronze to silver, start to finish

from pyspark.sql import functions as F

bronze = spark.table("bakery.bronze.orders_raw")

silver = (bronze
    # IDs: text to whole number. try_cast gives NULL for anything that is not a number.
    .withColumn("order_id", F.col("order_id").try_cast("int"))

    # Text: remove stray spaces, then make the capitals consistent.
    .withColumn("shop", F.initcap(F.trim("shop")))

    # Money: strip everything that is not a digit or a point, then make it a decimal.
    .withColumn("price",
        F.regexp_replace("price", "[^0-9.]", "").try_cast("decimal(10,2)"))

    # Dates: say what pattern the text is in. dd/MM/yyyy means day, month, year.
    .withColumn("order_date", F.try_to_timestamp("order_date", F.lit("dd/MM/yyyy")).cast("date"))

    .dropna(subset=["order_id"]))

# Save as a silver table. "overwrite" replaces the table's contents with this result.
silver.write.mode("overwrite").saveAsTable("bakery.silver.orders")
-- The same in SQL: create the silver table from a query.
CREATE OR REPLACE TABLE bakery.silver.orders AS
SELECT
  try_cast(order_id AS INT)                                         AS order_id,
  initcap(trim(shop))                                               AS shop,
  try_cast(regexp_replace(price, '[^0-9.]', '') AS DECIMAL(10,2))   AS price,
  try_to_date(order_date, 'dd/MM/yyyy')                             AS order_date
FROM bakery.bronze.orders_raw
WHERE try_cast(order_id AS INT) IS NOT NULL;

Function availability depends on the runtime version. try_cast and try_to_date are long-standing in Databricks SQL. The PySpark column method .try_cast() and F.try_to_timestamp are newer. If your runtime lacks one, F.expr("try_cast(price AS DECIMAL(10,2))") does the same job. Verify in the docs for your runtime.

Casting and writing options

Whether ANSI mode is on by default depends on the compute. SQL warehouses and serverless have it on. Older classic runtimes had it off. Do not assume: check, or use try_cast where you want forgiving behaviour.

Ways to save the result

overwrite

Replace the table's contents. Simple and safe to rerun. Reprocesses everything each time.

append

Add rows. Right for genuinely new data. Dangerous to rerun.

MERGE

Update matching rows and insert new ones (lesson 01-02). Right for incremental loads with changes.

Don't confuse these

Type traps

cast vs try_cast

cast can fail the query. try_cast never does: it returns NULL instead.

DECIMAL vs DOUBLE

DECIMAL is exact and suits money. DOUBLE is approximate.

DATE vs TIMESTAMP

DATE has no time of day. TIMESTAMP does. Casting a TIMESTAMP to DATE drops the time.

overwrite vs append

overwrite replaces. append adds. Only overwrite is safe to run twice.

Check yourself

Quiz

1. With ANSI mode on, what does CAST('n/a' AS INT) do?

Under ANSI mode a strict cast refuses a value it cannot convert. try_cast would return NULL.

2. Which type should hold prices?

DECIMAL stores exact values. DOUBLE can introduce tiny errors, and STRING cannot be added up.

3. A text column holds dates such as 16/11/2026. What do you need to convert it?

The default layout is year-month-day. Any other layout must be described with a pattern.

4. In the demo, what happened to "£4.50" with try_cast and no cleaning?

The £ sign makes it not a number. try_cast returns NULL. Stripping the sign first lets it convert.

5. A silver load uses mode("append") and is accidentally run twice. What is the result?

append adds rows every time. It does not check whether they were added before.

Wrap up

Key takeaways

  • Bronze columns are mostly text. Silver columns have real types.
  • cast can fail on bad values. try_cast returns NULL instead.
  • Clean before casting: trim spaces, strip symbols, give dates their pattern.
  • Use DECIMAL for money, DATE or TIMESTAMP for time, INT for whole numbers.
  • Save with overwrite or MERGE so the load is safe to rerun.
