Data quality: checks, constraints and expectations

A silver or gold table is only useful if people can trust it. Quality rules say what "correct" means for your data. Then you decide, for each rule, whether a bad row is warned about, dropped, or stops the whole load.

The idea

Write the rule down, then choose what happens when it breaks

A data quality rule is a statement that must be true of every good row. "Price is not missing." "Shop is one of the known shops." "Order date is not in the future." Writing rules down forces agreement on what "correct" means.

Databricks gives you three tools, from simplest to most flexible:

  • Table constraints are rules the table itself enforces. A NOT NULL constraint refuses a row with no value. A CHECK constraint refuses a row that fails a condition. A bad row cannot be written.
  • Pipeline expectations are rules attached to a dataset in a pipeline. Each has an action for bad rows: keep and warn, drop the row, or fail the update. You choose per rule.
  • Your own checks are queries that count violations and raise an alert, in any job. They are the most flexible and the least automatic.

Keys need one warning. A primary key or foreign key declared on a Unity Catalog table is informational: it records the intention, helps the optimiser, but is not enforced. Only NOT NULL and CHECK constraints actually stop bad rows.

Everyday analogy

Checking parcels at a sorting office. Some rules are printed on the door: "no parcels over 30 kg" (a constraint). The door physically refuses a heavy parcel. Other rules are on a clipboard: "log any parcel with a damaged label, but deliver it" (warn), "set aside parcels with no address" (drop), "stop the whole van if a parcel contains glass" (fail). The clipboard rules are the ones that need a decision about what to do.

How it works

Three outcomes for a bad row

The three expectation actions

In a pipeline, each rule can be written in SQL or Python. The action is set per rule:

  • Warn is the default. It keeps invalid rows and records how many failed, so the problem is visible without stopping anything.
  • Drop removes invalid rows before they are written, and records how many were removed.
  • Fail stops the update when any row is invalid. In a triggered pipeline, only that flow is rolled back; other flows continue.

Code

Rules in SQL and Python

-- Pipeline expectations, in SQL. The rule is a named constraint on the dataset.
CREATE OR REFRESH STREAMING TABLE bakery.silver.orders (
  CONSTRAINT price_present  EXPECT (price IS NOT NULL),                       -- warn (default)
  CONSTRAINT valid_shop     EXPECT (shop IN ('North', 'South', 'East')) ON VIOLATION DROP ROW,
  CONSTRAINT positive_qty   EXPECT (qty > 0) ON VIOLATION FAIL UPDATE
)
AS SELECT * FROM STREAM bakery.bronze.orders_raw;
# The same rules in Python. The import is the pipeline module.
from pyspark import pipelines as dp

@dp.expect("price_present", "price IS NOT NULL")                 # warn
@dp.expect_or_drop("valid_shop", "shop IN ('North', 'South', 'East')")
@dp.expect_or_fail("positive_qty", "qty > 0")             # stop the update
def silver_orders():
    return spark.readStream.table("bakery.bronze.orders_raw")
-- Constraints on a plain Unity Catalog table are enforced on every write.
ALTER TABLE bakery.silver.orders ALTER COLUMN order_id SET NOT NULL;
ALTER TABLE bakery.silver.orders ADD CONSTRAINT qty_positive CHECK (qty > 0);

-- A primary key is informational: recorded and used by the optimiser, not enforced.
ALTER TABLE bakery.silver.shops ADD CONSTRAINT shops_pk PRIMARY KEY (shop_id);
# A check of your own, in any job: count the violations and alert if there are any.
bad = spark.table("bakery.silver.orders").filter("price IS NULL OR qty <= 0").count()
if bad > 0:
    raise ValueError(f"{bad} silver order rows fail the quality rules")

Check the exact decorator names and the SQL clause spelling for your runtime in the expectations reference. The pattern is the lesson: name each rule, and choose its action.

What if I change this?

Each action and each constraint

ChangeEffect
Expectation with no action (warn)Bad rows are kept. The failure is counted in the pipeline's metrics, so someone must look.
Change warn to dropBad rows never reach the table. Good rows still load. Totals may fall, silently unless someone reads the drop count.
Change drop to failOne bad row stops the update. Nothing new is published until the data is fixed. Strict, and sometimes disruptive.
Add NOT NULL to a column in a plain tableAny write containing a NULL there is refused.
Add a CHECK constraint to a table that already has bad rowsThe check is applied to new writes. Existing bad rows must be fixed before the constraint can be added.
Declare a primary key that the data violatesNothing is refused. The key is informational, so duplicates still load. Enforce uniqueness yourself, for example with a check.
Use a violation counter alone, with no actionNothing stops. Useful for monitoring, but it does not protect the table.

Which action, when?

Warn

New rule, or a rule that is informative but not critical. Watch the counts first.

Drop

Rows that are useless without the value, such as an order with no ID. Losing them is acceptable.

Fail

Rules that protect a number people act on, such as finance totals. Better late and right than early and wrong.

Don't confuse these

Quality traps

Warn is the default

An expectation with no action only warns. Many people assume bad rows are blocked. They are not.

Primary key is not enforced

On Unity Catalog tables a primary or foreign key is informational. Only NOT NULL and CHECK actually refuse rows.

Drop vs fail

Drop removes the bad row and carries on. Fail stops the update and writes nothing from it.

Constraint vs expectation

A constraint belongs to a table and is always enforced on write. An expectation belongs to a pipeline dataset and is applied on update.

Check yourself

Quiz

1. An expectation has no ON VIOLATION clause. What happens to a row that fails it?

The default action is warn: keep the row and count the violation.

2. Which action stops an update when one row breaks the rule?

ON VIOLATION FAIL UPDATE (or expect_or_fail) stops the update.

3. A primary key is declared on a Unity Catalog table, and a duplicate row is written. What happens?

Primary and foreign keys are not enforced on Unity Catalog tables. They only record intent.

4. In the demo, which action left the table with no bad rows and no update at all when a bad row existed?

Fail rolls back the update, so nothing from it is written.

5. Which statement adds a rule that refuses any NULL order ID on every write?

NOT NULL is an enforced table constraint. A primary key is not enforced, and an expectation belongs to a pipeline, not to the table.

Wrap up

Key takeaways

  • Write quality rules down, then choose what happens to a bad row for each one.
  • Expectations: warn (default, keeps the row), drop (removes it), fail (stops the update).
  • NOT NULL and CHECK constraints are enforced on writes. Primary and foreign keys are not.
  • Warn without monitoring is silent failure. Watch the counts.
  • Use the strictest action for numbers that people act on.
