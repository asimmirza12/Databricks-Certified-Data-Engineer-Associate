The idea

Say what you want, not how to run it

Lakeflow Spark Declarative Pipelines (formerly Lakeflow Declarative Pipelines, and before that Delta Live Tables, or DLT) is Databricks' tool for building data pipelines by declaring datasets. Each dataset is a query that says what a table should contain. You never say "run bronze, then silver, then gold". The pipeline reads which dataset uses which, draws the graph itself and runs it in the right order, in parallel where it can.

A pipeline holds three kinds of dataset:

  • Streaming table: reads its source as a stream and processes each new record once. Best for ingestion and append-only data.
  • Materialized view: recomputed so it always matches its source, incrementally when that is cheaper. Best for joins and aggregations, such as gold summaries.
  • Temporary view: an in-between step that is not stored and can only be used inside the same pipeline.

Both stored kinds are published as Unity Catalog managed tables, by default into the pipeline's default catalog and schema. Each dataset is defined in exactly one place: a second pipeline cannot define or write to the same table.

Running a pipeline is called a pipeline update. It checks the code, builds the graph and refreshes every dataset. Updates can run:

  • Triggered (the default): process what is there, then stop. Usually started from a job on a schedule or trigger.
  • Continuous: keep running and process data as it arrives.

A normal refresh only processes new data. A full refresh empties streaming tables and reprocesses everything still in the source, which is slow and can lose rows if old source files were deleted.

You write the code in SQL or Python files (one pipeline can mix both) in the Lakeflow Pipelines Editor. In Python the module is from pyspark import pipelines as dp; the older import dlt still works but is the legacy name. New pipelines run on serverless compute by default.

Everyday analogy

A bakery's order board instead of a to-do list. With a to-do list, you tell each baker what to do and in what order. With an order board, you just pin up what must be on the shelves: "croissants, made from today's dough, made from today's flour". The head baker works out that flour comes first, starts what can run in parallel, and only bakes fresh what has run out. Asking for a "full refresh" means throwing out every tray and baking everything again from the flour still in the store.

Code

The same pipeline in SQL and in Python

-- transformations/orders.sql : three datasets, no run order written anywhere

-- Bronze: Auto Loader (read_files with STREAM) picks up each new file once
CREATE OR REFRESH STREAMING TABLE bronze_orders
AS SELECT * FROM STREAM read_files('/Volumes/bakery/landing/orders/', format => 'json');

-- Silver: a streaming read of bronze, with quality rules (lesson 03-16)
CREATE OR REFRESH STREAMING TABLE silver_orders (
  CONSTRAINT qty_positive EXPECT (qty > 0) ON VIOLATION DROP ROW
)
AS SELECT order_id, shop, CAST(qty AS INT) AS qty, CAST(price AS DECIMAL(8,2)) AS price
FROM STREAM bronze_orders;

-- Gold: a batch summary, kept up to date. No STREAM for a materialized view.
CREATE OR REFRESH MATERIALIZED VIEW gold_sales_by_shop
AS SELECT shop, SUM(qty * price) AS revenue
FROM silver_orders
GROUP BY shop;
# transformations/orders.py : the same three datasets in Python
from pyspark import pipelines as dp          # legacy code used: import dlt
from pyspark.sql import functions as F

@dp.table()                                  # streaming table: returns a streaming read
def bronze_orders():
    return (spark.readStream.format("cloudFiles")
            .option("cloudFiles.format", "json")
            .load("/Volumes/bakery/landing/orders/"))

@dp.table()
@dp.expect_or_drop("qty_positive", "qty > 0")
def silver_orders():
    return (spark.readStream.table("bronze_orders")
            .select("order_id", "shop",
                    F.col("qty").cast("int").alias("qty"),
                    F.col("price").cast("decimal(8,2)").alias("price")))

@dp.materialized_view()                      # materialized view: returns a batch read
def gold_sales_by_shop():
    return (spark.read.table("silver_orders")
            .groupBy("shop")
            .agg(F.sum(F.col("qty") * F.col("price")).alias("revenue")))

Names without a catalog and schema go to the pipeline's default catalog and schema. A dataset function must only return a DataFrame: never call collect(), count() or saveAsTable() inside it. Check the pipeline SQL and Python references for the full syntax.

What if I change this?

Choices and their effects

ChangeEffect
Leave out STREAM in the bronze queryIt becomes a batch read; a streaming table needs a streaming source, and read_files needs STREAM to act as Auto Loader.
Use STREAM in a materialized viewNot allowed: materialized views read in batch.
Run a normal update twice with no new filesLittle or nothing is processed: streaming tables only take new records.
Full refresh a streaming tableIts data and progress are cleared and every source record is read again. Rows whose files were deleted are gone for good.
Start the update from the editorDebugging behaviour: the compute is kept running for reuse and failures are not retried.
Start the update from a jobProduction behaviour: failures are retried automatically and the compute shuts down afterwards.
Switch from triggered to continuousThe pipeline never stops, so new data lands within moments, but compute runs all the time.
Define the same table in a second pipelineNot allowed: a dataset can be the target of only one pipeline.

Don't confuse these

Pipeline traps

Declarative vs ordered

You declare datasets; the pipeline decides the order from what each reads.

STREAM keyword

Streaming tables read with STREAM. Materialized views never do.

Refresh vs full refresh

Refresh processes new data. Full refresh throws away streaming table data and rebuilds it from the source.

dp vs dlt

The current Python module is pyspark.pipelines (as dp); dlt is the legacy name.

Check yourself

Quiz

1. How does a declarative pipeline know to build silver before gold?

The pipeline reads the dependencies between datasets and builds the graph itself.

2. Which dataset type suits a gold summary that joins and aggregates silver data?

Materialized views are recomputed to match their source and are made for joins and aggregations.

3. What does a full refresh do to a streaming table?

Rows whose source files no longer exist cannot come back.

4. Which import does current Python pipeline code use?

dlt still works but is the legacy module name.

5. In the demo, you deleted old files, then ran a full refresh. What happened to bronze?

A full refresh rebuilds only from what the source still holds.

Wrap up

Key takeaways

  • Declare streaming tables, materialized views and temporary views; the pipeline builds the graph and runs it.
  • Streaming tables read with STREAM and process each record once; materialized views read in batch and stay matched to the source.
  • An update is triggered (run then stop) or continuous; a full refresh rebuilds streaming tables from the source.
  • Updates from a job retry failures; updates from the editor favour quick debugging.
  • Python uses from pyspark import pipelines as dp; dlt is legacy.
