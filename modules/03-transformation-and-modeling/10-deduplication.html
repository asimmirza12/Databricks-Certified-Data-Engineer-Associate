Deduplication

The same order arrives twice. A file is sent again. A record is updated and both versions are kept. Duplicates are normal in raw data, and removing them properly is one of the main jobs of a silver table.

The idea

First decide what "the same" means

Deduplication means keeping one copy of each thing and removing the rest. The hard part is not the removing. It is deciding which rows count as copies of each other. There are two answers, and they need different tools.

  • Exact duplicates. Two rows identical in every column. Usually caused by loading the same data twice. Any one of them will do, because they are the same.
  • Duplicates by key. Two rows with the same order ID, but different values elsewhere. Usually caused by an order being updated: first "placed", later "shipped". These are not interchangeable. You must choose which one to keep, and normally you want the most recent.

Three tools cover these cases:

  • distinct() removes exact duplicates. It compares whole rows.
  • dropDuplicates(["order_id"]) keeps one row for each value of the columns you list. It does not let you say which one.
  • Ranking and keeping the first. Number the rows within each order ID from newest to oldest, then keep number 1. This is the only one of the three that lets you choose.
Everyday analogy

Clearing out a contacts list. If an entry was imported twice and both copies are identical, delete either one. But if you have two entries for the same friend, one with an old phone number and one with a new, you do not delete at random. You keep the newer one. First you had to decide that "same person" was your test, not "identical entry".

How it works

Three ways, three results

The ranking uses a window function. A window function works something out for each row by looking at a group of related rows, without collapsing them into one. Here the group is "all rows with this order ID", and the thing worked out is each row's position when sorted by time. The function is called row_number.

Code

Each method

from pyspark.sql import functions as F
from pyspark.sql.window import Window

orders = spark.table("bakery.bronze.orders_raw")

# 1. Exact duplicates: rows identical in every column.
no_copies = orders.distinct()
no_copies = orders.dropDuplicates()          # with no arguments, the same thing

# 2. One row per key. WHICH row is kept is not defined.
one_each = orders.dropDuplicates(["order_id"])

# 3. One row per key, and you choose which: the most recent.
newest_first = Window.partitionBy("order_id").orderBy(F.col("updated_at").desc())

latest = (orders
    .withColumn("rn", F.row_number().over(newest_first))   # 1 = newest in its group
    .filter(F.col("rn") == 1)
    .drop("rn"))

latest.write.mode("overwrite").saveAsTable("bakery.silver.orders")
-- 1. Exact duplicates.
SELECT DISTINCT * FROM bakery.bronze.orders_raw;

-- 3. Latest row per order. QUALIFY filters on the result of a window function.
SELECT *
FROM bakery.bronze.orders_raw
QUALIFY row_number() OVER (PARTITION BY order_id ORDER BY updated_at DESC) = 1;

-- Before removing anything, look: which keys appear more than once?
SELECT order_id, COUNT(*) AS copies
FROM bakery.bronze.orders_raw
GROUP BY order_id
HAVING COUNT(*) > 1;

In a stream, dropDuplicates has to remember every key it has ever seen, which grows without end. Streaming deduplication therefore needs a time limit, set with a watermark. That is beyond this exam's scope, but know that batch and streaming deduplication differ.

What if I change this?

Which rows survive

ChangeEffect
distinct() on rows that differ in any columnBoth are kept. A different timestamp or a trailing space is enough to make rows "not the same".
dropDuplicates() with no columnsSame as distinct().
dropDuplicates(["order_id"])One row per order ID. Which one is kept can differ from run to run.
dropDuplicates(["order_id", "shop"])One row per combination. The same order ID in two shops is kept twice.

Two rows tie on the ordering columnrow_number still gives 1 and 2, in an order that is not defined. Add a second ordering column to break ties.

Don't confuse these

Deduplication traps

distinct vs dropDuplicates

With no columns they are the same. Only dropDuplicates can be told to look at particular columns.

"One per key" is not "the latest"

dropDuplicates gives you one row per key. It makes no promise about which. For "latest", rank.

row_number vs rank

row_number gives 1, 2, 3 with no repeats, so "= 1" is always exactly one row. rank gives tied rows the same number, so "= 1" can return several.

WHERE vs QUALIFY

WHERE cannot use a window function. QUALIFY is the filter that can.

Check yourself

Quiz

1. Two rows have the same order ID but different status values. What does distinct() do?

distinct compares whole rows. They differ in status, so they are not duplicates to it.

2. You need exactly one row per order, and it must be the most recent version. Which approach?

Only the ranking approach lets you state which row to keep.

3. What does dropDuplicates(["order_id"]) promise about the row it keeps for each order?

The choice is not defined and can change between runs.

4. In the demo, how many rows did distinct() leave from the six?

Only the one exact copy was removed. The later versions of two orders differ, so they stayed.

5. Which SQL clause filters on the result of a window function such as row_number()?

QUALIFY exists for exactly this. WHERE runs before window functions are worked out.

Wrap up

Key takeaways

  • Decide first what makes two rows "the same": every column, or a key.
  • distinct() removes exact copies only.
  • dropDuplicates([key]) keeps one row per key, without promising which.
  • To keep the latest, number rows per key with row_number and keep 1.
  • Clean and standardise before deduplicating, or near-copies slip through.
