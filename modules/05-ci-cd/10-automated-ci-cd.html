Automated CI/CD: deploying from a pipeline

The idea

Let a robot press the buttons

CI/CD means two habits. Continuous integration: every change is checked automatically as soon as it is proposed. Continuous delivery: a change that passes is sent to the next environment automatically, with no manual copying.

You write the steps once in a workflow file kept in the repository. A CI service such as GitHub Actions starts a fresh machine, called a runner, whenever something happens (a pull request opens, a merge lands) and runs your steps on it.

For Databricks the steps are the commands you already know: install the CLI, then bundle validate, bundle deploy and bundle run. The new part is that the runner has no person logged in, so it needs its own identity: a service principal.

Everyday analogy

A bakery with a night-shift robot. The recipe book is the repository. The workflow file is the instruction card taped to the robot. When a baker proposes a new recipe, the robot bakes a test batch in the practice kitchen (dev). When the head baker approves it, the robot bakes it in the shop kitchen (prod). The robot carries its own staff badge (the service principal), never a baker's.

How it works

Two events, two targets

The runner is a fresh machine each time. It gets its identity from the workflow settings, not from a person.

Code

Two workflow files

Workflow files live in .github/workflows/. This one checks and tries every pull request in dev. Names such as nightly and the bakery host are made-up examples.

# .github/workflows/dev.yml: runs on every pull request to main
name: Dev deployment
on:
  pull_request:
    types: [opened, synchronize]
    branches: [main]

concurrency: 1                       # never two deploys at once

jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: dev
    permissions:
      id-token: write                # lets the runner ask for an identity token
      contents: read
    env:
      DATABRICKS_AUTH_TYPE: github-oidc
      DATABRICKS_HOST: ${{ vars.DATABRICKS_HOST }}
      DATABRICKS_CLIENT_ID: ${{ secrets.DATABRICKS_CLIENT_ID }}
      DATABRICKS_BUNDLE_TARGET: dev
    steps:
      - uses: actions/checkout@v4
      - uses: databricks/setup-cli@main
      - run: databricks bundle validate
      - run: databricks bundle deploy

  run_job:
    needs: deploy                    # only after the deploy worked
    runs-on: ubuntu-latest
    environment: dev
    permissions: { id-token: write, contents: read }
    env:
      DATABRICKS_AUTH_TYPE: github-oidc
      DATABRICKS_HOST: ${{ vars.DATABRICKS_HOST }}
      DATABRICKS_CLIENT_ID: ${{ secrets.DATABRICKS_CLIENT_ID }}
      DATABRICKS_BUNDLE_TARGET: dev
    steps:
      - uses: actions/checkout@v4
      - uses: databricks/setup-cli@main
      - run: databricks bundle run nightly

The production file is nearly the same. It triggers on push to main, uses environment: prod, and sets DATABRICKS_BUNDLE_TARGET: prod.

The older recipe stores a service principal token in a repository secret and passes it as DATABRICKS_TOKEN. The docs now steer you to federation instead, so no long-lived secret is stored. Federation needs a policy on the service principal whose subject matches your repository and environment exactly. Verify the exact subject format in the docs for your repository.

What if I change this?

Workflow choices and their effects

ChangeEffect
Trigger on push to main for dev tooYou only learn about a bad change after it is merged.
Leave out permissions: id-token: writeThe runner cannot get an identity token, so federated sign-in fails.
Use a person's token instead of a service principalDeploys break when that person leaves, and the audit trail names a person for a robot's actions.
Set DATABRICKS_BUNDLE_TARGET: prod on pull requestsUnreviewed code reaches prod.
Add concurrencyRuns queue up instead of overlapping, so two deploys cannot fight over the same resources.
Remove the needs: deploy lineThe run may start before the deploy has finished, using old code.
Change the environment name but not the federation policyThe subject no longer matches, and sign-in is refused.

Pipelines in practice

ScenarioWhat happensFix

Don't confuse these

CI/CD traps

CI vs CD

CI checks each change. CD delivers it onward. A pipeline can have one without the other.

Target vs environment

A bundle target is where a bundle deploys. A GitHub environment is a CI setting that holds secrets and rules. They are separate things; you often name them alike.

Service principal, not a person

Automation runs as a service principal. Its permissions decide what the pipeline can touch.

deploy does not run

A deploy only sets things up. A separate bundle run step starts the job.

Check yourself

Quiz

1. Which identity should an automated pipeline deploy as?

Automation should not depend on a person. A service principal is a non-human identity made for this.

2. A federated GitHub Actions job fails to get a token. What is the first thing to check?

Without that permission the runner cannot request an identity token. (The policy subject and env vars are the other usual suspects.)

3. Which pair is the usual mapping of event to target?

Try changes safely in dev first. Only reviewed, merged code reaches prod.

4. In the demo, a pull request with a broken bundle started the workflow. What happened?

Validation runs before deploy, so a bad configuration never reaches a workspace.

Wrap up

Key takeaways

  • CI/CD runs the same bundle commands automatically: validate, deploy, run.
  • Pull requests go to dev; a merge to main goes to prod.
  • The runner signs in as a service principal, ideally with workload identity federation and no stored secret.
  • Use needs for order and concurrency to avoid overlapping deploys.
