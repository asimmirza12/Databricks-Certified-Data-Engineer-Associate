The idea

A history you can read, branch and undo

Git is a version control system. It records every change to a set of files, who made it and why, so you can look back, compare, and return to any earlier state.

The core words are:

  • A repository (repo) is the project: its files and their full history.
  • A commit is one saved snapshot of changes, with a message describing it.
  • A branch is a separate line of commits. You start a branch to try a change without touching the main line.
  • A remote is a copy of the repo on a shared server, such as GitHub or Azure DevOps. Pushing sends your commits there; pulling brings others' commits here.
  • A pull request (PR) asks for your branch to be reviewed and merged into another, usually the main branch.
Everyday analogy

Writing a book with a team, with tracked changes. The manuscript is the repository. Each saved set of edits is a commit, with a note saying what changed. A draft chapter you rewrite separately is a branch. The publisher's shared copy is the remote. Sending your chapter to the editor for approval is the pull request. Nothing is lost, and any earlier draft can be read again.

How it works

Commits form a chain, and branches are pointers into it

Commit c3 and c4 exist only on the feature branch until it is merged. main is unchanged until then.

The everyday loop

  1. Pull the latest commits from the remote.
  2. Branch to start a change on its own line.
  3. Commit the change with a clear message.
  4. Push the branch to the remote.
  5. Open a pull request, get it reviewed, then merge.

The same steps on the command line

  
Databricks does most of this for you, but the commands show what happens underneath.


git clone https://github.com/example/bakery-pipelines.git    # copy the repo to your machine
git checkout -b feature/add-shop-codes                    # start a branch
git add pipelines/load_orders.py                          # stage the changed file
git commit -m "Add shop code check to order load"         # save a commit with a message
git push -u origin feature/add-shop-codes                 # send the branch to the remote
git switch main && git pull                               # return to main and fetch its latest commits

  
The commands are shown for understanding. In the Databricks workspace you use the Git dialog, covered in lessons 05-02 and 05-03.






  
What if I change this?

  
Choices that change the history

  

    
ChangeEffect

    
Commit straight to main, with no branchUnreviewed work goes into the shared line. Hard to undo if it breaks something.

    
Write a vague message such as "fix"Nobody can tell later why the change was made. History becomes hard to use.

    
Forget to pull before startingYour branch starts from an old main, and merging later is harder.

    
Commit a secret password in a fileIt is now in the history, even if deleted later. Rotate the secret; do not rely on deleting the commit.

    
Make the branch long-lived and never merge itIt drifts far from main, and merging it becomes a painful task.

Don't confuse these

  
Git traps

  

    
Commit vs push
A commit is saved on your machine. A push sends it to the shared remote. Nobody else sees a commit until it is pushed.

    
Branch vs repository
A repository is the whole project and its history. A branch is one line within it.

    
Pull request vs merge
A pull request is the request and its review. The merge is the act of combining the branches.

    
Git vs GitHub
Git is the tool. GitHub, Azure DevOps and others host repositories and pull requests.

      1. What does a commit record?
      
      
      
      
A commit is one snapshot of changes plus its message and author.

    

    

      2. Why start a branch for a change?
      
      
      
      
A branch isolates the change until it is reviewed and merged.

    

    

      3. In the demo, which commits did main contain after the feature was merged?
      
      
      
      
Merging brings the feature's commits into main and records a merge commit.

    

    

      4. What does a push do?
      
      
      
      
Push sends local commits to the shared remote. Pull fetches from it.
