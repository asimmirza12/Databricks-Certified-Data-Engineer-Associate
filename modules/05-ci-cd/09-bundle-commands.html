Bundle commands: validate, deploy, run, destroy

A bundle's whole life is handled by a handful of commands. Start it, check it, send it to a workspace, run what it deployed, and finally clean it all away.

The idea

Five verbs for a bundle's life

All bundle commands start with databricks bundle and are run from the bundle's folder. Most take -t <target>.

  • init: creates a new bundle folder from a template, a ready-made starting layout such as default-python.
  • validate: reads the configuration and checks it, without touching the workspace. Errors such as an unknown reference or a missing variable show up here. Run it first, every time.
  • deploy: uploads the files and creates, updates or removes resources in the target's workspace so they match the bundle.
  • run: starts one deployed job or pipeline by its resource key, such as databricks bundle run nightly. It runs what is deployed, not your local edits.
  • destroy: permanently deletes everything the bundle deployed to that target. It asks for confirmation unless you add --auto-approve.

Two helpers are worth knowing: summary lists what is deployed with links, and generate writes bundle YAML for a job or pipeline that already exists in the workspace.

Everyday analogy

Opening a pop-up stall. init: unpack the starter kit. validate: check the plan against the rules before driving out. deploy: set up the stall exactly as planned. run: open for business. destroy: pack everything away and leave the pitch empty.

How it works

The usual loop

init happens once. The edit, validate, deploy, run loop happens many times. destroy is the end.

Try it

Drive a bundle

Run the commands against the dev target. Try running before deploying, editing without redeploying, or deploying with a broken file.

Code

A full cycle in the terminal

databricks bundle init default-python        # answer the prompts; creates a folder
cd bakery_pipelines

databricks bundle validate                    # default target (dev)
databricks bundle deploy -t dev
databricks bundle run -t dev nightly          # "nightly" is the resource key
databricks bundle summary -t dev              # what is deployed, with links

# bring an existing UI-built job into the bundle
databricks bundle generate job --existing-job-id 123456

# remove everything this bundle deployed to dev (cannot be undone)
databricks bundle destroy -t dev --auto-approve

Each command also takes -p to choose a CLI profile and --var for variables. Check flags with databricks bundle <command> --help.

What if I change this?

Command choices and their effects

ChangeEffect
Skip validatedeploy still checks, but you find problems later and nothing tells you about warnings first.
Edit code, then run without deployThe old deployed code runs.
run before ever deployingFails: the resource does not exist in the workspace.
destroy without --auto-approveAsks you to confirm. In CI there is no one to answer, so it waits or fails.
Leave out -tThe default target is used.
run with a pipeline keyStarts a pipeline update instead of a job run.

Don't confuse these

Command traps

deploy vs run

deploy sets things up. run starts them. deploy never runs a job by itself.

validate is local

It checks configuration; it does not prove the code works.

destroy is final

It deletes the deployed jobs, pipelines and files for that target. Use it on purpose.

run uses keys

Pass the resource key from the YAML, not the display name or a job ID.

Check yourself

Quiz

1. Which command checks the configuration without changing the workspace?

validate only reads and checks. deploy and run change things.

2. You edit a notebook locally and run databricks bundle run nightly. Which code runs?

run starts what is deployed. Deploy first to send your edit.

3. What does --auto-approve do on destroy?

Useful in scripts, and dangerous for the same reason.

4. In the demo, what happened when you deployed with the broken YAML ticked?

Configuration errors stop the deploy before anything changes.

Wrap up

Key takeaways

  • init starts a bundle from a template.
  • The loop is edit, validate, deploy, run, with -t choosing the target.
  • run starts what is deployed, by resource key.
  • destroy permanently removes the target's deployment; --auto-approve skips the prompt.
