The idea

Write it once, fill it per environment

A bundle variable is a named placeholder declared under variables in databricks.yml. You use it anywhere in the configuration as ${var.name}. When you deploy, the CLI swaps each placeholder for a real value.

A variable can have a default. A target can override it, which means replace the default with its own value for that environment. You can also pass a value when you run the command.

When more than one value is given, the CLI picks one using a fixed order, strongest first:

  1. --var="name=value" on the command line
  2. An environment variable called BUNDLE_VAR_name
  3. The file .databricks/bundle/<target>/variable-overrides.json
  4. The value set in the chosen target
  5. The top-level default

If none of these gives a value, the deploy fails. One important point: variables are filled in at deploy time. For values that change on every run, use job parameters instead (lesson 04-05).

Everyday analogy

A recipe card with blanks. "Bake at ___ degrees." The card prints a usual value (180). Each branch kitchen writes its own number over it because its ovens differ: that is the target override. And the head baker can shout a number on the day, which beats anything written: that is --var.

How it works

The value with the highest rank wins

The CLI checks from the top and stops at the first source that has a value.

Kinds of variable

Simple

A single text, number or true/false value, such as a catalog name.

Complex

type: complex holds a structure, such as a whole cluster definition. Needs a recent CLI.

Lookup

Finds the ID of a named object, such as a warehouse, in the target workspace. Verify the supported object types in the docs.

Built-in

Values the CLI supplies, such as ${bundle.target} and ${workspace.current_user.userName}.

Code

Declare, use and override a variable

variables:
  catalog:
    description: Catalog the jobs write to
    default: bakery_dev

resources:
  jobs:
    nightly_load:
      name: nightly_load
      parameters:
        - name: catalog
          default: ${var.catalog}       # filled in at deploy
      tasks:
        - task_key: load_sales
          notebook_task:
            notebook_path: ../src/load_sales.py

targets:
  dev:
    mode: development                 # uses the default
  prod:
    mode: production
    variables:
      catalog: bakery                  # override for prod
databricks bundle deploy -t prod                          # catalog = bakery
databricks bundle deploy -t prod --var="catalog=bakery_hotfix"   # flag wins
BUNDLE_VAR_catalog=bakery_ci databricks bundle deploy -t dev     # env var

The deploy-time value lands in the job parameter's default. The notebook then reads the job parameter at run time, so one setting covers both.

What if I change this?

Variable changes and their effects

ChangeEffect
Remove the default and give no other valueThe deploy fails: the variable has no value.
Set the value in the prod targetOnly prod deploys use it. Other targets keep the default.
Export BUNDLE_VAR_catalog in the CI systemBeats the target value and the default, but loses to --var.
Pass --var as wellThe flag always wins.
Expect a variable to change between runsIt will not. Its value is fixed at deploy. Use a job parameter.
Type $var.catalog without bracesNot a reference. Write ${var.catalog}.

Don't confuse these

Variable traps

Order of strength

Flag, then environment variable, then overrides file, then target, then default. The default is the weakest.

Deploy time

Variables are resolved once, at deploy. They are not run-time inputs.

Prefix

The environment variable is BUNDLE_VAR_ plus the variable's name.

Two syntaxes

${var.x} is a bundle variable. {{job.parameters.x}} is a job reference. Don't mix them up.

Check yourself

Quiz

1. How do you reference a bundle variable called catalog?

Bundle variables use a dollar sign and braces, with the var. prefix.

2. The prod target sets catalog: bakery and BUNDLE_VAR_catalog=bakery_ci is set. Which value is used?

An environment variable outranks the target value and the default.

3. Which source has the highest precedence?

A value passed with --var beats every other source.

4. You need a value that changes on every run. What should you use?

Bundle variables are fixed at deploy. Job parameters are set per run.

Wrap up

Key takeaways

  • Declare variables under variables and use them as ${var.name}.
  • Targets override defaults with per-environment values.
  • Precedence: --var, then BUNDLE_VAR_, then variable-overrides.json, then target, then default.
  • Variables resolve at deploy. Use job parameters for run-time values.
