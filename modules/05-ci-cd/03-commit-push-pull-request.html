Commit, push, pull requests and merge conflicts

You have a branch and your changes. Now you save them, share them, ask for review, and bring them into main. Along the way two things can go wrong: a change can be pushed to the wrong place, or two people can change the same lines. This lesson covers both.

The idea

Save, share, review, merge

In a Git folder, the workflow is:

  1. Commit: save your changed notebooks and files as one commit. A commit message is required, and should say what changed and why.
  2. Push: send the commit to the remote branch. The Git dialog offers this as Commit and push.
  3. Create a pull request: ask for the branch to be reviewed and merged. You create it on your Git host, such as GitHub or Azure DevOps. After a push, the Git folder can show a link to open it.
  4. Merge: combine the branch into main, once it is approved.

Databricks recommends that you do not commit straight to main when your permissions allow a branch. If you lack permission to commit to the default branch, create a new branch, push it, and open a pull request.

Everyday analogy

Submitting a homework essay. You save the draft as a final version with a note ("added the results section"). You hand it in to the teacher. The teacher checks it and, once it is approved, it goes into the class file. If a classmate wrote a different ending to the same paragraph, the teacher must choose which words stay: that is a merge conflict.

How it works

A change through to main

The steps are in order. Each one depends on the one before.

When a merge conflicts

A conflict happens when the same lines changed differently on both branches. Git cannot choose, so it stops and marks the file. In the Git folder you then:

  • edit the file to keep the parts you want, and resolve each conflict; or
  • choose Keep all current changes or Take all incoming changes for the whole file.

Then Continue Merge finishes the merge. Abort cancels it and returns the branch to how it was before. Databricks recommends merge over rebase for newcomers, because merge does not rewrite commit history.

What a commit does not change

Committing, pushing and creating a branch do not change your notebook's state. A pull, or a switch that alters the notebook source, can. The docs warn that such an operation may drop cell outputs, comments, version history or widgets. Dashboards are different: switching branch can remove a dashboard that does not exist on the target branch.

Code

  
The same steps as Git commands


git commit -m "Use shop code from the lookup table"    # commit: a message is required
git push -u origin feature/shop-codes                  # push: share the branch
# ...open the pull request on the Git host, get it reviewed, then:
git switch main && git pull                            # update main first
git merge feature/shop-codes                           # merge; a conflict stops here
# on a conflict, edit the file, then:
git add pipelines/load_orders.py && git commit         # finish the merge

  
Your Git host may require a passing check or an approval before merging. Those rules belong to the host, not to Git itself.






  
What if I change this?

  
Choices at merge time

  

    
ChangeEffect

    
Keep all current changes on a conflicting fileThe main version wins. The feature branch's work on that file is dropped from the merge.

    
Take all incoming changesThe feature version wins. Main's work on that file is dropped from the merge.

    
Abort the mergeNothing is merged. The branch returns to its state before the merge.

    
Use rebase instead of mergeThe history is rewritten, which needs force pushes on shared branches. Newcomers should prefer merge.

    
Pull, with cell outputs and widgets in a notebook that changedThe notebook state may be lost, including outputs, comments and widgets.

    
Commit with a vague messageThe history no longer explains the change. Reviewers and later readers lose context.

Don't confuse these

  
Workflow traps

  

    
Abort vs Continue
Abort cancels the merge and restores the branch. Continue finishes it, after conflicts are resolved.

    
Keep current vs take incoming
"Current" is the branch you are on. "Incoming" is the branch being merged in.

    
Commit vs push
Committing saves locally. Pushing shares. A commit is invisible to others until pushed.

    
Pull request vs merge
The pull request is the review. The merge is the change to main. The review should come first.

Wrap up

  
Key takeaways

  
    
    
  • Commit with a clear message, then push to share the branch.
    • 
    
  • Open a pull request on the Git host, and review before merging.
    • 
    
  • A conflict stops the merge. Resolve it, then Continue; or Abort to go back.
    • 
    
  • Commit before pulling. Pulls and branch switches can change notebook state.
