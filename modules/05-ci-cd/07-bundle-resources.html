Bundle resources: jobs, pipelines and more

The resources section is the heart of a bundle. It lists every Databricks object the bundle owns: jobs, pipelines, schemas, volumes, dashboards and others. Resources can point at each other, so a job can run a pipeline defined in the same file.

The idea

A shopping list of objects

A bundle resource is one Databricks object described in the bundle. Resources are grouped by type under resources: jobs, pipelines, schemas, volumes, dashboards and more. Under each type, every object gets a resource key: a short name you choose, such as nightly_load, used to refer to it inside the bundle.

The settings under each key are the same ones the object has in the workspace. A job has tasks and a schedule. A pipeline has a catalog, a schema and its source files. A schema has a catalog and a name.

Resources often need each other. A job's pipeline task needs the pipeline's ID, but that ID only exists after deploy. So you write a resource reference, such as ${resources.pipelines.sales_pipeline.id}, and the CLI fills in the real ID during deploy.

Big bundles split resources into several files, for example resources/jobs.yml, and pull them in with include.

Everyday analogy

A new shop's fit-out list. "Oven A, oven B, display fridge, till." Each item has a label. The till's notes say "connect to the fridge's alarm": you don't know the fridge's serial number yet, so you write "the fridge" and the installer fills in the real number when it arrives. That label is the resource key; the note is the reference.

Code

  
A schema, a pipeline and a job that runs it


# resources/sales.yml, pulled in by include in databricks.yml
resources:
  schemas:
    silver:                               # resource key
      catalog_name: ${var.catalog}
      name: silver

  pipelines:
    sales:
      name: sales_pipeline
      catalog: ${var.catalog}
      schema: ${resources.schemas.silver.name}
      serverless: true
      libraries:
        - file:
            path: ../src/sales_pipeline.py

  jobs:
    nightly:
      name: nightly_sales
      tasks:
        - task_key: refresh_sales
          pipeline_task:
            pipeline_id: ${resources.pipelines.sales.id}   # real ID at deploy
      permissions:
        - group_name: bakery-analysts
          level: CAN_VIEW


# in databricks.yml
include:
  - resources/*.yml

  
Field names follow the workspace API for each object. Some newer resource types need a specific deployment engine; verify in the docs before relying on one.






  
What if I change this?

  
Resource changes and their effects

  

    
ChangeEffect

    
Rename a resource keyThe CLI sees a new resource: it creates one and removes the old one on deploy. Rename the name field instead if you only want a new display name.

    
Delete a resource from the fileThe next deploy removes it from the workspace.

    
Reference a key that does not existValidation or deploy fails with an unknown reference.

    
Hard-code a pipeline ID instead of a referenceWorks in one workspace only, and breaks in every other target.

    
Split resources into several filesFine, as long as include lists them.

    
Change a job in the workspace UIThe next deploy puts the bundle's version back.

Don't confuse these

  
Resource traps

  

    
Key vs name
The key is the bundle's ID for the object. The name is the label in the workspace.

    
${resources...} vs ${var...}
Resource references point at objects in the bundle. Variables hold values you set.

    
Bundle wins
The bundle is the source of truth. UI changes to deployed objects are overwritten.

    
Code is not a resource
Notebooks and Python files are uploaded as files. Only objects like jobs and pipelines go under resources.

  






  
Check yourself

  
Quiz

  

    

      1. How should a job task point at a pipeline defined in the same bundle?
      
      
      
      
A resource reference becomes the real ID in whichever workspace you deploy to.

    

    

      2. You rename a job's resource key and deploy. What happens?
      
      
      
      
The key is the job's identity in the bundle, so a new key looks like a new job.

    

    

      3. In the demo, what did validation report when the pipeline was unticked but the job remained?
      
      
      
      
The job still pointed at a pipeline key that no longer existed.

    

    

      4. How do you keep resources in several YAML files?
      
      
      
      
include takes file paths or patterns such as resources/*.yml.

    

  






  
Wrap up

  
Key takeaways

  
    
    
  • resources lists objects by type: jobs, pipelines, schemas, volumes, dashboards and more.
    • 
    
  • Each object has a stable resource key; its name is what the workspace shows.
    • 
    
  • Link objects with ${resources.<type>.<key>.<field>}, never hard-coded IDs.
    • 
    
  • Split big bundles with include. The bundle overrides UI edits on deploy.
