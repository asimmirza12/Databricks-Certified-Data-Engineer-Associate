What are Declarative Automation Bundles?

You built jobs and pipelines by clicking in the workspace. That works once. To create the same job in a test workspace and then in production, identically, you want it written down as files in Git. A bundle is that written-down project.

The idea

Your project's code and its settings, in one folder

A Declarative Automation Bundle is a folder that holds everything a data project needs: the code (notebooks, Python files, SQL) and a description of the Databricks resources that run it (jobs, pipelines and more). The product was formerly called Databricks Asset Bundles, and the name changed in 2026. You will still see the short form "DABs" in older material.

The description is written in a file called databricks.yml, in a format called YAML. YAML is plain text that uses indentation to show structure.

"Declarative" means you describe what should exist, not the clicks to create it. You write "there is a job called nightly_load with these tasks", and the Databricks CLI makes the workspace match.

Because the whole project is files, it lives in Git. It is reviewed in pull requests, and the same files can be deployed to dev, test and prod. That is the base of CI/CD on Databricks.

Everyday analogy

A flat-pack furniture kit. The box holds the parts (your code) and the instruction sheet (databricks.yml). Anyone with the kit can build exactly the same bookshelf in any room. You do not describe how you moved your hands; you describe what the finished shelf looks like, and the builder makes it so. Rooms are environments: the same kit goes into the dev room, the test room and the production room.

How it works

From files to resources in a workspace

Run the same deploy again with no changes, and nothing changes in the workspace. The description is the source of truth.

The main parts of databricks.yml

bundle

The bundle's name and basic settings.

resources

The jobs, pipelines and other objects to create. Often split into separate files listed under include.

variables

Values that change between environments, such as a catalog name (lesson 05-06).

targets

The environments to deploy to, such as dev and prod (lesson 05-05).

Try it

Build a bundle and deploy it

Choose which resources the bundle describes, then deploy. Deploy again with no change, then remove a resource and deploy once more. Watch the workspace follow the description.

Workspace after deploy

    

    

    
Model: deploy creates what is described, updates what changed, and removes resources that the bundle created earlier but no longer describes.

  






  
Code

  
A minimal bundle


# databricks.yml
bundle:
  name: bakery_pipelines

include:
  - resources/*.yml                 # pull in the resource files

targets:
  dev:
    mode: development
    default: true                   # used when no target is named
    workspace:
      host: https://dev-bakery.cloud.databricks.com


# resources/nightly_load.job.yml
resources:
  jobs:
    nightly_load:
      name: nightly_load
      tasks:
        - task_key: load_orders
          notebook_task:
            notebook_path: ../src/load_orders.py   # a path inside the bundle


databricks bundle validate     # check the description is well formed
databricks bundle deploy       # make the workspace match it

  
The workspace host is an example. The bundle commands are covered properly in lesson 05-09. Check field names in the configuration reference.






  
What if I change this?

  
Editing the bundle

  

    
ChangeEffect

    
Add a task to a job in the YAML, then deployThe job in the workspace gains the task. No clicking needed.

    
Deploy twice with no changeNothing changes the second time. The workspace already matches.

    
Remove a job from the YAML, then deployThe job the bundle created is removed from the workspace.

    
Edit the deployed job by hand in the UIThe next deploy puts it back to what the YAML says. Change the YAML, not the UI.

    
Keep the bundle in GitEvery change is reviewed and recorded, and any version can be deployed again.

Don't confuse these

  
Bundle traps

  

    
Bundle vs Git folder
A Git folder holds code in the workspace. A bundle also describes the jobs and pipelines, and deploys them.

    
Old and new names
Declarative Automation Bundles is the current name. Databricks Asset Bundles (DABs) is the former name.

    
Declarative vs scripted
You describe the end state. You do not write the steps to create it.

    
Deploy vs run
Deploy creates or updates the resources. Running a job is a separate step.

Wrap up

  
Key takeaways

  
    
    
  • A bundle is a folder of code plus databricks.yml, kept in Git.
    • 
    
  • It declares the jobs, pipelines and other resources that should exist.
    • 
    
  • The Databricks CLI deploys it, and the workspace is made to match.
    • 
    
  • Change the YAML, not the deployed resource in the UI.
    •
