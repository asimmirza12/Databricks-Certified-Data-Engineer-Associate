Targets: dev, test and prod

One bundle, several places to deploy it. A target names one of those places and says how deployment should behave there. Development is forgiving and private. Production is strict and shared.

The idea

The same code, promoted through environments

An environment is a separate place where the project runs: dev for building, test for checking, prod for real use. Often each is its own workspace, or at least its own catalog.

A target is a named entry under targets in databricks.yml. Each target says which workspace to deploy to, and can change settings for that environment. Moving the same code from dev to test to prod is called promotion.

Each target can set a mode. There are only two:

  • mode: development: every resource is prefixed with [dev your-name], and schedules and triggers are paused by default. Several developers can deploy the same bundle to one workspace without clashing, and nothing runs on its own.
  • mode: production: none of those safety changes. Resources keep their real names and schedules run. Extra checks apply, such as requiring the current Git branch to match the branch the target names. --force overrides that check.

One target can be the default, used when a command names no target. Set default: true on it. Only one target may be the default.

Everyday analogy

A theatre production. Rehearsals happen in a practice room with name tags on everything ("Sam's script") and no audience: that is development. The dress rehearsal is test. Opening night is production: real names, real tickets, and the curtain goes up on schedule. Same play, three settings, and the rules get stricter as you move towards the audience.

How it works

One bundle, three targets

The code is identical in all three. Only the target's settings differ. -t chooses the target.

What a target can change

workspace

Which workspace to deploy to, by its host address.

mode

development or production, with the behaviour above.

variables

Different values for this environment, such as the catalog name (lesson 05-06).

resources and run_as

Per-target changes to resources, and which identity jobs run as.

Code

  
Three targets in databricks.yml


bundle:
  name: bakery_pipelines

targets:
  dev:
    mode: development               # [dev name] prefix, schedules paused
    default: true                    # used when -t is left out
    workspace:
      host: https://dev-bakery.cloud.databricks.com

  test:
    mode: production
    workspace:
      host: https://test-bakery.cloud.databricks.com

  prod:
    mode: production                # real names, schedules run
    git:
      branch: main                     # deploy only from main, unless --force
    workspace:
      host: https://prod-bakery.cloud.databricks.com


databricks bundle deploy               # goes to dev, the default target
databricks bundle deploy -t prod       # goes to prod

  
Hosts are examples. Presets can fine-tune behaviour per target, such as a name prefix or pausing triggers in production too. Check the deployment modes page for the full list.






  
What if I change this?

  
Target settings and their effects

  

    
ChangeEffect

    
Deploy with no -tThe default target is used: the one with default: true, or the first one if none is marked.

    
Two developers deploy to dev in development modeEach gets their own copy, prefixed with their name. No clash.

    
Use production mode for devNo prefix, so developers overwrite each other's job, and schedules start running.

    
Deploy to prod from a feature branchRefused when the target names main as its branch.

    
Add --force to that deployThe branch check is skipped. Use only when you are sure.

    
Mark two targets default: trueInvalid. Only one target may be the default.

Don't confuse these

  
Target traps

  

    
Target vs environment
The environment is the real place. The target is its entry in databricks.yml.

    
Only two modes
development and production. There is no "test mode". A test target usually uses production mode.

    
Paused, not removed
Development mode pauses schedules. The schedule is still defined, and runs in production.

    
--force
It overrides safety checks such as the branch rule. It is not a fix for errors in the bundle.

  






  
Check yourself

  
Quiz

  

    

      1. What does mode: development do to deployed resources?
      
      
      
      
Development mode keeps each developer's copy separate and stops it running on its own.

    

    

      2. Which target is used when a command gives no -t?
      
      
      
      
The target marked default: true is used. With none marked, the first target is used.

    

    

      3. In the demo, what happened when you deployed to prod from a feature branch?
      
      
      
      
The prod target names main as its branch, so production mode checks the branch.

    

    

      4. What are the valid values for a target's mode?
      
      
      
      
There are only two modes. Target names are chosen by you; modes are not.

    

  






  
Wrap up

  
Key takeaways

  
    
    
  • A target is an environment entry in databricks.yml: its workspace and settings.
    • 
    
  • Development mode prefixes names and pauses schedules. Production mode does not.
    • 
    
  • Production targets can require a Git branch; --force overrides the check.
    • 
    
  • One target is the default. Name the target explicitly in scripts.
